Topic 01

Framework Comparison

Before we compare frameworks, a clarification on what a framework actually is. In the agentic context, a framework is code that implements the agentic loop — perceive, reason, act, observe, repeat — and exposes abstractions so you don't have to write that loop from scratch. The abstractions differ. So do the tradeoffs.

We compare across seven axes: abstraction level, state management, multi-agent support, built-in observability, production track record, learning curve, and governance/HITL support. Read the table first, then we'll unpack each framework.

Framework Abstraction State Mgmt Multi-Agent Observability Production HITL
LangGraph Low–Mid Explicit Strong LangSmith Strong Native
CrewAI High Managed Role-based Limited Moderate Manual
OpenAI Agents SDK Low Manual Handoffs Tracing Good Manual
AutoGen Mid Message-based Strong Weak Research-grade Manual
Agentforce Very High Managed Enterprise Built-in Enterprise Native

LangGraph

LangGraph (by LangChain) models your agent as a directed graph. Nodes are agent steps — each node is a Python function that receives state and returns updated state. Edges are transitions between nodes; they can be conditional (e.g., "if the tool returned an error, go to the retry node; otherwise go to the synthesis node"). You define state as a typed dictionary — an explicit contract for what's in memory at every step.

The explicitness is the point. When something goes wrong in production, you can inspect the state at each node. Checkpointing lets you persist state to a database, so long-running agents survive restarts. Human-in-the-loop is a first-class primitive: you pause at a node, wait for human input, resume. For teams that need auditability — compliance, regulated industries, anything covered by M5's EU AI Act discussion — LangGraph's explicitness is not overhead, it's the requirement.

The tradeoff is verbosity. Building a simple three-step agent in LangGraph requires more boilerplate than other frameworks. The graph abstraction has a learning curve, especially for engineers new to DAG-based thinking.

Aria & COMPASS

COMPASS is the natural fit for LangGraph. The Planner → parallel Researchers → Synthesizer flow maps cleanly to a graph with conditional edges. You get checkpointing (research takes time), explicit state (which sources have been consulted), and HITL (the human can review the Planner's research questions before execution begins). For Aria: LangGraph is overkill. Aria's flow is nearly linear — read CRM, reason, act, maybe escalate. The graph overhead doesn't earn its keep for a simple customer success agent.

CrewAI

CrewAI takes a different metaphor: you hire a crew. Each agent has a role, a goal, and a backstory (a system prompt, in practice). Agents collaborate on tasks. You choose a process — sequential (agents execute in order, each building on the last) or hierarchical (a manager agent delegates to specialist agents). The framework handles the orchestration loop for you.

This high abstraction buys speed. You can prototype a five-agent competitive research system in an afternoon. The cost: you give up control over the internals. Error handling, memory management, and retry logic are handled by the framework — which means when they fail, debugging requires reading CrewAI's internals rather than your own code. Custom memory backends and fine-grained tool permissions require more work than frameworks with lower abstraction.

CrewAI's sweet spot is demos, early experiments, and situations where a working prototype in 48 hours matters more than production hardening. For COMPASS, CrewAI gets you to a working multi-agent system fast. Whether it survives contact with real-world scale is a different question.

OpenAI Agents SDK

The OpenAI Agents SDK (formerly Swarm) is deliberately lightweight. It gives you agents and handoffs. An agent is a model with instructions and tools. A handoff is an explicit function call that transfers control from one agent to another. The loop is close to the metal — you can read and understand the framework source in an afternoon.

This low abstraction is a feature for teams that want to know exactly what is happening. There's no magic. State management is your responsibility. Built-in tracing covers tool calls and handoffs. The SDK is optimized for the OpenAI ecosystem, though it can be adapted for other providers with more effort.

Aria

The OpenAI Agents SDK is a strong fit for Aria. Aria's flow is: intake customer query → read CRM → reason → pick action (refund, email, escalate). That's a clean handoff pattern. The SDK's simplicity means it's easy to add the guardrails from M5 — input validation, output checks, the escalate_to_human tool as a HITL interrupt — without fighting the framework's abstractions.

AutoGen

AutoGen (Microsoft) frames multi-agent collaboration as a conversation. Agents send messages to each other. A UserProxyAgent can represent a human in the loop. A ConversableAgent can execute code, which is where AutoGen really shines: it supports agents that write Python, run it in a sandbox, observe the output, and iterate. That makes it powerful for research workflows, coding agents, and internal developer tooling.

AutoGen's weak spot is production observability. The message-passing model produces conversational logs, not structured traces. For customer-facing systems with strict SLAs, you'd need to add significant logging infrastructure. For COMPASS, the message-passing model maps reasonably well — each Researcher can be an agent that reports findings via messages — but you'll spend real time on observability setup that LangGraph gives you for free.

Salesforce Agentforce

Agentforce is not a developer framework. It's an enterprise platform baked into the Salesforce ecosystem. If your company runs Salesforce CRM, Agentforce lets you deploy agents that have native access to your Salesforce data, workflows, and permissions model. Low-code configuration, enterprise-grade security and governance, built-in audit trails.

The constraint is obvious: it only makes sense inside Salesforce. If you're building custom agents, integrating non-Salesforce systems, or need flexibility in model choice, Agentforce is not the answer. It's relevant here because many organizations encountering agentic AI will encounter it through the Salesforce channel — particularly the non-technical stakeholders in your audience.

Framework Best for Avoid when
LangGraph Complex flows, production systems, auditability, HITL-heavy workflows Simple linear tasks; small teams new to graph-based thinking
CrewAI Rapid multi-agent prototyping, role-based task delegation Production hardening, fine-grained error control
OpenAI Agents SDK Clean handoff patterns, transparency, OpenAI-native teams Provider flexibility, complex persistent state
AutoGen Code-execution agents, research workflows, internal developer tooling Customer-facing production, strict latency SLAs
Agentforce Enterprises fully embedded in the Salesforce ecosystem Any non-Salesforce context; custom agent development
Topic 02

Framework vs. Building from Scratch

Abstraction is either leverage or a debugging nightmare. The same layer of code that speeds up your initial build becomes an obstacle when something goes wrong and you can't see inside it. The decision between using a framework and rolling your own comes down to one question: does this framework's abstraction model match what I'm trying to build?

Build from scratch when
  • You need full control over the agentic loop
  • The framework's abstractions don't match your mental model
  • You're building something the framework wasn't designed for
  • Debugging through framework internals is costing more time than the framework saves
  • Vendor lock-in is a real risk for your organization
vs
Use a framework when
  • The framework's abstractions match your use case cleanly
  • You need to ship a prototype quickly
  • The team is small and can't maintain custom infrastructure
  • The framework is open source and you can inspect it
  • You've prototyped enough to know the framework's limits

The M2 lab — building a ReAct loop from scratch — was intentional. You should understand the perceive–reason–act–observe cycle before a framework hides it from you. When LangGraph adds a node, you should be able to describe what that node is doing in terms of the underlying loop. If you can't, the framework is hiding complexity you might need to reason about later.

Rule of Thumb

Prototype with a framework. Understand what it's doing — read the source, trace a single request end-to-end, know where state lives. Then decide whether the abstraction is earning its keep. If you're spending more time working around the framework than working with it, the abstraction isn't a fit.

Common Mistake

Teams sometimes reach for a framework in the first hour, before they've articulated what their agent actually needs to do. The framework then shapes the design — the agent's behavior is determined by what the framework makes easy, not by what the task requires. Prototype by hand first. Even a rough sketch of the loop, state, and tools reveals constraints that matter for framework selection.

Topic 03

Building MCP Servers

We covered MCP as a protocol in M4. Here we build one. An MCP server is a process that exposes tools to agents via the Model Context Protocol. Clients — agents, Claude Desktop, IDEs, anything implementing the MCP client spec — connect, discover what tools are available, and call them. The server handles the execution and returns structured results.

MCP Server — Three Required Components
01
Server Manifest
A JSON description listing every tool the server exposes. Each tool entry includes a name, a human-readable description (the model reads this to decide when to call the tool), and an input schema (JSON Schema). The quality of your descriptions directly affects how reliably agents invoke the right tool.
02
Tool Handlers
Python (or TypeScript) functions that execute when a tool is called. They receive validated arguments, perform the actual work — call an API, query a database, write a file — and return a structured result. Error handling belongs here: return structured errors rather than raising exceptions, so the agent can reason about what went wrong.
03
Transport Layer
How the agent communicates with the server. stdio is for local development and subprocess deployment — the agent spawns the server as a child process. HTTP + SSE is for remote deployment — the server runs as a web service, enabling multi-client access and containerized deployment.

Let's build a minimal MCP server that wraps a weather REST API. We'll implement two tools: get_current_weather and get_forecast. The pattern generalizes to any REST API your agents need to reach.

weather_mcp_server.py — Manifest and Tool Registration
from mcp.server import Server from mcp.server.stdio import stdio_server from mcp.types import Tool, TextContent import httpx, os app = Server("weather-service") # Tool manifest — the model reads these descriptions to decide what to call @app.list_tools() async def list_tools(): return [ Tool( name="get_current_weather", description="Get current weather conditions for a city. " "Returns temperature (°C), conditions, and wind speed.", inputSchema={ "type": "object", "properties": { "city": {"type": "string", "description": "City name"}, "country_code": {"type": "string", "description": "ISO 3166-1 alpha-2 code"}, }, "required": ["city"], }, ), Tool( name="get_forecast", description="Get a 5-day weather forecast for a city.", inputSchema={ "type": "object", "properties": { "city": {"type": "string"}, "days": {"type": "integer", "minimum": 1, "maximum": 5}, }, "required": ["city"], }, ), ]
weather_mcp_server.py — Tool Handlers
# Tool handler — call this when the agent invokes a tool @app.call_tool() async def call_tool(name: str, arguments: dict): api_key = os.environ["WEATHER_API_KEY"] # Never hard-code credentials base_url = "https://api.openweathermap.org/data/2.5" async with httpx.AsyncClient() as client: if name == "get_current_weather": resp = await client.get( f"{base_url}/weather", params={"q": arguments["city"], "appid": api_key, "units": "metric"}, ) if resp.status_code != 200: # Return structured errors — don't raise; let the agent reason about it return [TextContent(type="text", text=f"Error: {resp.json().get('message', 'unknown')}")] data = resp.json() result = { "city": data["name"], "temp_c": data["main"]["temp"], "conditions": data["weather"][0]["description"], "wind_kph": data["wind"]["speed"] * 3.6, } return [TextContent(type="text", text=str(result))] elif name == "get_forecast": days = arguments.get("days", 5) resp = await client.get( f"{base_url}/forecast", params={"q": arguments["city"], "appid": api_key, "units": "metric", "cnt": days * 8}, ) return [TextContent(type="text", text=resp.text)] # Run with stdio transport for local/subprocess deployment if __name__ == "__main__": import asyncio asyncio.run(stdio_server(app))

Authentication: MCP servers requiring credentials should receive them via environment variables. Never hard-code API keys. For OAuth flows (e.g., connecting to Google Workspace, GitHub), the MCP spec supports a client-to-server credential negotiation step — check the spec for the current implementation pattern.

For deployment: run the server locally via stdio (the agent spawns it as a subprocess — zero network overhead), containerize it with Docker and expose HTTP+SSE for multi-agent access, or deploy as a serverless function for cloud-native scale. The MCP ecosystem has grown significantly; the official MCP server registry and npm's @modelcontextprotocol namespace include pre-built servers for GitHub, Slack, Notion, Stripe, PostgreSQL, and dozens more. Check there before building from scratch.

Design Principle

Write tool descriptions as if the model has never seen your codebase. Describe what the tool does, when to use it, and what the output looks like. A vague description like "get weather data" produces worse tool selection than "Get current weather conditions for a city — returns temperature in Celsius, sky conditions, and wind speed in kph." The description is the interface contract between your tool and the model's reasoning.

Topic 04

Model Selection

The default assumption — use the biggest frontier model for everything — is wrong. It was wrong in 2024 and it's more wrong now. Smaller, fine-tuned models outperform frontier models on specific, well-defined tasks. They're also faster, cheaper, and can run locally. The discipline is knowing when frontier power is actually required.

We use a decision framework across four axes: reasoning complexity, task definition, latency requirements, and data sensitivity.

Model Selection — Decision Framework
Broad world knowledge + complex multi-step reasoning
Claude Opus / GPT-4o / Gemini Ultra
Frontier — reasoning complexity justifies cost
Well-defined, repetitive, domain-specific classification or summarization
Haiku / GPT-4o-mini / Mistral 7B
Smaller fine-tuned model — fraction of the cost, comparable quality
Latency-sensitive tasks (<500ms)
Smaller cloud model or local inference
Frontier models can't reliably hit sub-500ms at scale
Sensitive data that cannot leave the device (legal, medical, financial)
Local: MLX on Apple Silicon / Ollama
Data sovereignty — no cloud dependency

The Cascade Pattern

The cascade pattern uses a cheap model for initial routing and a frontier model only when the task genuinely requires it. Apply it wherever your agent receives a high volume of inputs that can be classified before expensive reasoning begins.

model_cascade.py — Route simple queries before touching the frontier model
from anthropic import Anthropic client = Anthropic() def classify_query(query: str) -> str: """Use a fast, cheap model to classify the query type.""" response = client.messages.create( model="claude-haiku-4-5", # Fast, cheap — perfect for classification max_tokens=20, messages=[{ "role": "user", "content": f"Classify this customer query as: 'simple_faq', 'order_issue', or 'complex_complaint'.\n\nQuery: {query}\n\nRespond with only the category." }] ) return response.content[0].text.strip() def handle_query(query: str, customer_data: dict) -> str: query_type = classify_query(query) if query_type == "simple_faq": # Still use fast model — no frontier needed for FAQ lookup response = client.messages.create( model="claude-haiku-4-5", max_tokens=200, messages=[{"role": "user", "content": f"Answer this FAQ: {query}"}] ) else: # Complex reasoning, empathy, nuanced response — frontier justified response = client.messages.create( model="claude-opus-4-5", max_tokens=800, messages=[{ "role": "user", "content": f"Customer context: {customer_data}\n\nQuery: {query}\n\nProvide a detailed, empathetic response." }] ) return response.content[0].text

Multi-Agent Model Selection: COMPASS

In COMPASS, the three agents don't need the same model. The Planner generates the research agenda — it benefits from a frontier model because it needs to decompose ambiguous competitive intelligence questions into precise research tasks. The parallel Researchers do constrained summarization of fetched documents — a well-defined, repetitive task that a smaller, faster model handles well. The Synthesizer assembles the final report from structured summaries — it needs judgment about what's important, which justifies a frontier model for the final step.

This model selection strategy roughly triples throughput and cuts cost by 60–70% compared to using a frontier model for every agent step, with minimal quality loss on the final output. Run evals (from M5) to verify quality before committing to smaller models in production.

Common Mistake

Teams benchmark their agent on small samples, see that the frontier model produces better outputs, and conclude they must use the frontier model everywhere. The right comparison is: does the quality difference in intermediate steps materially affect the quality of the final output? Often it doesn't. Measure final output quality, not intermediate step quality.

Topic 05

Deployment Patterns

Where you run your agent affects latency, cost, operational complexity, and — critically — what data you're allowed to send where. There are four main patterns. Most production systems use more than one.

Pattern 01
Cloud Functions
AWS Lambda, GCP Cloud Run, Azure Functions. Scalable, managed, pay-per-use. No servers to maintain. Cold starts can add 1–3 seconds of latency on first invocation — a real concern for synchronous agents that a user is waiting on. For asynchronous agents (batch processing, background tasks), cold starts are irrelevant.
Scalable Managed Cold starts
Pattern 02
Containerized (Docker / Kubernetes)
More control, predictable latency, no cold starts if you keep containers warm. Higher operational overhead — you own the infrastructure. Right choice for agents with strict latency SLAs or complex dependencies that don't package cleanly into function deployments.
Predictable Ops overhead
Pattern 03
Edge (Cloudflare Workers, Vercel Edge)
Deploy to data centers close to users. Very low network latency. Severely limited compute — no long-running processes, limited memory, restricted runtime environments. Good for lightweight routing agents and thin proxy layers. Not for multi-step reasoning or complex tool orchestration.
Low latency Limited compute
Pattern 04
Local (MLX / Ollama)
Model runs on-device. Data never leaves the machine. Essential for privacy-sensitive workloads — legal review, medical records, personal finance. MLX on Apple Silicon delivers impressive throughput on M-series chips. Ollama provides a clean local inference server for a wide range of open models. The capability gap vs. frontier models is closing, but not closed.
Data sovereign No cloud cost Capability gap

The Privacy vs. Capability Tradeoff

Local models are the only option when data cannot leave the device. As of 2026, models like Llama 3 and Mistral running locally on M-series hardware are genuinely capable on well-defined tasks. They still trail frontier models on complex multi-step reasoning, long-context synthesis, and tasks that benefit from broad world knowledge. The gap is closing, and it's closing faster than most enterprise procurement timelines.

Design for this: build your agent's tool interface so the model is swappable. If you architect Aria against a frontier model today, you should be able to drop in a capable local model in 12 months without restructuring the agent. The agentic loop and tool definitions shouldn't change — only the inference call.

Architecture Principle

Treat the model as a dependency, not an assumption. Define a model interface layer in your agent — a single place where you swap between claude-opus, claude-haiku, a local MLX model, or an Ollama endpoint. This makes A/B testing models in production tractable and prevents frontier model lock-in from becoming a data governance problem later.

Topic 06

Observability and Eval Tooling

In M5 we established why observability matters: without traces, debugging a multi-agent system is archaeology. Here we evaluate the tools. The landscape has consolidated somewhat, but there's still no single winner. Your choice depends on your team's priorities: data sovereignty, eval maturity, compliance requirements, or existing ML monitoring infrastructure.

Langfuse
Open source — self-hostable — cloud option
Best-in-class for LLM observability. Traces full agentic loops — each span records model call, tokens, cost, latency. User feedback loops, session grouping, dataset management. Strong LangChain and LangGraph integration. Self-hostable means your traces stay in your infrastructure.
Best for: teams wanting data sovereignty, LangGraph users, broad framework support
Braintrust
Cloud — eval-first platform
Eval-first design with excellent LLM-as-judge support. Strong dataset management — version-controlled test sets, regression tracking across deploys. If structured evals are your priority and you don't need self-hosting, Braintrust is the most mature dedicated eval platform.
Best for: teams with mature eval workflows; regression testing across model versions
Galileo
Enterprise — cloud — SOC 2
Enterprise-focused with strong hallucination detection and guardrail monitoring built in. Turnkey for regulated industries. Higher cost than open-source alternatives. If you're shipping agents into healthcare or finance and need a compliance-ready observability stack, Galileo removes significant setup overhead.
Best for: regulated industries; enterprise compliance requirements
Phoenix (Arize)
Open source — local-first
Open-source observability from Arize. Strong OpenTelemetry support makes it drop-in for teams already using OTel. Excellent embedding visualization and retrieval debugging — useful when your agents use vector search (RAG, M3). Best if you're already in the Arize ML monitoring ecosystem.
Best for: RAG debugging; OTel-native teams; embedding visualization

PromptFoo — Lightweight CI/CD Evals

PromptFoo deserves a separate mention because it occupies a different niche. It's not a full observability platform — it's a lightweight eval framework designed to integrate into your CI/CD pipeline. You define test cases (prompt + expected output criteria), run them against your agent, and fail the build if quality regresses. Lower overhead than Braintrust, easier to integrate than rolling your own. Use it for prompt regression testing when you're iterating quickly and don't yet need a full eval platform.

Recommendation

Start with Langfuse. It's free, self-hostable, and supports most frameworks out of the box. Add PromptFoo when you want evals in CI/CD. Migrate to Braintrust when evals become a first-class priority and you need dedicated dataset management. Adopt Galileo only if enterprise compliance specifically requires its hallucination detection and audit features — the cost is hard to justify otherwise.

Common Mistake

Teams add observability after something breaks in production. The right order is: set up Langfuse before you deploy anything. Traces from your first week of production traffic are invaluable for understanding normal behavior. Without that baseline, distinguishing a regression from normal variance is guesswork.

Module 06 Lab

Two Frameworks, One System, One Comparison

Build the same agent system in two different frameworks. Observe what each framework makes easy, what it makes hard, and what you would choose in production.

The goal is not just to build two working systems. The goal is to develop an informed opinion about framework tradeoffs grounded in direct experience — not documentation or benchmarks. By the end of this lab, you should be able to answer "which framework would you use for this, and why?" with specifics.

Step 1 — Choose Your System

Pick one of the two running examples from this curriculum. Both are valid choices; they test different framework axes.

Option A
Aria — Customer Success Agent
Tools: read_crm, query_order_history, issue_refund(≤$50), escalate_to_human, send_email. Tests: tool orchestration, guardrails, HITL for escalations, simple linear flows. Frameworks to try: OpenAI Agents SDK + LangGraph.
Option B
COMPASS — Competitive Intelligence
Three agents: Planner, parallel Researchers, Synthesizer. Tests: multi-agent coordination, parallel execution, state passing between agents, conditional routing. Frameworks to try: LangGraph + CrewAI.

Step 2 — Build Implementation 1 (Suggested: LangGraph)

LangGraph is the suggested first framework for both options — it forces you to be explicit about state and transitions. For Aria, define a state dict with customer context, action history, and a flag for escalation status. For COMPASS, define graph nodes for Planner, each Researcher, and Synthesizer with conditional edges routing based on whether all Researchers have returned results.

Starter structure for COMPASS in LangGraph:

compass_langgraph.py — State and Graph Structure
from typing import TypedDict, List, Annotated from langgraph.graph import StateGraph, END import operator # Explicit state — you control exactly what's in context at every node class CompassState(TypedDict): query: str research_questions: List[str] # Set by Planner research_results: Annotated[List[str], operator.add] # Accumulated by Researchers final_report: str # Set by Synthesizer error: str # Set if any node fails # Node functions — each receives state, returns state update def planner_node(state: CompassState) -> dict: # Call frontier model to decompose query into research questions questions = run_planner(state["query"]) return {"research_questions": questions} def researcher_node(state: CompassState, researcher_id: int) -> dict: # Each researcher handles one question — use cheaper model question = state["research_questions"][researcher_id] result = run_researcher(question) return {"research_results": [result]} # operator.add accumulates these def synthesizer_node(state: CompassState) -> dict: # Frontier model assembles final report from accumulated results report = run_synthesizer(state["research_results"], state["query"]) return {"final_report": report} # Build the graph builder = StateGraph(CompassState) builder.add_node("planner", planner_node) builder.add_node("researcher_0", lambda s: researcher_node(s, 0)) builder.add_node("researcher_1", lambda s: researcher_node(s, 1)) builder.add_node("synthesizer", synthesizer_node) builder.set_entry_point("planner") builder.add_edge("planner", "researcher_0") builder.add_edge("planner", "researcher_1") builder.add_edge("researcher_0", "synthesizer") builder.add_edge("researcher_1", "synthesizer") builder.add_edge("synthesizer", END) compass_graph = builder.compile()

Step 3 — Build Implementation 2 (Suggested: CrewAI or OpenAI Agents SDK)

For COMPASS: rebuild the same system in CrewAI. Define a Crew with three agents — Planner, Researcher, Synthesizer — with roles, goals, and backstories. Use the hierarchical process so the Planner manager delegates to Researchers. For Aria: rebuild in CrewAI or the OpenAI Agents SDK. The SDK's handoff pattern maps naturally to Aria's flow: triage agent → specialist agent → escalation agent.

Starter structure for COMPASS in CrewAI:

compass_crewai.py — Crew Definition
from crewai import Agent, Task, Crew, Process # Define agents by role, goal, and backstory planner = Agent( role="Research Planner", goal="Decompose the competitive intelligence query into focused, answerable research questions.", backstory="You are a senior analyst who specializes in structuring ambiguous questions into actionable research tasks.", llm="claude-opus-4-5", # Frontier model for planning ) researcher = Agent( role="Market Researcher", goal="Research and summarize findings for a single research question.", backstory="You are a meticulous researcher who produces concise, evidence-backed summaries.", llm="claude-haiku-4-5", # Cheaper model for constrained summarization tools=[web_search_tool, fetch_url_tool], ) synthesizer = Agent( role="Intelligence Synthesizer", goal="Produce a coherent, actionable competitive intelligence report.", backstory="You are a strategic analyst who synthesizes research into executive-grade reports.", llm="claude-opus-4-5", # Frontier model for final synthesis ) # Tasks define what each agent does and the expected output plan_task = Task(description="Decompose query into 2-3 research questions.", agent=planner, expected_output="List of research questions.") research_task = Task(description="Research each question.", agent=researcher, expected_output="Factual summary per question.") synthesis_task = Task(description="Synthesize findings into final report.", agent=synthesizer, expected_output="Structured competitive intelligence report.") crew = Crew( agents=[planner, researcher, synthesizer], tasks=[plan_task, research_task, synthesis_task], process=Process.hierarchical, # Planner manages Researcher delegation manager_llm="claude-opus-4-5", )

Step 4 — Write Your Comparison

After both implementations are working, write a short (one page) structured comparison. Answer these questions specifically — not in the abstract, but grounded in what you actually experienced building both.

  1. What did each framework make easier? Specific examples: "LangGraph made it easy to inspect state between nodes. CrewAI made the agent role definition feel natural."
  2. What did each framework make harder? Specific examples: "LangGraph required more boilerplate to set up the graph. In CrewAI, I couldn't control which sub-results went to which agent."
  3. Where did you fight the framework? Moments where the abstraction got in the way and you spent time working around it rather than with it.
  4. How would you add Langfuse tracing to each? Actually do it — trace at least one tool call in each implementation and compare the debugging experience.
  5. Which would you use in production and why? Your answer should reference specific production concerns: observability, HITL support, error handling, state persistence.

Deliverables

Two working implementations (Python scripts or notebooks) and a written comparison document. The comparison is the primary deliverable — the code is evidence for your claims, not the goal in itself.

Reflection Prompt

After completing the lab: if you had to implement Aria using a framework you didn't use in this lab — AutoGen or Agentforce — what would you predict would be easy and hard, based on what you now understand about how framework abstractions affect development? Write two sentences. This is the skill the module is actually training: the ability to evaluate a framework before committing to it.

Capstone Connection

The Module 08 capstone is built framework-free — raw Anthropic SDK. That's deliberate: you need to understand what every line does because you wrote it. This lab is why that choice is defensible. You now know exactly what LangGraph and CrewAI provide (state persistence, checkpointing, visual debugging, retry logic) and what you give up by going to raw SDK (all of that — in exchange for full transparency and zero abstraction overhead). When the capstone breaks at 2 AM, you'll know where to look because there's nowhere to hide.

Checkpoint

Before moving to Module 07: write a one-sentence framework verdict for your next agentic project. It should be specific and falsifiable — not "depends on the project" but "start with LangGraph if the workflow has conditional branching and state you need to persist across failures; start with raw SDK otherwise." Vague preferences don't transfer to architectural decisions under deadline pressure.

Module Summary

  • LangGraph gives explicit, auditable state management and native HITL — the right choice for complex production systems needing conditional routing and checkpointing. Steeper learning curve, worth it for the control.
  • CrewAI trades control for speed-to-prototype. Right for multi-agent demos and early experiments; requires significant hardening before it's production-ready.
  • The OpenAI Agents SDK is close to the metal — good for teams that want transparency and clean handoff patterns without a lot of abstraction overhead.
  • AutoGen excels at code-execution and research workflows. Its observability requires extra setup and it's not optimized for customer-facing production.
  • Agentforce is an enterprise platform, not a developer framework. Relevant inside Salesforce ecosystems; irrelevant outside them.
  • Framework vs. scratch: prototype with a framework, understand what it does, then decide whether the abstraction is earning its keep. Never let a framework shape your agent's design before you've defined what the agent needs to do.
  • An MCP server needs three things: a tool manifest with high-quality descriptions, tool handlers that return structured results (including errors), and a transport layer. Credentials go in environment variables — never hard-coded.
  • Don't default to the largest frontier model. Use the cascade pattern: cheap model for routing and classification, frontier model only for complex reasoning. Apply the model selection framework across four axes: reasoning complexity, task definition, latency, and data sensitivity.
  • Cloud functions scale without ops overhead but introduce cold start latency. Containers give predictable latency at higher ops cost. Edge works for lightweight routing only. Local inference (MLX, Ollama) is the only option when data cannot leave the device.
  • Start with Langfuse — it's free, self-hostable, and broadly compatible. Add PromptFoo for CI/CD eval regression testing. Migrate to Braintrust when evals become a dedicated workstream. Galileo for enterprise compliance requirements only.
