Running Example
Running Example: Maya

Throughout these six modules, we follow Maya — a marketing analyst at a mid-size SaaS company. She's been using AI tools (ChatGPT, Claude) for 18 months and has been asked to build the company's first internal AI-powered tools: a meeting notes summarizer and a recipe recommender. No engineering background. Just curiosity and a deadline. Her questions drive the examples.

Module F01
What Language Models Actually Are
FOUNDATION
⏱ 1 week
Open Module →
Why this matters
Most practitioners use AI tools every day without understanding what's happening under the hood. This module closes that gap. Once you know how models learn and generate text, the design decisions in the main curriculum — context engineering, guardrails, hallucination defenses — stop seeming arbitrary and start making obvious sense.
Before you can build with language models, you need to understand what they actually are — not the marketing version, but the real one. This module explains how models go from raw text on the internet to a system that can answer questions, write code, and summarize meetings. No math required. What is required: genuine curiosity about what's happening inside the black box you're about to wire into a production system.
Core Topics
  • The shift from rules to learning: how AI got useful Machine learning, neural networks, training data — what these actually mean
  • Training vs. inference: two completely different things How the model learned what it knows; how it applies that knowledge at runtime
  • What the model "knows" — and what it's making up Parametric knowledge, training cutoffs, and the hallucination mechanism
  • Why models are probabilistic, not deterministic Temperature, sampling, and why the same prompt gives different answers each time
  • The model landscape: GPT, Claude, Gemini — what actually differs Parameters, fine-tuning, instruction-tuning, and capability differences
Exercise
The Temperature Test — send the same prompt 10 times at temperature 0, then 10 times at temperature 1. Document what changes, what stays the same, and explain in plain language why.
Module F02
Tokens and Context: The Physics of Language Models
FOUNDATION
⏱ 3–4 days
Open Module →
Why this matters
Tokens are the atom of everything in a language model. Understanding what they are — and understanding the context window as finite working memory — explains why agents fail at long tasks, why API costs scale the way they do, and why context engineering (Module 3 of the main curriculum) is a core skill rather than a nice-to-have.
Maya's first question when she got her API bill: "Why did summarizing one document cost more than I expected?" The answer is tokens. This module explains what tokens are, how the context window works as the model's finite working memory, and why the economics of language models are inseparable from these concepts. You'll leave with a mental model that makes every API call make sense.
Core Topics
  • What is a token? Not a word, not a character — something in between Byte-pair encoding; how rare words and punctuation tokenize differently
  • Autoregressive generation: how models produce text one token at a time Left-to-right; why this matters for latency, cost, and output quality
  • The context window: everything the model sees at once System prompt, conversation history, injected documents, tool results — all in one window
  • Why bigger context windows don't solve everything The "lost in the middle" problem; attention quality at long ranges
  • Tokens as currency: cost, latency, and economics Per-token pricing; why a 1M-token context is expensive; input vs. output token costs
Exercise
Find the limit. Take a long document — a meeting transcript, a report — and try to process it in a single API call. Find where it breaks. Then design a chunking strategy to handle it correctly.
Module F03
APIs: The Plumbing of Modern Software
FOUNDATION
⏱ 3–4 days
Open Module →
Why this matters
Every agent in the main curriculum makes API calls — to language models, databases, and external services. Understanding APIs isn't optional. It's the literacy you need to read documentation, debug failures, and understand what's happening when an agent calls a tool.
When Maya's meeting summarizer stopped working, the error said "429 Too Many Requests." She had no idea what that meant. This module makes that gap disappear. APIs are how software talks to software — and every AI tool you'll ever build or use depends on them. You don't need to build APIs. You need to understand them well enough to use them confidently and debug them when they break.
Core Topics
  • What an API actually is: a contract for software-to-software communication Endpoints, methods, the request/response pattern; what REST means
  • HTTP: the protocol everything runs on GET vs. POST; headers; status codes (200, 401, 429, 500) and what each means
  • JSON: the universal language of data exchange Key-value pairs, arrays, nesting; reading and writing JSON confidently
  • Authentication: API keys, security, and what happens when keys leak Bearer tokens, environment variables, key rotation — practical security habits
  • Rate limits, quotas, and graceful error handling 429 Too Many Requests; exponential backoff; what happens when you exceed limits
  • Anatomy of an LLM API call: request, parameters, response model, messages, temperature, max_tokens, stop sequences — what each controls
Hands-On Lab
Make your first raw API call to Claude using curl. Modify the temperature. Change the system prompt. Read the full JSON response. Find the token usage fields. Make it fail intentionally (wrong API key, over max_tokens) and read the error.
Module F04
Data, Storage, and How AI Finds Information
FOUNDATION
⏱ 3–4 days
Open Module →
Why this matters
Agents retrieve, store, and reason over information — not just generate text. Before you can understand RAG, vector stores, and context engineering (all central to the main curriculum), you need to understand how data is stored, searched, and retrieved. This module builds that foundation.
Maya's recipe recommender needs to find recipes that match a user's description — not by keyword, but by meaning. "Something light and summery" shouldn't only return recipes that contain those exact words. This module explains how AI-powered search actually works, why it's fundamentally different from traditional search, and what the data infrastructure behind it looks like.
Core Topics
  • Structured vs. unstructured data: why the distinction matters for AI Tables and rows vs. documents and free text; where AI excels, where it struggles
  • What databases actually are: the three types you'll encounter Relational databases, document stores, key-value stores — use cases for each
  • How traditional search works — and why it's insufficient for AI Keyword matching, inverted indexes; what full-text search can't do
  • Embeddings: turning text into numbers that capture meaning Vector representations; why semantically similar sentences embed to similar vectors
  • Vector stores: databases built for similarity search Approximate nearest-neighbor (ANN) search; popular options (Pinecone, Weaviate, pgvector)
  • Why AI doesn't know about last week: training cutoffs and runtime retrieval Static model weights vs. dynamic retrieval; the RAG pattern as the bridge
Hands-On Lab
Build a simple semantic search over 20–30 short documents. Compare keyword search vs. embedding-based search on the same 5 queries. Document where they agree, where they diverge, and why.
Module F05
Prompts, Instructions, and Model Behavior
FOUNDATION
⏱ 3–4 days
Open Module →
Why this matters
You will write prompts for every agent you build. Understanding how they actually influence model behavior — and how to get structured, consistent output — is non-negotiable before you start wiring prompts into agentic systems where you can't manually review every response.
Maya's meeting summarizer works fine for some meetings and badly for others. The difference isn't the model — it's what she's asking it to do and how. This module is about prompt craft as a discipline: not tricks and hacks, but a structured understanding of how models respond to instructions, what kinds of instructions work, and how to get reliable output from a system that is, by nature, probabilistic.
Core Topics
  • The anatomy of a prompt: system message, user messages, conversation history What the model sees vs. what the user sees; role hierarchy; how context flows
  • How models follow instructions: instruction-tuning explained Base models vs. instruction-tuned models; RLHF; why models follow system prompts
  • System prompts: setting persona, constraints, format, and guardrails What belongs in the system prompt; length vs. specificity tradeoffs
  • Temperature and sampling: controlling randomness Temperature 0 vs. 1; top-p; when to use creative vs. deterministic settings
  • Few-shot examples: showing the model what you want One-shot, few-shot; when examples beat descriptions
  • Structured output: requesting JSON instead of prose Output format instructions; JSON mode; why structured output is essential for agents
Hands-On Lab
Prompt iteration sprint. Start with a vague prompt for a meeting summarizer. In exactly 5 iterations, improve it until it produces consistent JSON with action_items, summary, and attendees fields. Document what changed each round and what the biggest impact was.
Module F06
Failure Modes: What AI Gets Wrong and Why
FOUNDATION
⏱ 1 week
Open Module →
Why this matters — and why it comes last
Every module in the main curriculum — guardrails, HITL design, evals, observability — exists because AI systems fail in predictable, architectural ways. This module is the bridge: learn what breaks and why, so when the main curriculum says "here's how to defend against it," you understand what you're defending against.
Maya's meeting summarizer once confidently attributed an action item to someone who wasn't even in the meeting. The model didn't flag uncertainty. It just stated it as fact. This isn't a bug you can fix with a patch — it's a property of how language models work. This module is an honest accounting of how AI fails: the mechanisms, the patterns, and the practical defenses. You'll end this curriculum knowing exactly what you're up against.
Core Topics
  • Hallucinations: confident wrongness and why it's architectural, not a bug The autocomplete nature of LLMs; why confidence does not equal accuracy
  • Knowledge cutoffs and temporal reasoning failures Static training data; what models get wrong about recent events; mitigation strategies
  • Calibration: when the model doesn't know it doesn't know Overconfidence; the spectrum from "I don't know" to confidently fabricated detail
  • Prompt injection: when external content hijacks the model's instructions Direct and indirect injection; why agents with tool access are especially vulnerable
  • Bias from training data Representation bias, recency bias; how it appears in real outputs
  • Practical defenses: grounding, verification, structured output, human-in-the-loop Citation requirements; double-checking against source data; when to route to humans
Hands-On Lab
Stress-test an AI. In 30 minutes, try to produce: 3 hallucinations, 2 prompt injection attacks, 1 calibration failure (model is confidently wrong about something checkable). Document what worked. Then: for each failure you produced, describe one specific defense you'd build.
