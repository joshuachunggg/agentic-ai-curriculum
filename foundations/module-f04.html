Data, Storage,
and How AI Finds Information

Agents don't just generate text — they retrieve, store, and reason over information. Before you can understand RAG, vector stores, and context engineering (all central to the main curriculum), you need to understand how data is stored and how search actually works. This module builds that foundation.

Running Example · Maya

Maya wants her meeting summarizer to know about company-specific context: the team structure, internal project codenames, and a custom glossary of 200 internal terms. Topic 01

Structured vs. Unstructured Data: Why the Distinction Matters

Not all data is the same shape. This seems obvious, but the failure to distinguish between structured and unstructured data is responsible for a surprising number of poorly designed AI tools. Understanding the difference tells you which tool to reach for — and when AI is solving a real problem versus adding unnecessary complexity.

Structured Data

Structured data is organized into a defined schema — rows, columns, fixed fields. Every record has the same shape. A CRM database has fields for customer name, email, company, tier, and last contact date — and every customer record fills in those same fields. A spreadsheet of orders has columns for order ID, product, quantity, price, and date. A SQL database table for inventory has a fixed set of columns and every row conforms to them.

The defining property: you know the structure before you see the data. You can write a query against it without reading its contents first. "Give me all customers in the Enterprise tier who haven't been contacted in 90 days" is a precise, answerable SQL query. The database executes it in milliseconds and returns exact results.

Unstructured Data

Unstructured data has no predefined schema. The content matters; the container is just a vessel. Meeting transcripts. Emails. PDFs. Slack messages. Wikipedia articles. Product reviews. Legal contracts. The information inside these is meaningful, but it isn't organized into consistent fields you can directly query.

You can't write a SQL query against a meeting transcript to find "all discussions about budget overruns." There's no "budget_overrun" column. The information might be there — buried in a sentence, phrased a dozen different ways — but extracting it requires reading and understanding language, not filtering a field.

Semi-Structured Data

Semi-structured data sits in between. It has some structure — typically key-value pairs or nested objects — but not a rigid, consistent schema. JSON records where different records have different fields. A product catalog where some items have a color field and others don't. API responses that return varying keys depending on the resource type. You'll encounter this constantly when working with APIs and modern web data.

Where AI Excels — and Where It Doesn't

For structured data, traditional databases are exceptional. SQL queries retrieve exactly what you want, instantly, with zero hallucination risk. AI is overkill — and unreliable — for "give me all orders over $100." A database query does that faster, cheaper, and with perfect accuracy every time. Using an AI model to answer questions that are really just database queries is a common architectural mistake. It's slower, more expensive, and less reliable.

For unstructured data, the situation reverses. Traditional keyword search is weak here. AI is powerful — it can read a meeting transcript and extract semantic meaning, classify the discussion, summarize key decisions, and identify action items. No traditional database query can do that. The content has meaning that machines couldn't reliably extract until language models matured.

Most real AI applications bridge both worlds. Maya's meeting summarizer processes unstructured transcripts (the input) but produces structured outputs — a JSON record with fields for attendees, decisions, action items, and follow-ups. Her recipe recommender searches unstructured recipe descriptions but returns a structured list with names, match scores, and preparation times. Understanding this bridge is foundational.

The Data Pipeline Pattern

In practice, AI systems often follow a pipeline: unstructured data comes in, gets processed by a model, and its meaningful content gets stored in a structured or semi-structured format that can be retrieved and queried later. A transcript becomes a structured summary. A customer email becomes a classified ticket record. A product review becomes a sentiment score and extracted theme tags. This transformation — unstructured to structured — is one of the most valuable things AI makes possible at scale.

Key Insight

AI doesn't replace databases for structured data — it complements them. The right architecture typically uses a traditional database for structured records (customer data, order history) and AI-powered retrieval for unstructured content (documents, transcripts, notes). Forcing AI to "remember" structured facts is unreliable. Querying a database for those facts and injecting them into the AI's context is reliable.

Topic 02

What Databases Actually Are: The Three Types You'll Encounter

A database is not just "a place to store data." A filesystem stores data. What makes a database distinct is the ability to query, filter, sort, and retrieve data efficiently at scale — across millions or billions of records, in milliseconds, with precision. That querying capability is what makes a database useful. Everything else is organizational detail.

You'll encounter three main types of databases when building AI tools — plus a fourth category purpose-built for AI. Each is designed for a different kind of query and a different kind of data. Using the wrong one adds friction without solving anything.

Type Best For Examples
Relational SQL Structured data with defined relationships. Customer records, order history, inventory, financial data. Any data where you know the schema upfront and need to join across tables. PostgreSQL, MySQL, SQLite
Document Store Flexible schemas where records don't all have the same fields. Blog posts, user profiles, product catalogs with varying attributes, API response caches. Natural for JSON-shaped data. MongoDB, Firestore
Key-Value Store Fast lookups by a known key. Session data, caching computed results, feature flags, simple counters. You know the key; you just want the value. No complex queries needed. Redis, DynamoDB
Vector Store AI Semantic similarity search over embeddings. Finding documents, images, or records that are conceptually similar to a query — regardless of exact wording. The foundation of RAG systems. Pinecone, Weaviate, Chroma, pgvector

Relational Databases

Relational databases have been the backbone of business software for 40+ years. Data lives in tables — rows and columns. Tables can reference each other through keys. A customer record in the customers table has a unique ID; orders in the orders table reference that ID. You can join them to answer "show me all orders for customers in California." This relational structure is powerful for exactly the kinds of queries that structured business data requires.

SQL — Structured Query Language — is the query language for relational databases. You don't need to write SQL to understand why relational databases matter. The key concept: structured data with relationships is exactly what relational databases were designed for, and they do it exceptionally well. Don't try to replace them with AI for this job.

Document Stores

Document stores store data as documents — usually JSON. Each document is self-contained and can have a different structure from the others. This flexibility is valuable when your data doesn't fit neatly into fixed columns. A product in an electronics catalog has a wattage field; a product in an apparel catalog has a size_range field. In a relational database, you'd need a complex schema to handle this. In a document store, each product just has whatever fields are relevant to it.

The tradeoff: document stores are less efficient at complex queries that cross-reference many records. Use them when schema flexibility matters more than complex relational querying.

Key-Value Stores

Key-value stores are the simplest database type: a key maps to a value, like a dictionary. Redis is the most common example. They're extremely fast — sub-millisecond lookups — but limited. You can only look up by the exact key you already know. No filtering, no sorting, no querying by content. Use them for caching (store the result of an expensive computation under a key, retrieve it instantly next time), session storage, and any pattern where "I know exactly what I'm looking for" holds true.

Key Insight

Databases are not interchangeable. A relational database is excellent for "give me all customers in California who haven't renewed in 90 days." A vector store is excellent for "find me the 5 meeting transcripts most similar to this one." Using the wrong tool for the job — trying to do semantic search in a relational database, or storing relational data in a vector store — creates unnecessary complexity and poor performance. Knowing which category a problem belongs to is the first architectural decision.

Topic 03

How Traditional Search Works — and Why It Falls Short

Before you can appreciate what semantic search does differently, you need to understand exactly how traditional search works. Most people interact with search daily without knowing what's happening under the hood. The mechanics are worth understanding — because they explain precisely where keyword search breaks down, and why AI-powered retrieval is genuinely different rather than just marketing language.

Keyword Search and Inverted Indexes

The foundation of most search is the inverted index. When you index a document collection, the system processes every word in every document and builds a mapping: word → list of documents containing that word. Search for "budget" → instantly retrieve all document IDs in the inverted index entry for "budget." This lookup is very fast, even at scale, because the index pre-computes the hard work.

The limitation is immediate and fundamental: the inverted index maps words to documents. Not concepts. Not meanings. Words. Search for "budget" and you get every document containing the exact string "budget." You get nothing for documents that discuss finances, expenditures, spending, costs, or allocation — unless those exact words are also in your query.

TF-IDF: Better Ranking, Same Limitation

TF-IDF (Term Frequency-Inverse Document Frequency) is the classic algorithm for ranking results. TF measures how often your search term appears in a specific document — a document that mentions "budget" fifteen times is probably more about budgets than one that mentions it once. IDF measures how rare the term is across the entire document collection — common words like "the" or "meeting" have low IDF and shouldn't dominate rankings; rare terms like "EBITDA" have high IDF and carry more signal.

Multiply TF by IDF and you get a relevance score for each document. This is meaningfully better than pure keyword count. It doesn't solve the fundamental problem: TF-IDF still operates entirely on word matches. A document about "Q3 financial planning" scores zero for a search for "third-quarter budget review" because "third-quarter" and "financial" don't overlap with "Q3" and "budget."

Full-Text Search: Incremental Improvements

Modern databases like PostgreSQL and search engines like Elasticsearch offer "full-text search" that goes beyond basic keyword matching. Stemming treats "run," "runs," and "running" as the same token. Phrase matching penalizes documents where your search terms appear in unrelated sentences. Relevance ranking combines multiple signals. These are meaningful improvements over basic inverted index lookup.

They're still fundamentally limited to finding matching words, not matching meaning. Full-text search closes some of the synonym gap — but it still misses the cases where natural language uses entirely different vocabulary to express the same concept.

Maya's Recipe Recommender Problem

Maya has 300 recipes in a spreadsheet. A user describes: "I want something healthy, vegetarian, that would work well for a team lunch, not too spicy." Keyword search returns every recipe that contains the word "vegetarian" — 40 recipes, unsorted by relevance. It finds nothing for "healthy" (the recipes don't use that word). It has no concept of "appropriate for a team lunch." The user gets a bad experience. Semantic search, which we'll cover next, handles this correctly.

What Keyword Search Is Still Good For

This isn't a case against keyword search — it's a case for knowing when it's the right tool. Keyword search excels when users know the exact terminology. Searching a codebase for a function name. Finding a specific email by subject line. Looking up a product by its SKU. In these cases, the user has the exact words, and keyword search is fast and precise. The limitation only appears when users search by meaning rather than by word — which is most of the time in natural language use cases.

Topic 04

Embeddings: Turning Text into Numbers That Capture Meaning

This is the conceptually hardest topic in this module. Take it slowly. The payoff is understanding a mechanism that underlies most of what makes modern AI retrieval work — RAG, semantic search, recommendation systems, and more.

The Problem to Solve

Computers work with numbers. Text is not numbers. To do math on text — to measure whether two pieces of text have similar meaning — we need to convert text to numbers in a way that preserves semantic relationships. A naive encoding (assign every word a number: "the" = 1, "cat" = 2, "sat" = 3...) doesn't work. The numbers would be arbitrary. "Cat" (2) and "dog" (4) would seem as different as "cat" (2) and "democracy" (8741), even though cats and dogs are semantically related and cats and democracy are not.

What we need is a number representation where similar meanings produce similar numbers. That's exactly what embeddings are.

What an Embedding Is

An embedding is a list of numbers — a vector — that represents the meaning of a piece of text. Typically 768, 1536, or 3072 numbers long depending on the model. These numbers are produced by a neural network trained specifically to ensure that semantically similar text produces similar vectors.

The neural network learned these representations by training on enormous amounts of text. Through that training, it developed an internal representation of meaning — not rules anyone wrote, but patterns learned from billions of examples of language in use. The embedding is the output of that learned representation for a specific piece of text.

The Geometric Intuition

Think of each embedding as a point in a high-dimensional space. Two pieces of text with similar meaning end up close together in that space. Two pieces of text with very different meanings end up far apart.

"The meeting was postponed" and "We pushed the call back" end up close to each other — they express the same idea with different words. "Please forward the invoice" and "The cat sat on the mat" end up far apart — they have essentially nothing in common semantically.

This geometric relationship is meaningful and consistent. The word "king" minus "man" plus "woman" produces a vector close to "queen" — a famous example showing that the arithmetic of embeddings preserves semantic relationships. You don't need to understand the math to use embeddings. But understanding the geometry helps: distance in embedding space corresponds to difference in meaning.

Measuring Similarity: Cosine Similarity

Once two pieces of text are both embeddings, you can measure how similar they are. Cosine similarity computes the angle between two vectors and returns a number between 0 and 1. A score of 1 means identical meaning. A score near 0 means completely unrelated. A score of 0.85 between a user's query and a recipe description suggests that recipe is highly relevant to what the user was asking for.

This single number — computable from two vectors in milliseconds — is what enables semantic search. Compare the user's query embedding to every document embedding, rank by cosine similarity, return the top results. That's the core of it.

Embedding Models

Embedding models are separate, specialized neural networks trained specifically to produce good vector representations. They're different from the models that generate text — they're purpose-built for representation quality, not generation quality. Common examples include OpenAI's text-embedding-3-large, Google's gecko, and open-source options like BAAI/bge or the sentence-transformers family.

Calling an embedding model is simple: send a string, receive an array of floating-point numbers. Here's what the API response looks like:

{
  "object": "embedding",
  "embedding": [
    0.0023064255,
    -0.009327292,
    0.015987842,
    ...  // 1535 more numbers
  ],
  "model": "text-embedding-3-small",
  "usage": {"prompt_tokens": 8, "total_tokens": 8}
}

That array has 1,536 numbers for this model. Each number encodes a dimension of meaning that the model learned during training. You don't need to understand what each number represents — you just need to know that similar texts produce similar arrays.

Key Insight

Embeddings are the bridge between language and math. Once text is an embedding, you can use geometric operations to find "similar" content — without knowing what words were used. Two meeting transcripts about a budget discussion will have similar embeddings even if one says "allocation" and the other says "spending." This is the foundation of semantic search, RAG, and many other AI capabilities. The model isn't matching words. It's comparing meaning, represented as geometry.

Topic 05

Vector Stores: Databases Built for Similarity Search

You now understand what an embedding is. The next problem is practical: how do you search across a large collection of embeddings efficiently? If Maya has 300 recipe embeddings, comparing her query embedding to all 300 is trivial. But what if you have 100,000 transcripts? Or 10 million product descriptions? Brute-force comparison becomes a bottleneck. Vector stores solve this.

The Scale Problem

Suppose you have 1 million document embeddings, each with 1,536 dimensions. To find the 5 most similar to a query embedding using exact comparison, you'd compute cosine similarity 1 million times. At scale, that takes seconds — too slow for a real-time search interface. At tens of millions of documents, it becomes impractical entirely.

Approximate Nearest Neighbor (ANN) Algorithms

The solution is Approximate Nearest Neighbor (ANN) algorithms. Instead of checking every embedding exactly, ANN algorithms use clever data structures — HNSW graphs (Hierarchical Navigable Small Worlds), inverted file indexes (IVF), product quantization — to find "close enough" neighbors very quickly. Instead of checking all 1 million embeddings, the algorithm might check only a few thousand strategically chosen ones, using the data structure to skip large portions of the space that are unlikely to contain close matches.

The tradeoff is explicit and known: you might miss the absolute closest vector 1–2% of the time. In practice, this is acceptable. Semantic search doesn't need to find the single mathematically closest embedding — it needs to return results that are genuinely relevant, and ANN delivers that at millisecond latency even at tens of millions of vectors.

Purpose-Built Vector Databases

Vector stores are databases designed from the ground up to store embeddings and serve ANN queries at scale. The major options each have tradeoffs worth knowing:

Pinecone is fully managed — no infrastructure to run. You create an index, push embeddings to it, query it. Easy to start, scales well, no DevOps required. Popular for prototypes and production deployments that don't want to manage infrastructure.

Weaviate is open source, self-hostable or cloud-managed. Strong support for hybrid search (combining keyword + semantic in a single query). Good choice when you need both semantic search and traditional filtering on structured metadata.

Qdrant is open source with a high-performance Rust-based engine. Fast and resource-efficient. Good documentation. Popular for teams that want control over their infrastructure.

Chroma is open source and designed to be easy to use locally. The default choice for getting a semantic search prototype running on a laptop in an afternoon. Less suited for production at scale.

pgvector is a PostgreSQL extension — it adds vector search to a PostgreSQL database you might already be running. If your application already uses Postgres, pgvector lets you avoid running a separate database while still getting semantic search. Performance doesn't match dedicated vector stores at very large scale, but for most applications it's more than sufficient.

Hybrid Search

Sometimes you need both kinds of search at once. "Find me documents semantically similar to this query, but only from Q3 2025, and only from the engineering team's meetings." The date and team filters are exact — traditional structured filtering. The similarity match is semantic. Hybrid search combines both: filter by structured metadata first, then rank the filtered results by semantic similarity. Most modern vector stores support this pattern, and it's the practical design for most real-world retrieval systems where you have both structured metadata and unstructured content.

The RAG Pipeline, End to End

With all the pieces in place, here's how Retrieval-Augmented Generation (RAG) works — the pattern that underlies Maya's recipe recommender and most real AI retrieval applications:

1
Preprocessing (done once, offline)
Take all your documents. Chunk them into pieces — paragraphs, sections, or fixed-size windows with overlap. Embed each chunk using an embedding model. Store each embedding alongside its source text and any metadata (document ID, date, author) in a vector store.
2
Query Time (happens for each user request)
Embed the user's question using the same embedding model. Search the vector store for the top-K most similar chunks. The vector store returns the actual text of those chunks, not just their IDs.
3
Context Injection
Take the retrieved chunks and inject them into the LLM's context window, alongside the user's original question. "Here are the 5 most relevant documents from our knowledge base. Using only these documents, answer the user's question."
4
Generation
The LLM reads the retrieved context and generates a grounded response. It isn't relying on its training data — it's reasoning over the specific documents you retrieved. Hallucination risk drops significantly because the model has the actual source material in front of it.

This is RAG. The main curriculum's Module 3 covers it in depth. What matters now is that you understand the pipeline — and that each step depends on the concepts from this module: embeddings to convert text to searchable vectors, a vector store to index and retrieve them efficiently, and context injection to give the model the retrieved information.

Maya Builds a Semantic Recipe Search

Maya embeds all 300 recipes — title + ingredients + description concatenated into a single string, producing a single embedding per recipe. She stores the embeddings in a local Chroma vector store running on her laptop. When a user says "something healthy and vegetarian for a team lunch," Maya's system embeds that query and finds the 5 most similar recipe embeddings. The results are coherent and relevant — not a keyword match, but a meaning match. She can now show those 5 recipes with a brief description. This works without any rule-writing on her part. She didn't define what "healthy" means or enumerate vegetarian recipes. The embedding model encoded those concepts during its training.

Topic 06

Why AI Doesn't Know About Last Week: Training Cutoffs and Runtime Retrieval

Every language model has a training cutoff — a specific date after which the model has no knowledge of what happened in the world. This is a direct consequence of how these models are built: they're trained on a large static dataset, and that dataset has an end date. The weights — the billions of numerical parameters that encode the model's knowledge — are frozen once training is complete.

What the Cutoff Means in Practice

Ask a model about an event that happened after its training cutoff and one of two things happens. Either the model honestly says it doesn't know — which is the correct behavior. Or, more dangerously, the model generates a plausible-sounding response based on patterns in its training data, with no flag that the information might be outdated or fabricated. Models can't reliably distinguish "I know this" from "I don't know this but I'm pattern-matching something plausible." That second failure mode — confident-sounding but ungrounded responses about recent events — is one of the most common sources of AI errors in practice.

The Gap Is Larger Than You Think

Training large models takes months. There's typically a 6–12 month gap between when training data was collected and when a model becomes available to the public. After release, models often remain in production for one to two years before being replaced. Add it up: a user interacting with a deployed model today might be talking to a model whose knowledge stopped accumulating 18–24 months ago. In fast-moving domains — regulatory changes, competitive landscapes, technology releases, market events — that gap is significant.

This isn't a flaw that will be fixed with the next model release. It's a structural property of how models are built. The solution isn't to wait for a fresher model. The solution is retrieval.

The Right Solutions

When recency matters, plan for retrieval from an up-to-date source rather than relying on the model's parametric knowledge. The patterns for doing this are well-established:

Web search tools: give the model a tool that can search the web in real time. Perplexity does this by default. You can build agents that call web search APIs before answering questions about current events. The model's knowledge cutoff becomes irrelevant when it can retrieve fresh information mid-conversation.

RAG against a maintained database: for private or specialized knowledge that isn't on the public web, build a retrieval system against a database you keep updated. Internal documents, product specifications, customer records, recent research reports — maintain these in a vector store and retrieve at query time.

Explicit context injection: for simple cases, just give the model the relevant recent information directly in the prompt. "Today is May 2026. Here is the current status of Project Orion: [recent document text]. Given this context, summarize the key risks." The model's training cutoff doesn't matter when you've injected the relevant facts.

What Models Are Still Good At, Regardless of Cutoff

Training cutoffs constrain factual knowledge about time-sensitive events. They don't constrain reasoning, language understanding, code writing, analysis, or synthesis. A model from two years ago can still write excellent code, analyze a document you provide, explain complex concepts, and reason through a problem. These capabilities don't expire. The limitation is narrow: factual claims about recent events, current prices, recent product releases, and similar time-sensitive specifics.

This distinction matters for how you design AI tools. If the tool involves reasoning over data you provide — summarizing a document, analyzing a contract, structuring a meeting transcript — the training cutoff is essentially irrelevant. If the tool involves making claims about current state of the world — "what is our competitor's current pricing?" or "what are the latest regulations in this space?" — build in retrieval from a current source.

Common Mistake

Asking the model "What's our competitor's current pricing?" without providing that data. The model will either say it doesn't know (useful) or generate pricing based on outdated training data or a reasonable guess (dangerous). The safe approach: retrieve the competitor's current pricing page using a web scraping tool or API, inject it into the prompt, and ask the model to analyze it. The model's strength is reasoning over data you provide — not knowing data it wasn't trained on. Build your systems to give it what it needs, rather than trusting it to have knowledge it structurally cannot have.

Module F04 · Hands-On Lab

Keyword vs. Semantic Search — Side by Side

This exercise doesn't require coding. You'll use existing tools to directly compare keyword search and semantic search on the same document set. Allow 45–60 minutes.

Step 01
Create a document set
Write 15–20 short descriptions of different meeting topics — 2–3 sentences each. Mix them deliberately: some about Q3 planning, some about product roadmap, some about team structure, some about budget, some about customer feedback. Use varied vocabulary intentionally. Don't always use the word "budget" for financial discussions — sometimes write "cost," "expenditure," or "allocation." This variation is what will expose keyword search's limits. Save the descriptions somewhere easily searchable (a text file, a doc, a spreadsheet).
Step 02
Keyword search
Use Ctrl+F (or any search tool) to search your document set for each of the following queries. Record exactly which documents each query returns — and which relevant documents it misses.
  • "budget"
  • "cost"
  • "revenue"
  • "team"
  • "Q3"
Step 03
Semantic search
Use a semantic search tool — Claude.ai with file upload works well here; Perplexity or any RAG tool you have access to also works — and ask the same conceptual questions against the same document set.
  • "Which meetings were about financial topics?"
  • "What discussions happened about people or organizational structure?"
  • "Which meetings had forward-looking planning discussions?"
Step 04
Compare the results
Document three things: where keyword search and semantic search agree; where they differ; and what semantic search found that keyword search missed (or vice versa). Pay special attention to the financial topic query — did the semantic search surface documents that used "cost," "expenditure," and "allocation" without the word "budget"? Did the keyword search miss them?
Step 05
Design challenge: Maya's recipe recommender pipeline
For Maya's system with 300 recipes, sketch the full data pipeline in plain English — no code required. Think through each of the following questions and write down your answers:
  • How would you embed and store the recipes? What would you include in the text you embed — just the title? Title + ingredients? The full description? What metadata would you store alongside the embedding?
  • How would you handle a query like "something light and refreshing for summer, pescatarian"?
  • What would you return to the user? Just the recipe name? A short preview? Preparation time?
  • What would you do when the top semantic search result is actually a poor match — the similarity score is decent but the recipe doesn't fit the request?
Facilitation Notes
  • The gap between keyword and semantic search is most dramatic on queries about concepts that use varied vocabulary in the document set. Set up your document set to maximize this variation — deliberately avoid using the same word for the same concept across different documents.
  • Step 2 is often surprising for participants. The keyword searches return something — but the gaps become obvious when participants check whether relevant documents were missed.
  • The design challenge in Step 5 is where non-engineers often have their best ideas. Encourage creative thinking about chunking strategy, what metadata to store, and how to handle weak matches. There are no wrong answers — only tradeoffs to discuss.
  • A useful discussion prompt for Step 5: "What would make a semantic search result bad even if the similarity score is high?" (Possible answers: the model embedded noise in the description; the recipe has the right concepts but is wildly impractical; the description was misleading.) This opens up the idea that retrieval quality depends on both embedding quality and the quality of the source text.
  • Close with this reflection: "For Maya's use case, would you use only semantic search? Or would you combine it with keyword filtering?" Push toward the answer that hybrid search — semantic ranking + metadata filters like dietary tags or preparation time — usually outperforms either approach alone.

By the End of This Module, You Should Be Able To...

  • Explain the difference between structured and unstructured data and describe where each type naturally appears in a real AI application — including the pipeline pattern where AI transforms unstructured input into structured output.
  • Describe the three main database types (relational, document, key-value) and explain which is appropriate for which use case — and why using the wrong type creates unnecessary friction.
  • Explain how keyword search works (inverted indexes, TF-IDF), articulate exactly why it falls short for semantic use cases, and identify the specific query patterns that expose its limits.
  • Explain what an embedding is: a vector representation of text meaning, produced by a neural network trained to ensure similar meanings produce similar vectors — the bridge between language and math.
  • Describe how a vector store works: storing embeddings and serving approximate nearest-neighbor queries to find semantically similar content at scale, using ANN algorithms rather than brute-force comparison.
  • Walk through the RAG pipeline end to end: embed documents at ingestion time, embed queries at retrieval time, inject the top-K retrieved chunks into the LLM's context window, and generate a grounded response — and explain why this reduces hallucination.
  • Explain training cutoffs structurally — not as a bug but as a property of how models are built — and describe practical retrieval-based strategies for providing models with information they weren't trained on.
