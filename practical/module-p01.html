Section 01

What we're building

Scout starts as the simplest possible agent: one tool, one loop. That's intentional. The goal of this module isn't to impress you — it's to give you a concrete, runnable foundation that every subsequent module builds on. Simple enough to fully understand, real enough to matter.

By the end of this module, you'll type a question into your terminal, Scout will reason about it, call web_search, read the results, and give you a cited answer. The search is stubbed — it returns realistic fake results — so you don't need an API key to get started. The loop, the tool call protocol, the stop condition, the message accumulation: all of that is real, unmodified Anthropic SDK code. The pattern you build here will survive every upgrade in modules P02 through P07.

Section 02

The concept — The ReAct loop

ReAct is a 2022 paper by Yao et al. that formalized something practitioners had been doing intuitively: combining reasoning and acting inside the same model inference loop. The name is literal — Reason + Act. Instead of asking a model to generate a final answer in one shot, you ask it to produce a thought, then take an action, then observe the result of that action, and repeat — until it has enough evidence to give a grounded answer.

The loop works like this: the model receives the current message history and produces a response. If that response contains a tool call (in Anthropic's API, a tool_use block), the agent runtime executes the tool and appends the result as a tool_result message. The model now sees both its own action and what happened — this is the observation. It then decides: do I have enough to answer, or should I act again? This continues until the model reaches stop_reason: "end_turn", at which point it outputs its final answer.

Why does this work better than a single shot? Because each action is grounded in actual evidence before the next decision is made. A model generating an answer in one pass has to predict what a search would find — and that's where hallucination lives. ReAct replaces prediction with observation. The model doesn't need to imagine what the web says about a topic; it looks, reads the actual results (even if stubbed here), and synthesizes from evidence. The reasoning is still probabilistic, but it's anchored to real retrieved data rather than latent statistical patterns.

In the Anthropic SDK, this pattern maps directly to the messages list. Every turn, the model's response is appended as an assistant message. Every tool result is appended as a user message containing a tool_result block. The growing message list is the agent's working memory — it has no other state. The loop is just: call the API, check stop_reason, append, repeat.

Key Insight

ReAct is not a library. It's a design principle. Any loop where the model can reason, act, and observe before deciding what to do next is ReAct, regardless of what framework wraps it. LangChain implements it. CrewAI implements it. The code you're about to write from scratch implements it. The pattern predates all of them.

Step 02

Define Scout's first tool

Give Claude Code this prompt to build the tool definition:

Claude Code Prompt
In tools.py, create a web_search stub function and a TOOLS list for the Anthropic SDK. The web_search(query: str) function should return a dict with: the query, a list of 3 realistic-looking fake results (each with title, url, snippet, source fields), and a timestamp. The TOOLS list should define web_search with a proper description and input_schema that tells Claude when and how to use it. The description should say: use this to find current information, recent news, or sources to cite. Make the tool description genuinely helpful — the model reads it.

Only touch tools.py.

Claude Code will generate a file close to this:

# tools.py — what Claude Code generates
import time

def web_search(query: str) -> dict:
    return {
        "query": query,
        "results": [
            {
                "title": f"Understanding {query}: A Complete Guide",
                "url": "https://example.com/guide",
                "snippet": f"A comprehensive overview of {query}, covering key concepts, recent developments, and practical applications...",
                "source": "example.com"
            },
            {
                "title": f"{query} — Latest Research and Analysis",
                "url": "https://research.example.com/analysis",
                "snippet": f"Recent analysis shows that {query} continues to evolve, with new findings suggesting...",
                "source": "research.example.com"
            },
            {
                "title": f"How {query} Works: Technical Deep Dive",
                "url": "https://technical.example.com/deep-dive",
                "snippet": f"A technical examination of {query}, including underlying mechanisms and implementation details...",
                "source": "technical.example.com"
            }
        ],
        "timestamp": time.time()
    }

TOOLS = [
    {
        "name": "web_search",
        "description": (
            "Search the web for current information on a topic. Returns a list of "
            "relevant results with titles, URLs, and snippets. Use this when you need "
            "factual information, recent news, or sources to cite in your answer. "
            "Be specific in your query — 'Claude 3.5 Sonnet context window size' "
            "beats 'Claude info'."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "query": {
                    "type": "string",
                    "description": "The search query. Specific and precise gets better results."
                }
            },
            "required": ["query"]
        }
    }
]

Why the stub returns a dict, not a string: When the tool result is passed back to the model, it gets JSON-serialized. Structured data — with titled fields — is easier for the model to parse and reference than a flat string blob. The model can extract url, title, and snippet as separate entities to cite. This is a principle from M02: tool outputs should be designed for the model's consumption, not just for human readability.

The tool description is model-facing control logic: This is the single most underappreciated part of tool use. The description field in the TOOLS list isn't documentation — it's a behavioral specification. The model reads this at inference time to decide whether to use the tool, when to use it, and how to form the query. The hint about specificity ("'Claude 3.5 Sonnet context window size' beats 'Claude info'") directly influences how the model constructs search queries. Bad descriptions produce bad tool use; good descriptions produce focused, high-signal calls.

The input_schema: This is a JSON Schema object that tells the model exactly what arguments the tool accepts. The SDK validates calls against this schema before dispatching. The required: ["query"] field means the model cannot call web_search without providing a query — the API will reject incomplete calls. This is a compile-time guarantee for tool invocations.

Step 03

Build the ReAct loop

Now give Claude Code the core of the agent:

Claude Code Prompt
In agent.py, build Scout's core ReAct loop using the Anthropic SDK. Scout is a research assistant agent. Here's what it needs to do:

1. Accept a question from the user
2. Send it to claude-opus-4-7 with the TOOLS from tools.py and a system prompt that defines Scout as a research assistant who always cites sources
3. If the model returns tool_use, execute the tool (just web_search for now) and append a tool_result back to messages
4. If the model returns end_turn, print the final response
5. Repeat up to 10 turns
6. Print a brief trace line each time a tool is called: "→ web_search(query)"

At the bottom, add a simple if __name__ == "__main__" block that reads a question from input() and calls run_scout(question).

Only touch agent.py.

Claude Code will generate the following:

# agent.py — what Claude Code generates
import anthropic
import json
from tools import web_search, TOOLS

client = anthropic.Anthropic()
MODEL = "claude-opus-4-7"

SYSTEM = """You are Scout, a research assistant. You help users find information and answer questions with cited sources.

When you search, synthesize the results into a clear answer. Always reference your sources by URL. Be concise — a well-cited paragraph beats a wall of text."""

def run_scout(question: str) -> list:
    messages = [{"role": "user", "content": question}]
    print(f"\n🔍 Scout researching: {question}\n")

    for turn in range(10):
        response = client.messages.create(
            model=MODEL,
            max_tokens=4096,
            system=SYSTEM,
            tools=TOOLS,
            messages=messages
        )

        messages.append({"role": "assistant", "content": response.content})

        if response.stop_reason == "end_turn":
            for block in response.content:
                if hasattr(block, "text"):
                    print(f"Scout: {block.text}")
            break

        elif response.stop_reason == "tool_use":
            tool_results = []
            for block in response.content:
                if block.type == "tool_use":
                    print(f"  → {block.name}({json.dumps(block.input)})")
                    if block.name == "web_search":
                        result = web_search(**block.input)
                    else:
                        result = {"error": f"unknown tool: {block.name}"}
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": json.dumps(result)
                    })
            messages.append({"role": "user", "content": tool_results})

    return messages

if __name__ == "__main__":
    question = input("Ask Scout: ")
    run_scout(question)

Section 04

Under the hood

Why messages is a list that grows: The Anthropic API is stateless. There's no session, no server-side memory, no continuity between calls. The model "remembers" nothing unless you tell it. The messages list is literally the agent's entire working memory — every question, every thought, every tool call, every result. When you append the assistant's response and the tool results and pass them back in the next API call, the model sees its own history and can reason about it. This is not a limitation; it's the architecture. It means you have complete, auditable control over what the agent knows at every turn.

What stop_reason: "tool_use" means: When Claude returns tool_use as the stop reason, it's not an error or an interruption — it's the model's way of saying "I have decided that before I can give you a final answer, I need to take an action." The model could have attempted an answer without searching. It chose not to. That's a genuine reasoning decision made at inference time, based on the question and the tool descriptions available. The stop reason is the handshake between the model's agency and your runtime's execution capability.

Why tool_result uses tool_use_id: Claude can call multiple tools in a single response. If you ask a complex question, the model might emit three tool_use blocks simultaneously — searching three things in parallel before synthesizing. Each block has a unique id assigned by the API. When you pass results back, you must use those exact IDs in your tool_result blocks so the model can correlate each result with the action that produced it. This is not bureaucracy — it's how the model maintains coherent reasoning when parallel tool calls are in flight.

The 10-turn limit and why it matters: Without a maximum turn count, a buggy agent loop can run indefinitely — calling tools in circles, never reaching a terminal state, burning API credits until you forcibly kill the process. This is called "agent loop hell" and it's a real failure mode in production systems. The 10-turn limit is the simplest form of a circuit breaker. In production you'd also add cost tracking, a hard timeout, and an escalation path when the limit is hit. The number 10 is somewhat arbitrary for this module; what matters is that there is a limit, and you own it.

Common Mistake

The most common error in first ReAct implementations: passing the tool result as a new plain user message — just a string — without the tool_result type and tool_use_id. The Anthropic API will reject messages structured this way, or worse, silently ignore the correlation and leave the model confused about which result corresponds to which action. Always pass tool results as a user message containing a list of {"type": "tool_result", "tool_use_id": "...", "content": "..."} objects — one per tool call made in the preceding assistant turn.

Checkpoint

Before moving on, verify that Scout is working correctly:

Verify these pass
  • Run python agent.py and ask "What is retrieval-augmented generation?"
  • Scout calls web_search at least once (you see the → web_search(...) trace line)
  • Scout's final answer cites sources by URL
  • The total number of tool-call trace lines shown is ≤ 10
  • The program exits cleanly after printing the answer

If anything fails: first check that ANTHROPIC_API_KEY is set in your environment (echo $ANTHROPIC_API_KEY should print your key, not an empty string). If the API call succeeds but the loop doesn't terminate, check that your tool_result blocks include the tool_use_id from the corresponding tool_use block. If you see a 400 Bad Request, the message structure is malformed — the most common cause is appending results as a flat string instead of the structured tool_result format shown in the code above.
