MODULE P04

Deep Research Mode

Section 01

What we're building

When you ask Scout "what's the capital of France?" it should answer immediately — no need to search, no need for a pipeline. But when you ask "give me a comprehensive analysis of the competitive landscape in enterprise AI tooling," that's a fundamentally different kind of request. It requires exploring multiple angles, reading multiple sources, and synthesizing potentially conflicting information into a coherent picture. A single linear ReAct loop isn't the right tool for that. It processes one thought at a time, and thoroughness is serial.

This module adds a "deep research mode." When Scout detects a complex research request, it spawns two parallel subagents: a Searcher that finds and reads multiple sources, and a Synthesizer that turns those raw findings into a structured report. Scout acts as the orchestrator — it decides when to go deep, delegates the work, and assembles the final output. The ReAct loop stays exactly as it is. You're adding a second mode of execution, not replacing the first.

Section 02

The concept — Orchestrator/subagent and when to go multi-agent

The orchestrator/subagent pattern from Module 04 is straightforward: the orchestrator decomposes a task, delegates pieces to subagents, and synthesizes their results into a final output. Subagents receive scoped tasks, execute them with their own tools and context, and return structured output. One key constraint here: subagents shouldn't spawn further subagents. Recursive delegation adds coordination complexity before it adds value. Keep the hierarchy flat — Scout orchestrates, subagents execute, that's the depth.

Module 04 identifies three legitimate reasons to go multi-agent. All three apply here. Parallelism: the Searcher and Synthesizer run concurrently — total wall time is roughly max(searcher_time, synthesizer_time), not their sum. Specialization: each subagent has a focused system prompt for its specific job; the Searcher is tuned to find and read, the Synthesizer is tuned to structure and synthesize. Context isolation: each subagent gets a fresh context window, so their tool calls and intermediate reasoning don't pollute Scout's main context. One illegitimate reason: "it sounds more sophisticated." Multi-agent adds real complexity — state management, error handling across process boundaries, coordination overhead. Don't add it unless you need one of those three things.

The concurrency mechanism is asyncio.gather. Both subagents are async coroutines. asyncio.gather schedules them concurrently and returns when both finish — yielding a list with both results. Since both subagents make API calls (I/O-bound work), the event loop can interleave them efficiently. For a Searcher that reads 5 URLs and a Synthesizer that writes a 500-word report, this cuts latency roughly in half compared to running them sequentially. The wall time is bounded by whichever subagent takes longer, not by their sum.

Structured output from subagents is non-negotiable for reliable orchestration. If the Synthesizer returns free-form prose, the orchestrator can't reliably extract the key findings, confidence level, or cited sources without another parsing step. JSON with defined keys makes the downstream assembly deterministic and testable. The system prompt instructs each subagent to output only valid JSON with a specific schema. Combined with a try/except json.loads fallback, this gives you structured output 95% of the time and graceful degradation the rest.

Key Insight

The COMPASS pattern from Module 04 — Planner + Researchers + Synthesizer — is the same architecture at different scale. Scout's deep research mode is COMPASS miniaturized: a 2-agent pipeline instead of 3, but the same orchestrator-delegates-delegates principle. Start minimal; scale up if you need it. If Scout's deep research mode proves insufficient, the right upgrade path is to add a dedicated Planner step — not to add more subagents in parallel before you understand the bottleneck.

Common Mistake

Spawning subagents for simple tasks. Multi-agent adds latency (at minimum one extra API call per subagent) and complexity (state management, error handling across agents). Scout should detect intent and only spawn subagents when the request is genuinely complex. A simple rule: if a single ReAct loop can handle it in five turns or fewer, don't go multi-agent. The overhead isn't worth it — and if you route everything through the deep research pipeline, you'll burn API credits on questions that a single search would answer perfectly well.

One note on the architecture: the Searcher and Synthesizer are sequential here (Synthesizer needs the Searcher's output to work from), but asyncio.to_thread still provides value — each API call runs in a thread pool rather than blocking the event loop. If you were to extend this with a third parallel subagent that doesn't depend on the Searcher, asyncio.gather would give you genuine parallelism for free.

Step 02

Add deep research detection to agent.py

Now update the main agent loop to detect complex research requests and route them to the subagent pipeline:

Claude Code Prompt
Update agent.py to detect when a request needs deep research and route it to the subagent pipeline. Add an is_deep_research_request(question: str) function that uses a simple heuristic — returns True if the question contains phrases like "comprehensive", "analysis", "compare", "landscape", "research in depth", "thorough", "overview of", "everything about". Claude Code will add detection logic and a routing branch. The additions look like this:

# Additions to agent.py import asyncio from subagents import run_deep_research DEEP_RESEARCH_TRIGGERS = [ "comprehensive", "in depth", "in-depth", "thorough", "detailed analysis", "compare", "landscape", "overview of", "everything about", "full report on", "research", "analyze" ] def is_deep_research_request(question: str) -> bool: q = question.lower() return any(trigger in q for trigger in DEEP_RESEARCH_TRIGGERS) def format_deep_research_result(result: dict) -> str: synth = result.get("synthesizer", {}) lines = [ f"## {result['topic']}", f"\n{synth.get('summary', '')}", "\n**Key findings:**" ] for finding in synth.get("key_findings", []): lines.append(f" * {finding}") sources = synth.get("sources_cited", []) if sources: lines.append(f"\n**Sources:** {', '.join(sources)}") lines.append(f"\n*Confidence: {synth.get('confidence', 'unknown')}*") return "\n".join(lines) # In run_scout, BEFORE the main ReAct loop: def run_scout(question: str, ctx: dict = None) -> dict: ctx = ctx or {} if is_deep_research_request(question): print(" [mode: deep research — spawning subagents]\n") result = asyncio.run(run_deep_research(question, client, MODEL)) formatted = format_deep_research_result(result) print(f"\nScout (deep research):\n{formatted}") # Persist to notes automatically save_note( title=f"Deep Research: {question[:60]}", content=formatted, tags=["deep-research", "auto-generated"] ) return ctx # ... existing ReAct loop for normal questions ...

The routing logic is intentionally crude — keyword matching, not a classification model. That's by design for now. Section 4 explains when and how to upgrade it.

Section 04

Under the hood

asyncio.to_thread with a sync SDK: The Anthropic Python SDK's client.messages.create is a synchronous blocking call. If you await it directly from an async function, you'll block the event loop — other coroutines can't run while the HTTP request is in flight. asyncio.to_thread solves this by submitting the sync function to a thread pool executor, returning an awaitable that resolves when the thread completes. The event loop stays free to schedule other work. If you use anthropic.AsyncAnthropic instead, you get a natively async client and can await client.messages.create() directly — but asyncio.to_thread is the correct bridge when you're working with the sync client.

Why the Synthesizer has no tools: The Synthesizer's job is synthesis, not search. Giving it tools would create scope creep — it might try to verify facts, run additional searches, or read pages the Searcher already covered. Tight scopes make subagents reliable. When a subagent's job is clearly bounded, its system prompt can be correspondingly focused, and its behavior is more predictable. The Searcher is responsible for information gathering; the Synthesizer is responsible for structured reporting. Those are different cognitive tasks, and separating them produces better output than a single "do everything" agent would.

JSON output and the fallback pattern: The system prompt instructs each subagent to output only valid JSON. This works well — language models have strong formatting compliance when given explicit schema instructions. But it's not perfectly reliable. Network errors, mid-stream truncation, or edge-case reasoning can produce malformed output. Always wrap json.loads in a try/except json.JSONDecodeError and have a fallback that wraps the raw text in the expected schema shape. The fallback here sets raw_findings or summary to the unparsed text and leaves structured fields empty — enough for the orchestrator to assemble something useful rather than crash.

The detection heuristic and when to upgrade it: Keyword matching is crude but fast and costs nothing. For 80% of real queries, it works correctly. The failure modes are false positives (a casual question that happens to contain "analysis") and false negatives (a complex research request phrased without any trigger words). A better approach is to add a lightweight classification step before the main loop: send the question to a cheaper model and ask "is this a deep research request that requires reading multiple sources? Answer yes or no." This costs one small API call but dramatically improves routing accuracy. Start with keyword matching; upgrade to classification if you find the heuristic routing is producing poor results in practice.

Section 06

What Scout can do now

Scout now has two modes of execution: quick answers via the ReAct loop, and deep reports via the orchestrator-subagent pipeline. This routing layer — a simple function that looks at the question and decides which execution path to use — is the architecture that powers most production research agents.
