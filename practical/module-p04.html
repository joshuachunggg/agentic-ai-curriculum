Section 01

What we're building

Scout's web_search has been returning fabricated data since module one. Every result has been plausible-looking fiction: realistic-sounding URLs, generic snippets, fake sources. That was useful for building and testing the loop without needing API keys — but it means every note Scout has saved, every source it has cited, every fact it has reported has been invented. In this module we fix that. We also upgrade Scout's file operations to use proper MCP-based filesystem access. Both changes happen through the Model Context Protocol — Anthropic's open standard for agent-to-tool communication. After this module, Scout does real research on real information.

You'll install two MCP servers, configure them for Scout, and update the tool dispatch to use them. The ReAct loop doesn't change. Only the tools change — which is exactly the payoff of the design decision made in module P02, when tools were defined as swappable implementations behind a stable interface. The loop has always been correct; now the tools are real.

Section 02

The concept — MCP

The Model Context Protocol is Anthropic's open standard for how agents communicate with tools. Before MCP, every agent had its own bespoke integration — custom API wrappers, custom schemas, custom auth flows, custom error handling. Connecting a new tool meant writing new glue code every time. MCP standardizes the contract: a tool server exposes its capabilities via a defined protocol, and any MCP-compatible agent can discover and use those capabilities without writing custom integration code. It's the USB-C of agent tools — one standard, many devices.

Technically, an MCP server is a process that implements the MCP protocol. It exposes a tools/list endpoint (here are the tools I have) and a tools/call endpoint (call this tool with these parameters). The agent discovers what's available, then invokes tools by name with typed parameters. The server handles execution and returns structured results. Communication happens over stdio for local servers — the server is a subprocess, your agent pipes JSON-RPC messages into its stdin and reads results from its stdout. For remote servers the transport is HTTP+SSE, but the protocol is identical.

Why MCP matters for the ecosystem is best understood through the alternative. Without it, a Brave Search integration written for Scout would need to be rewritten from scratch to work with a different agent framework, a different language, or a different model provider. With MCP, a tool built once as an MCP server works with any MCP-compatible consumer — Claude Code, your Python agent, any future framework that implements the protocol. The tool investment compounds instead of stacking up as one-off integrations. This is the interoperability layer described in Module 04, and it's practically useful right now: the Brave Search MCP server you install in this module can also be added to Claude Code's config, so Claude Code itself gains that tool for all your sessions.

The MCP Python SDK — installed as the mcp package — provides a clean client interface for connecting to any MCP server. The pattern is a ClientSession wrapping a stdio_client context manager: open a pipe to the server process, initialize the session with a handshake, then call tools by name with typed parameters. The SDK handles the JSON-RPC wire format, message framing, and connection lifecycle. What you write is session.call_tool("brave_web_search", {"query": q}); what happens underneath is a JSON-RPC 2.0 exchange over stdio — covered in the Under the Hood section if you want the details.

Key Insight

MCP is not just for Anthropic models. It's an open standard — any agent framework can implement it. Wrapping your tools as MCP servers means they're immediately reusable across models, frameworks, and contexts. For tools you build and use repeatedly (web search, database access, calendar, email), MCP is the right abstraction. The upfront cost of the protocol is paid back the first time you reuse the server in a second context without writing new integration code.

MCP in Claude Code

When you add an MCP server to Claude Code's configuration, Claude Code's built-in agent gains that tool for all sessions — automatically, for any task where it's relevant. The same Brave Search MCP server you configure for Scout today can be added to ~/.claude/claude_desktop_config.json so Claude Code can also search the web during coding sessions. One MCP server, many consumers, zero additional integration code.

Step 02

Create mcp_tools.py

This file wraps the Brave Search MCP server in a clean Python interface:

Claude Code Prompt
Create mcp_tools.py to wrap the Brave Search MCP server using the MCP Python SDK:

- Load BRAVE_API_KEY from .env using python-dotenv
- get_brave_tools() — return the brave_web_search tool definition in Anthropic API format
- call_brave_search(query: str, count: int = 5) — use the mcp package (ClientSession + stdio_client + StdioServerParameters) to connect to the Brave Search MCP server and call the brave_web_search tool. The server returns one JSON object per content block (not a wrapper array), so iterate all result.content blocks and parse each one individually to build a list of {title, url, snippet} dicts
- Add python-dotenv and mcp to requirements.txt

Then update tools.py: make web_search use Brave Search when BRAVE_API_KEY is set, falling back to the stub when not. When using the stub fallback, include _stub: True in the returned dict so callers can detect which mode is active. Keep the web_search function signature identical.

Only touch mcp_tools.py and tools.py.

Claude Code will generate a file close to this:

# mcp_tools.py
import os
import json
import asyncio

from mcp import ClientSession
from mcp.client.stdio import stdio_client, StdioServerParameters

try:
    from dotenv import load_dotenv
    load_dotenv()
except ImportError:
    pass

BRAVE_API_KEY = os.getenv("BRAVE_API_KEY", "")

def get_brave_tools() -> list:
    """Return Brave Search tool definitions in Anthropic tool format."""
    return [
        {
            "name": "brave_web_search",
            "description": (
                "Search the real web using Brave Search. Returns current results "
                "with titles, URLs, snippets, and publication dates. Use for any "
                "topic requiring up-to-date information. Specific queries return "
                "better results than vague ones."
            ),
            "input_schema": {
                "type": "object",
                "properties": {
                    "query": {
                        "type": "string",
                        "description": "Search query. Be specific."
                    },
                    "count": {
                        "type": "integer",
                        "description": "Number of results to return (1-10, default 5)",
                        "default": 5
                    }
                },
                "required": ["query"]
            }
        }
    ]

async def call_brave_search(query: str, count: int = 5) -> dict:
    """Call the Brave Search MCP server via the MCP Python SDK."""
    if not BRAVE_API_KEY:
        return {
            "error": "no_api_key",
            "message": "Set BRAVE_API_KEY in .env — get a free key at brave.com/search/api/"
        }

    server = StdioServerParameters(
        command="npx",
        args=["-y", "@brave/brave-search-mcp-server"],
        env={**os.environ, "BRAVE_API_KEY": BRAVE_API_KEY}
    )

    try:
        async with stdio_client(server) as (read, write):
            async with ClientSession(read, write) as session:
                await session.initialize()
                result = await session.call_tool(
                    "brave_web_search",
                    {"query": query, "count": count}
                )
                # Brave returns one JSON object per content block, not a wrapper array
                results = []
                for block in result.content:
                    raw = getattr(block, "text", "") or ""
                    if not raw:
                        continue
                    try:
                        item = json.loads(raw)
                        results.append({
                            "title": item.get("title", ""),
                            "url": item.get("url", ""),
                            "snippet": item.get("description", item.get("snippet", "")),
                        })
                    except Exception:
                        continue
                return {"query": query, "results": results}

    except Exception as e:
        return {"error": "mcp_error", "message": str(e)}

stdio_client launches the server subprocess and returns a read/write pair. ClientSession handles the JSON-RPC handshake on initialize() and serializes call_tool() into the correct wire format. Both context managers clean up the process on exit — no manual process management needed.

Note the response shape: @brave/brave-search-mcp-server returns one JSON object per content block — each block is a single result with title, url, and description. Iterating all blocks and parsing each individually is the correct pattern; grabbing only content[0] silently discards all but the first result.

Section 04

Under the hood

The stub-to-real upgrade pattern: Nothing in agent.py, the ReAct loop, or the subagent architecture changed in this module. Only the implementation of web_search changed. This is the payoff of the tool design from Module P02 — tools as swappable implementations behind a stable interface. The agent dispatches to web_search(query=...); it has no knowledge of whether that call hits Brave or returns fake data. This interface boundary is where the upgrade happened. When you need to swap Brave for a different provider, the change is local to mcp_tools.py and the web_search function — nowhere else.

What the MCP SDK does for you — JSON-RPC 2.0 over stdio: Every MCP interaction follows the same two-phase pattern. First: an initialize handshake where the client announces the protocol version and its capabilities; the server responds with its own. Second: a sequence of tools/call requests, each with a tool name and typed arguments, each returning a structured result. ClientSession.initialize() handles the first phase; session.call_tool() handles the second. Under the hood both are JSON-RPC 2.0 messages serialized to stdin and read from stdout. You don't write any of that — the SDK does. The server runs as a subprocess managed by stdio_client: no port to open, no daemon, no network configuration. It starts when you enter the context manager and the process exits when you leave it.

Async in a sync codebase: asyncio.run() in a synchronous function works correctly when there is no active event loop in the current thread — which is the case when web_search is called from Scout's synchronous ReAct loop. The problem arises if web_search is ever called from within an already-running async context. In that case asyncio.run() raises RuntimeError: This event loop is already running. The fix is to call web_search via await asyncio.to_thread(web_search, query) from async code. You'll encounter this concretely in P05 when the Searcher subagent calls web_search from inside an async function — asyncio.to_thread is the bridge. For a fully clean codebase, the right long-term move is to make web_search itself async and update all callers. For now, the warning message and fallback to stub is an acceptable bridge.

When to go beyond the stub: The stub earned its keep across four modules of development. It let you build, test, and iterate on the agent architecture without consuming API credits or depending on external service availability. Keeping it as a fallback means Scout still works when BRAVE_API_KEY isn't set — useful for unit tests, offline demos, and environments where you want deterministic (if fake) results. The _stub: True flag in the response makes it easy to assert in tests that you're in the mode you expect. Don't delete the stub; just make it secondary.
