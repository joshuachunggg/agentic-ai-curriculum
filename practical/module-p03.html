MODULE P03

Memory That Persists

Every long research session runs into the same wall: the message list grows until the model starts losing the thread. This module adds rolling context compression and session persistence — Scout can now work across hours of research without degrading, and picks up exactly where it left off after a restart.

Section 01

What We're Building

Scout's current loop has a hidden time bomb: every tool call and every response appends to the messages list. After 15–20 research queries, that list easily exceeds 50,000 tokens. You pay for all of it. The model technically "sees" everything, but quality drops — older tool results get diluted by newer ones, the original question gets buried, and Scout starts repeating work it already did earlier in the conversation. This is the "lost in the middle" problem from Module 03, and it's not hypothetical. It reliably shows up in any agent doing serious multi-turn research.

This module adds two things that together solve it. First: a ContextManager class that implements rolling summarization — when the message list grows past a threshold, it compresses the oldest messages into a compact summary, keeping only the most recent turns verbatim. Second: session persistence — the manager's state is serialized to a JSON file after each run, and loaded back at startup. Scout can now be interrupted mid-research, restarted, and pick up the conversation with full context intact. These two capabilities together are the difference between a demo agent and one you'd actually run against a real project.

Section 02

The Concept — Context Engineering

The context window is the model's only working memory at inference time. Every call to the API is stateless — the model receives a window of tokens, produces a response, and forgets everything. The "memory" an agent has is entirely in that window: the system prompt, the tool definitions, the conversation history, and the tool results. For Opus 4 the window is 200k tokens — which sounds vast until you start counting. A system prompt with detailed tool descriptions might cost 2,000 tokens. Each web search result is 300–500 tokens. Each read_url result is up to 1,000 tokens after stripping HTML. After 15 research turns you can easily have 30,000+ tokens of history, and you're nowhere near done. The context window is the primary resource to manage in a production agent.

The deeper problem is dilution. As context grows, older information loses salience — not because the model forgets it, but because the signal-to-noise ratio drops. A model processing a 100-message conversation buries the original question under a sea of intermediate tool results, failed attempts, and repeated searches. Attention drifts toward the most recent messages. The model starts responding to what it saw 5 turns ago rather than the goal it was given 50 turns ago. This is a known limitation of how transformer attention works at scale, and it shows up as subtle quality degradation before it ever shows up as an obvious failure. You notice it as Scout saying "let me search for that" when it already found the answer three turns back.

The solution is a two-track approach: separate the conversation from the state. The conversation history serves the model's reasoning — it needs to see recent messages to understand the flow of what's happening. The state dict serves the orchestration logic — it holds the key facts extracted from the session: current research topic, sources found, key findings, decisions made. The conversation is ephemeral and compressible; the state is durable and structured. Keeping these two things mixed together — storing all knowledge only in the raw conversation history — is the most common context engineering mistake in early agent builds. It means you can't compress the conversation without potentially losing important facts.

Rolling summarization closes the loop: every N turns, take the oldest M messages, send them to the model with a compression prompt, and replace them with a single compact summary block. Keep the last K messages verbatim so the model has fresh context for its current reasoning. The compressed summary lives in the conversation as a [CONTEXT SUMMARY] block — the model can see it, reference it, and continue. The key insight from Module 03 applies here directly: compression isn't lossy if you're compressing the right things. Intermediate tool results, failed search attempts, repeated reasoning steps — these are compressible. Key findings, source URLs, decisions made — these go into the state dict and survive every compression cycle unchanged.

Insight

The state dict is your agent's working memory — structured facts extracted from tool results. The message list is the reasoning trace — how the model got there. These serve different purposes and have different lifespans. Mixing them together (relying entirely on conversation history to hold important facts) is the most common context engineering mistake in early agent builds. When you compress, you lose the reasoning trace but preserve the state. That's the right tradeoff.

Common Mistake

Don't compress on every turn. Compressing after every message wastes tokens summarizing work the model just did and destroys the recent context it needs to continue reasoning coherently. Set a meaningful threshold — 16 messages works well in practice — and keep the last 6–8 messages verbatim after each compression. The model needs those recent turns to understand what it was just doing and where to go next.

Step 01

Create memory.py

This is a new file — memory.py in your scout-agent/ directory. It handles context compression and session persistence independently of the agent loop. Run this prompt in Claude Code from inside your scout-agent/ directory:

Claude Code prompt
Create memory.py with two capabilities:

1. A ContextManager class that manages the agent's message history — compressing old messages into a summary when the conversation grows long while keeping recent messages intact. It needs add_message(role, content), should_compress(), compress(client, model), and to_dict()/from_dict() methods for serialization. Default COMPRESS_THRESHOLD to 16 and KEEP_RECENT to 6.

2. save_session(session_id, manager) and load_session(session_id) module-level functions that persist and restore a ContextManager from a JSON file in a sessions/ directory.

Use these exact print formats for status lines:
- On save: [session saved: {path}]
- On load: [session loaded: {path} — N messages]
- On compress: [context compressed: N→M messages]

No external dependencies beyond json and pathlib.

Only create memory.py — don't modify other files.

The complete memory.py Claude Code generates should look like this:

# memory.py
import json
from pathlib import Path
from datetime import datetime
import anthropic

SESSIONS_DIR = Path("sessions")
COMPRESS_THRESHOLD = 16
KEEP_RECENT = 6

COMPRESSION_PROMPT = """Summarize the following conversation context into a compact structured summary.
Preserve: key facts found, decisions made, topics researched, sources referenced.
Discard: intermediate reasoning, repeated searches, failed attempts.
Output a concise paragraph followed by a "Key facts:" bullet list."""

class ContextManager:
    def __init__(self):
        self.messages = []
        self.state = {}

    def add_message(self, role: str, content):
        self.messages.append({"role": role, "content": content})

    def should_compress(self) -> bool:
        return len(self.messages) > COMPRESS_THRESHOLD

    def compress(self, client: anthropic.Anthropic, model: str):
        n_before = len(self.messages)
        to_compress = self.messages[:-KEEP_RECENT]
        keep = self.messages[-KEEP_RECENT:]

        if not to_compress:
            return

        compress_messages = [
            {"role": "user", "content": f"{COMPRESSION_PROMPT}\n\n---\n{json.dumps(to_compress, indent=2)}"}
        ]

        response = client.messages.create(
            model=model,
            max_tokens=1024,
            messages=compress_messages
        )

        summary = response.content[0].text
        summary_message = {
            "role": "user",
            "content": f"[CONTEXT SUMMARY — {n_before - KEEP_RECENT} messages compressed]\n\n{summary}"
        }

        self.messages = [summary_message] + keep
        print(f"  [context compressed: {n_before}→{len(self.messages)} messages]")

    def get_state(self) -> dict:
        return self.state

    def set_state(self, key: str, value):
        self.state[key] = value

    def to_messages(self) -> list:
        return self.messages

    def to_dict(self) -> dict:
        return {"messages": self.messages, "state": self.state}

    @classmethod
    def from_dict(cls, data: dict) -> "ContextManager":
        manager = cls()
        manager.messages = data.get("messages", [])
        manager.state = data.get("state", {})
        return manager

def save_session(session_id: str, manager: ContextManager):
    SESSIONS_DIR.mkdir(exist_ok=True)
    path = SESSIONS_DIR / f"{session_id}.json"
    data = {
        **manager.to_dict(),
        "session_id": session_id,
        "saved_at": datetime.now().isoformat()
    }
    path.write_text(json.dumps(data, indent=2))
    print(f"  [session saved: {path}]")

def load_session(session_id: str) -> ContextManager | None:
    path = SESSIONS_DIR / f"{session_id}.json"
    if not path.exists():
        return None
    data = json.loads(path.read_text())
    print(f"  [session loaded: {path} — {len(data.get('messages', []))} messages]")
    return ContextManager.from_dict(data)

            model=MODEL,
            max_tokens=4096,
            system=SYSTEM,
            tools=TOOLS,
            messages=ctx.to_messages()   # <-- use ctx, not raw list
        )

        if ctx.should_compress():
            ctx.compress(client, MODEL)

        if response.stop_reason == "end_turn":
            for block in response.content:
                if hasattr(block, "text"):
                    print(f"\nScout: {block.text}")
            break

        elif response.stop_reason == "tool_use":
            tool_results = []
            for block in response.content:
                if block.type == "tool_use":
                    print(f"  → {block.name}({json.dumps(block.input)})")
                    result = tool_dispatch.get(
                        block.name,
                        lambda **kw: {"error": f"unknown tool: {block.name}"}
                    )(**block.input)
                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": json.dumps(result)
                    })
            ctx.add_message("user", tool_results)

    save_session(session_id, ctx)
    return ctx

Section 04

Under the Hood

Why ContextManager lives in its own file. The single-responsibility principle matters at the file level, not just the function level. agent.py is about what Scout does — the tools it calls, the loop it runs, the questions it answers. memory.py is about what Scout remembers — how long it remembers it, how it compresses old context, where it persists state. Keeping these separate means you can swap the compression strategy entirely — say, replacing the summarization approach with a vector-based retrieval approach — without touching a single line of the agent loop. Conversely, you can refactor the agent loop without worrying about breaking the memory layer. This is the kind of modularity that makes the later modules in this course straightforward to add, because each concern stays in its lane.

How compression actually works. There's no magic here. The compress() method takes the oldest messages — everything that came before the last 6 verbatim turns — serializes them to JSON, and sends them to Claude with a compression prompt. The model reads the raw message history and produces a compact summary: a paragraph describing the key trajectory, followed by a bullet list of key facts. That summary replaces the original messages as a single entry in the conversation. The cost is one extra API call per compression cycle. The savings across a long session — potentially thousands of tokens trimmed to a few hundred — far exceed that cost. And crucially, the quality of the summary is good: Claude is reading its own prior outputs, so the compression rarely misses important information.

The [CONTEXT SUMMARY] marker is load-bearing. When the model sees a message starting with [CONTEXT SUMMARY — N messages compressed], it understands it's reading a compressed digest of prior context, not a real user message that requires a response. Without this marker, the model might try to "respond" to the summary as if it were a new question — asking clarifying questions about it, or treating the key facts list as a new research request. The marker is essentially a content-type annotation: it tells the model the semantic role of this block in the conversation. Never strip it out for "cleanliness." It's doing real work.

Session files as transparent state. The sessions/ directory is Scout's long-term memory in a form you can inspect, copy, version-control, and debug without any special tools. Run cat sessions/my-research-session.json and you'll see exactly what Scout knows: every message, every compressed summary, the full state dict. This transparency is a deliberate design choice, not an accident of simplicity. Agents that store their state opaquely — in a database, in a vector store, in some framework's hidden cache — are agents you can't easily debug when they produce wrong outputs. When you can read the state directly, you can trace exactly why Scout gave a particular answer, exactly what it remembered from three sessions ago, and exactly where it went wrong if something breaks. In production you'll add more sophisticated storage, but the principle — keep agent state inspectable — should survive the upgrade.

Section 06

What Scout Can Do Now

Scout now handles long research sessions without degrading. It compresses its own context window periodically, extracts what matters into a compact summary, and persists that summary — along with its full state — across terminal restarts. This is the inflection point between a demo that works for one conversation and something you'd actually use across a multi-day research project. The notes library from P02 and the session persistence from P03 together give Scout two complementary forms of memory: the notes library is topic-indexed knowledge that can be searched, and the session state is task-indexed context that picks up exactly where you left off. Everything from here builds on this memory foundation — including the parallel subagents in P04, which will each benefit from being able to share state through the same persistence layer.
