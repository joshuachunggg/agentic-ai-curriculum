Section 01

What we've built

Over six modules, you built a complete AI agent from scratch. A ReAct loop backed by a real search engine. A four-tool research toolkit with web search, URL reading, note saving, and note retrieval. Rolling context compression with session persistence across restarts. A parallel subagent pipeline — Searcher and Synthesizer running concurrently — for deep research requests. Real MCP integrations that connect Scout to external services via an open protocol. And a guardrail layer with input filtering, output validation, human-in-the-loop confirmation, and a 10-case eval suite giving you a documented quality baseline. Scout is not a demo. It's a working system built on the same architectural principles that underpin production agents.

This last module is different: it's not about adding a new architectural layer. It's about making Scout your own. You'll consolidate all configuration into a single file you can edit without touching agent logic, add a clean CLI entry point that replaces the if __name__ == "__main__" block in agent.py, and understand your options for taking Scout further — a web frontend, a scheduled research job, or the right moment to reach for a framework. The architecture stays the same. The surface becomes yours.

Section 02

The concept — Customization and framework tradeoffs

System prompt as identity: Scout's current system prompt defines a general research assistant. That's one use case. The same architecture — ReAct loop, tools, memory, subagents, guardrails — works for a competitive intelligence analyst, a personal knowledge manager, a domain-specific research tool, a code reviewer, or a writing assistant. The system prompt is the cheapest thing to change and has the largest effect on what the agent feels like to use. Everything in the Python files gives Scout its capabilities; the system prompt gives it its character. Change the persona, and you change the agent. The code stays the same.

Tool selection as scope: not every use case needs web search. A code review agent needs access to a repository, not Brave Search. A scheduling assistant needs calendar access. A personal knowledge base assistant might need to read PDFs you provide, not live web results. The tool_dispatch dict is the right place to define what your agent can and can't do — what tools it's allowed to reach for and what tools simply don't exist in its world. Every tool you add expands Scout's capabilities and increases the surface area of possible actions. Every tool you don't add constrains it in ways you can reason about completely. Scope is a design decision, not a default.

When to switch to a framework (from Module 06 of the original curriculum): Scout is framework-free by design — the entire architecture is visible in five Python files totaling roughly 400 lines. But at some scale of complexity, a framework pays for itself. LangGraph adds explicit state machines — graphs of typed nodes — which is valuable for workflows with complex branching logic where you need to visualize or validate the state machine. CrewAI adds team-based orchestration with defined roles and coordination protocols. AutoGen adds agents that can write and execute code in a sandbox. The right time to reach for any of these is when you hit a genuine limitation of Scout's architecture, not when the framework sounds appealing. Scout's core loop — message list, tool dispatch, result appending — is directly replicable in any framework. Learn the loop first.

Deployment options: Scout runs as a CLI tool. Three paths forward, in order of complexity: (a) cron job — schedule research runs on a timer, results accumulated in notes/, session persisted between runs, no interactive input required; (b) web frontend — a minimal FastAPI server with a simple HTML chat UI that wraps run_scout, making Scout accessible from a browser; (c) API server — expose Scout as a REST endpoint so other tools, scripts, or services can call it programmatically. All three build on the same agent.py with minimal additions. The core agent doesn't change; only the interface to it changes.

Key Insight

The frameworks debate misses the point. Any agent framework is ultimately a wrapper around a loop that calls a model, runs tools, and appends results to a message list. Scout does exactly that in roughly 80 lines of Python you understand completely — every decision point is visible, every tradeoff is explicit. Learn the loop first. Reach for the framework when the scaffold is genuinely limiting you — not before. That's when you'll understand what the framework is doing for you and what it's hiding from you.

Architecture Continuity

Scout's architecture maps directly to the examples in the original curriculum. Aria (Module 02) runs the same ReAct loop with a different tool set and system prompt. COMPASS (Module 04) runs the same orchestrator-subagent pattern with more specialized subagents. The difference between all of these is specialization — tools and system prompts configured for a specific use case. The loop is constant. That's the insight that transfers to any framework, any model, any use case you build next.

Step 02

Create main.py — clean CLI entry point

Replace the if __name__ == "__main__" block in agent.py with a proper CLI module:

Claude Code Prompt
Create main.py — a clean CLI entry point for Scout. It should:
1. Parse command-line arguments: optional --session flag (default "default"), --deep flag to force deep research mode, and an optional QUESTION positional argument
2. If QUESTION is provided, run non-interactively (single query, then exit)
3. If no QUESTION, enter an interactive REPL: prompt is "{AGENT_NAME} ({session}) > ", loop until user types "exit", "quit", or presses Ctrl+C
4. On startup, print a brief banner: agent name, current session, note count, active tools
5. Handle KeyboardInterrupt gracefully with a friendly exit message

Remove the if __name__ == "__main__" block from agent.py — main.py replaces it entirely.

Only create main.py.

The complete main.py:

# main.py import argparse import sys from config import AGENT_NAME, ACTIVE_TOOLS, SESSION_DIR, NOTES_DIR def print_banner(session: str): notes_count = len(list(NOTES_DIR.glob("*.json"))) if NOTES_DIR.exists() else 0 print(f"\n{'─' * 52}") print(f" {AGENT_NAME} | session: {session} | {notes_count} note(s)") print(f" tools: {', '.join(ACTIVE_TOOLS)}") print(f"{'─' * 52}\n") def main(): parser = argparse.ArgumentParser( description=f"Run {AGENT_NAME} — your personal research assistant" ) parser.add_argument( "question", nargs="?", help="Question to answer (non-interactive mode)" ) parser.add_argument( "--session", "-s", default="default", help="Session name (default: 'default')" ) parser.add_argument( "--deep", "-d", action="store_true", help="Force deep research mode regardless of trigger keywords" ) args = parser.parse_args() from agent import run_scout # Non-interactive: single question, then exit if args.question: run_scout(args.question, session_id=args.session) return # Interactive REPL print_banner(args.session) try: while True: try: question = input(f"{AGENT_NAME} ({args.session}) > ").strip() except EOFError: break if not question: continue if question.lower() in ("exit", "quit", "q", ":q"): print("Goodbye.") break run_scout(question, session_id=args.session) print() except KeyboardInterrupt: print(f"\nGoodbye.") if __name__ == "__main__": main()

Usage examples:

# Interactive mode (start the REPL) python main.py # Interactive with a named session python main.py --session ai-research # One-shot mode (non-interactive, exits after answering) python main.py "What is the difference between RAG and fine-tuning?" # One-shot with a named session (context persists from prior runs) python main.py --session startup-research "What are the top YC companies from W25?" # Force deep research mode on a specific query python main.py --deep "Landscape of vector database providers in 2026"

Step 03

Customize for your use case

This step is yours — no Claude Code prompt required. Open config.py and make these three decisions:

1. Change AGENT_NAME. Give your agent a name that fits its purpose. "Sentinel" for competitive intelligence. "Archivist" for a personal knowledge base. "Dev" for code research. The name appears in the banner, the REPL prompt, and the system prompt.

2. Edit AGENT_PERSONA. Uncomment one of the example personas or write your own. The persona is the largest lever you have over how the agent behaves. Keep it specific: vague instructions produce vague behavior. Include the research workflow steps you actually want — the default is a good starting point, but a persona written for your exact use case will feel qualitatively different.

3. Adjust ACTIVE_TOOLS. Remove tools that don't fit your use case. A knowledge base assistant that processes documents you provide doesn't need web_search. A news digest tool might skip save_note entirely — ephemeral daily output, no persistence needed. Every tool you remove narrows the scope in a way you can reason about completely.

Section 04

Under the hood — Framework tradeoffs

What you understand now that you didn't before: you've built a ReAct loop, designed a tool interface, managed context with rolling compression, orchestrated parallel subagents, integrated with an external service via MCP, and added guardrails with behavioral evals — all from scratch, in code you wrote and can read. When you open LangGraph's documentation tomorrow, you'll understand what it's abstracting: the message list management, the tool dispatch, the state accumulation between turns. When you read CrewAI's role definitions, you'll recognize them as system prompts with structured handoff protocols. The conceptual model transfers. You're not starting from zero with each framework — you're recognizing the same loop under a different API.

LangGraph's tradeoff: LangGraph adds explicit state machines — directed graphs of nodes with typed state that flows between them. This is genuinely valuable for workflows with complex branching logic where you need to visualize, validate, or resume at an arbitrary point in a multi-step process. The cost is a new abstraction layer: graph definitions, state types, node functions, edge conditions. That's real cognitive overhead. LangGraph is the right tool when your workflow is complex enough that the state machine diagram is a useful artifact in its own right — when understanding the flow requires seeing the graph. For most agentic loops, Scout's architecture is faster to build, easier to debug, and equally powerful.

The managed agent option: Anthropic's SDK continues to evolve toward higher-level agent abstractions — tool calling, streaming, and state management that handles more of what Scout's main loop does manually. As these capabilities mature, the boilerplate in agent.py shrinks. The architectural understanding you've built here is the prerequisite for using those abstractions well: you'll know what the SDK is doing under the hood, which parts are configurable, and where to add custom logic when the default behavior doesn't fit. Understanding the loop is not wasted work when you move to managed abstractions — it's what lets you use them with precision rather than luck.

The eval loop as the real scaling strategy: every time Scout fails in real use on a query type you care about — produces an incoherent response, fails to use the right tool, misses an obvious citation opportunity — that failure is a test case. Add it to evals/run_evals.py. Fix the root cause (system prompt, tool logic, guardrail). Re-run evals. That's the loop that makes Scout better over time. The architecture doesn't change; the quality does, measurably and verifiably. This is the only sustainable approach to maintaining agent quality as you swap models, update tools, or refine the persona — regression testing is not optional, it's the scaffold that lets everything else evolve.
