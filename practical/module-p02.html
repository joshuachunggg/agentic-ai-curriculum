Section 01

What We're Building

Right now Scout can only call web_search and give you an answer. It can't read the actual contents of a webpage — it only has snippets. It forgets everything between sessions. And when you ask it to research something, it has no way to store what it learned so it can refer back to it the next time the same topic comes up. In practice, this means every conversation starts from zero, no matter how much work Scout did the last time.

This module gives Scout the tool set of a real research assistant: search the web, read the full content of a URL, save findings as structured notes, and search those notes for previously gathered information. We're also doing something important architecturally — designing four tools that follow the principles in Module 02. Each tool does exactly one thing. Each returns structured data, not freeform text. Each fails honestly with an actionable error rather than silently returning nothing. The result isn't just more tools — it's a coherent research loop that Scout can follow across every session.

Section 02

The Concept — Tool Design

The first principle from Module 02 is one tool, one side-effect domain. read_url and save_note are categorically different operations — one reads from the world, the other writes to your notes library. They belong in separate tools, not bundled into a single "research" function. This separation matters because it lets you apply different policies to each. You might want human-in-the-loop approval on any write operation (save_note) while letting reads happen freely. If those operations are mixed into one tool, you can't make that distinction without a lot of messy inspection logic. Clean separation keeps your control surface clean.

Tool names and descriptions aren't documentation — they're model-facing control logic. The model reads them at inference time to decide which tool to call and when. "get_content" is strictly worse than "read_url" as a function name, because "read_url" signals "fetch from the web" while "get_content" says nothing about domain. The description has to answer four questions: what does this tool do, what does it return, when should I use it, and crucially — when should I not use it. A description that says "reads a webpage" leaves the model to guess. A description that says "fetch the full text of a URL — use after web_search to get more detail from a specific result, not as a first step" tells the model exactly where this tool fits in the workflow.

Every tool call can fail. Network timeout. File not found. Invalid URL. Rate limit. The tool must return a structured error the model can act on — not an exception that crashes the loop, not None that silently looks like success, not a generic "something went wrong" string that gives no direction. A tool that returns {"error": "timeout", "url": "...", "message": "Request timed out after 10s", "suggestion": "Try a different source or retry"} gives the model something to work with. It can try a different URL. It can note the failure and continue. It can ask the user. The model can only act on information it can read — and a structured error is readable information.

The last design question is granularity: how many tools? Not too few — a single "do_research" tool that bundles search, reading, and saving is impossible to control and gives the model no ability to adapt its approach. Not too many — a model facing a 40-tool list spends reasoning cycles just navigating the options and makes more mistakes. Scout's four tools map to the complete research lifecycle: find information (web_search), read it in depth (read_url), persist it (save_note), and retrieve what you already know (search_notes). That's the cycle. Four tools, one cycle.

Insight

Tool descriptions sit in the context window on every single call. Write them like you're briefing a capable but context-limited assistant on exactly when to reach for each tool. "Use this when you need to verify something from the search results" is more useful than "reads a webpage." The extra specificity costs a few tokens and saves many turns of incorrect tool usage.

Common Mistake

The silent failure trap. A tool that returns None when a URL 404s — or raises an unhandled exception — will cause the model to silently proceed as if the page loaded successfully. Return a structured error dict with a concrete action the model can take: retry, try a different URL, skip and note the failure. Silence is the worst possible error signal for an agent that needs to self-correct.

# Changes to agent.py from tools import web_search, read_url, save_note, search_notes, TOOLS # Updated system prompt SYSTEM = """You are Scout, a research assistant with four tools: web_search, read_url, save_note, and search_notes. One well-read source beats three skimmed snippets.""" # Updated tool dispatch in run_scout tool_dispatch = { "web_search": web_search, "read_url": read_url, "save_note": save_note, "search_notes": search_notes, } # In the tool_use loop: if block.name in tool_dispatch: result = tool_dispatch[block.name](**block.input) else: result = {"error": f"unknown tool: {block.name}"}

The dispatch dict pattern is the right way to route tool calls. It's O(1), easily extended, and handles the "unknown tool" case cleanly. A chain of if/elif statements would work but breaks down as your tool list grows.

Section 04

Under the Hood

Why search_notes runs first. The system prompt instructs Scout to always check its notes before doing a web search. Right now, with the stub web search, those notes will almost always miss — the stub returns fake results regardless. But when you replace web_search with real Brave Search in P05, this ordering becomes a meaningful optimization: returning to a topic you already researched skips the API call entirely and uses your local knowledge base instead. You're building the habit now so the behavior is in place when it matters. This is the foundation of agent memory — not a database, not embeddings, just structured files and a well-ordered workflow.

The dispatch dict pattern. Mapping tool names to callable functions is the right architecture for tool routing. Not a chain of if/elif — that's linear in the number of tools, brittle when you rename something, and produces dead code when a tool is removed. The dispatch dict is O(1) lookup, scales cleanly as the tool list grows, and makes the "unknown tool" case trivially explicit: if the name isn't in the dict, return a structured error. This same pattern applies at any scale — you'll see it in production agent frameworks too, usually with some additional validation layer on top of the raw function call.

Why read_url extracts text and not raw HTML. The model pays per token. Sending raw HTML — with all its tags, inline scripts, navigation markup, and boilerplate — is expensive and noisy. A typical webpage might be 30,000 tokens of raw HTML but only 3,000 tokens of actual content. Stripping to visible text is context engineering: delivering the same information at a fraction of the token cost. The BeautifulSoup decompose calls that remove <script>, <style>, <nav>, and <footer> tags aren't cosmetic — they're meaningful cost and quality improvements. The 3,000-character cap is a deliberate tradeoff: enough to capture the substance of most articles, small enough to keep each tool result manageable within the context window.

The unknown tool case always needs handling. Language models can hallucinate tool names — especially as the tool list grows or the system prompt is ambiguous. If your dispatch logic doesn't handle an unknown tool name, you'll get a Python KeyError that crashes the agent loop entirely. A structured error return — {"error": "unknown tool: make_coffee"} — lets the model self-correct. In practice, Claude rarely hallucinates tool names when descriptions are clear, but the defensive handling is cheap and the benefit if it does happen is large: the loop continues, the model sees the error, and it typically picks the right tool on the next turn.

Insight

Scout's search_notes → web_search → read_url → save_note workflow is a genuine research loop. Each tool call serves a different part of the information lifecycle: find what you know, find new sources, read them in depth, store what matters. Most useful real-world agents follow this same pattern — the domain changes, the tools change, but the underlying structure of "check memory, find new, read deeply, persist" is remarkably consistent across domains.

Section 06

What Scout Can Do Now

Scout is now a research loop. It knows to check what it already knows before reaching for the web. It reads full pages, not just snippets. It saves findings for next time so that returning to a topic costs less than researching it fresh. The four tools are still partially stubbed — web_search returns fake results until P05 — but the architecture is fully real. The tool design, the dispatch pattern, the structured error handling, the note format: all of this carries forward unchanged into the production version.
