Section 01

What we're building

Scout's web_search has been returning fabricated data since module one. Every result has been plausible-looking fiction: realistic-sounding URLs, generic snippets, fake sources. That was useful for building and testing the loop without needing API keys — but it means every note Scout has saved, every source it has cited, every fact it has reported has been invented. In this module we fix that. We also upgrade Scout's file operations to use proper MCP-based filesystem access. Both changes happen through the Model Context Protocol — Anthropic's open standard for agent-to-tool communication. After this module, Scout does real research on real information.

You'll install two MCP servers, configure them for Scout, and update the tool dispatch to use them. The ReAct loop doesn't change. The subagent architecture from P04 doesn't change. Only the tools change — which is exactly the payoff of the design decision made in module P02, when tools were defined as swappable implementations behind a stable interface. The loop has always been correct; now the tools are real.

Section 02

The concept — MCP

The Model Context Protocol is Anthropic's open standard for how agents communicate with tools. Before MCP, every agent had its own bespoke integration — custom API wrappers, custom schemas, custom auth flows, custom error handling. Connecting a new tool meant writing new glue code every time. MCP standardizes the contract: a tool server exposes its capabilities via a defined protocol, and any MCP-compatible agent can discover and use those capabilities without writing custom integration code. It's the USB-C of agent tools — one standard, many devices.

Technically, an MCP server is a process that implements the MCP protocol. It exposes a tools/list endpoint (here are the tools I have) and a tools/call endpoint (call this tool with these parameters). The agent discovers what's available, then invokes tools by name with typed parameters. The server handles execution and returns structured results. Communication happens over stdio for local servers — the server is a subprocess, your agent pipes JSON-RPC messages into its stdin and reads results from its stdout. For remote servers the transport is HTTP+SSE, but the protocol is identical.

Why MCP matters for the ecosystem is best understood through the alternative. Without it, a Brave Search integration written for Scout would need to be rewritten from scratch to work with a different agent framework, a different language, or a different model provider. With MCP, a tool built once as an MCP server works with any MCP-compatible consumer — Claude Code, your Python agent, any future framework that implements the protocol. The tool investment compounds instead of stacking up as one-off integrations. This is the interoperability layer described in Module 04, and it's practically useful right now: the Brave Search MCP server you install in this module can also be added to Claude Code's config, so Claude Code itself gains that tool for all your sessions.

Since SDK version 0.40+, the Anthropic Python SDK has built-in support for connecting to MCP servers via MCPServerStdio and related classes. For this module, however, we use a direct subprocess approach to the MCP server — it's more explicit, easier to debug, and works without SDK version dependencies. The pattern is: start the server process, send a JSON-RPC initialize handshake, then send tools/call requests, parse the response. Once you understand the wire protocol, the higher-level SDK abstractions are easy to adopt later.

Key Insight

MCP is not just for Anthropic models. It's an open standard — any agent framework can implement it. Wrapping your tools as MCP servers means they're immediately reusable across models, frameworks, and contexts. For tools you build and use repeatedly (web search, database access, calendar, email), MCP is the right abstraction. The upfront cost of the protocol is paid back the first time you reuse the server in a second context without writing new integration code.

MCP in Claude Code

When you add an MCP server to Claude Code's configuration, Claude Code's built-in agent gains that tool for all sessions — automatically, for any task where it's relevant. The same Brave Search MCP server you configure for Scout today can be added to ~/.claude/claude_desktop_config.json so Claude Code can also search the web during coding sessions. One MCP server, many consumers, zero additional integration code.

Step 02

Create mcp_tools.py

This file wraps the Brave Search MCP server in a clean Python interface:

Claude Code Prompt
Create mcp_tools.py. It should:
1. Load BRAVE_API_KEY from the .env file using python-dotenv
2. Provide an async function get_brave_tools() that returns the brave_web_search tool definition in Anthropic API format
3. Provide an async function call_brave_search(query: str, count: int = 5) -> dict that starts the Brave Search MCP server as a subprocess, sends it an initialize request followed by a tools/call request over stdin, and parses the response from stdout
4. Add python-dotenv to requirements.txt

Use a direct subprocess approach — start the server with asyncio.create_subprocess_exec, pipe JSON-RPC messages in, parse the JSON lines out. Don't use the SDK's MCPServerStdio class for now — I want to understand the wire protocol.

Only create mcp_tools.py.

Claude Code will generate a file close to this:

# mcp_tools.py import os import json import asyncio try: from dotenv import load_dotenv load_dotenv() except ImportError: pass BRAVE_API_KEY = os.getenv("BRAVE_API_KEY", "") async def get_brave_tools() -> list: """Return Brave Search tool definitions in Anthropic tool format.""" return [ { "name": "brave_web_search", "description": ( "Search the real web using Brave Search. Returns current results " "with titles, URLs, snippets, and publication dates. Use for any " "topic requiring up-to-date information. Specific queries return " "better results than vague ones." ), "input_schema": { "type": "object", "properties": { "query": { "type": "string", "description": "Search query. Be specific." }, "count": { "type": "integer", "description": "Number of results to return (1-10, default 5)", "default": 5 } }, "required": ["query"] } } ] async def call_brave_search(query: str, count: int = 5) -> dict: """Call the Brave Search MCP server via subprocess JSON-RPC.""" if not BRAVE_API_KEY: return { "error": "no_api_key", "message": "Set BRAVE_API_KEY in .env — get a free key at brave.com/search/api/" } # MCP JSON-RPC messages init_msg = json.dumps({ "jsonrpc": "2.0", "id": 0, "method": "initialize", "params": { "protocolVersion": "2024-11-05", "capabilities": {}, "clientInfo": {"name": "scout", "version": "1.0"} } }) + "\n" call_msg = json.dumps({ "jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": { "name": "brave_web_search", "arguments": {"query": query, "count": count} } }) + "\n" try: proc = await asyncio.create_subprocess_exec( "npx", "-y", "@modelcontextprotocol/server-brave-search", stdin=asyncio.subprocess.PIPE, stdout=asyncio.subprocess.PIPE, stderr=asyncio.subprocess.DEVNULL, env={**os.environ, "BRAVE_API_KEY": BRAVE_API_KEY} ) stdout, _ = await asyncio.wait_for( proc.communicate(input=(init_msg + call_msg).encode()), timeout=15.0 ) # Parse lines, find the response with id=1 for line in reversed(stdout.decode().split("\n")): line = line.strip() if not line: continue try: data = json.loads(line) if data.get("id") == 1: result = data.get("result", {}) content = result.get("content", []) if content and content[0].get("type") == "text": return json.loads(content[0]["text"]) except (json.JSONDecodeError, KeyError): continue return {"error": "parse_error", "message": "Could not parse MCP server response"} except asyncio.TimeoutError: return {"error": "timeout", "message": "MCP server did not respond within 15 seconds"} except FileNotFoundError: return { "error": "not_installed", "message": "npx not found — install Node.js and run: npm install -g @modelcontextprotocol/server-brave-search" }

The asyncio.wait_for timeout wrapper is important: without it, a hung server process will block your agent indefinitely. 15 seconds is generous for a search request; reduce it to 8 seconds in production.

Step 03

Update tools.py to use real Brave Search

Now swap the stub for the real implementation with a clean fallback:

Claude Code Prompt
Update the web_search function in tools.py to use Brave Search when BRAVE_API_KEY is set in the environment, and fall back to the stub when it's not set. Import call_brave_search from mcp_tools and use asyncio.run() to call it from the sync web_search function. Add a comment at the top of the function showing how to tell which mode is active.

Only modify tools.py — keep the function signature identical to what's already there.

The updated web_search function:

# Updated web_search in tools.py def web_search(query: str, count: int = 5) -> dict: """ Search the web for information. Real mode: BRAVE_API_KEY is set in environment -> uses Brave Search MCP Stub mode: BRAVE_API_KEY not set -> returns placeholder results Check active mode: result.get("_stub") is True means stub is active. """ import os import asyncio if os.getenv("BRAVE_API_KEY"): from mcp_tools import call_brave_search try: result = asyncio.run(call_brave_search(query, count)) if "error" not in result: return result # MCP call failed — fall through to stub with a warning print(f" [warning] Brave Search error ({result.get('error')}): {result.get('message')} — using stub") except RuntimeError: # asyncio.run() raises RuntimeError if called inside a running event loop # (e.g., when called from within subagents.py's async context). # In that case, the caller should use `await asyncio.to_thread(web_search, query)`. print(" [warning] asyncio loop conflict in web_search — using stub") # Stub fallback import time return { "query": query, "results": [ { "title": f"Understanding {query}: A Guide", "url": "https://example.com/guide", "snippet": f"A comprehensive overview of {query}...", "source": "example.com" }, { "title": f"{query} — Analysis", "url": "https://research.example.com", "snippet": f"Analysis of {query} and related topics...", "source": "research.example.com" }, { "title": f"How {query} Works", "url": "https://technical.example.com", "snippet": f"Technical examination of {query}...", "source": "technical.example.com" } ], "timestamp": time.time(), "_stub": True }

The _stub: True flag in stub results lets you programmatically detect which mode is active during testing — check for its presence in debug output or assertions.

Section 04

Under the hood

The stub-to-real upgrade pattern: Nothing in agent.py, the ReAct loop, or the subagent architecture changed in this module. Only the implementation of web_search changed. This is the payoff of the tool design from Module P02 — tools as swappable implementations behind a stable interface. The agent dispatches to web_search(query=...); it has no knowledge of whether that call hits Brave or returns fake data. This interface boundary is where the upgrade happened. When you need to swap Brave for a different provider, the change is local to mcp_tools.py and the web_search function — nowhere else.

MCP protocol basics — JSON-RPC 2.0 over stdio: Every MCP interaction follows the same two-phase pattern. First: an initialize request where the client announces the protocol version and its capabilities; the server responds with its own capabilities. Second: a sequence of tools/call requests, each with a tool name and typed arguments, each returning a structured result. The server runs as a subprocess and communicates exclusively via stdin/stdout — there's no port to open, no service to run, no daemon. The server starts when you need it and the process exits when the pipe closes. This is why local MCP servers work in sandboxed environments and require no network configuration.

Async in a sync codebase: asyncio.run() in a synchronous function works correctly when there is no active event loop in the current thread — which is the case when web_search is called from Scout's synchronous ReAct loop. The problem arises when web_search is called from within an already-running async context, like run_searcher in subagents.py. In that case asyncio.run() raises RuntimeError: This event loop is already running. The fix is to call web_search via await asyncio.to_thread(web_search, query) from async code — which is how subagents.py already calls the Anthropic SDK. For a fully clean codebase, the right long-term move is to make web_search itself async and update all callers. For now, the warning message and fallback to stub is an acceptable bridge.

When to go beyond the stub: The stub earned its keep across four modules of development. It let you build, test, and iterate on the agent architecture without consuming API credits or depending on external service availability. Keeping it as a fallback means Scout still works when BRAVE_API_KEY isn't set — useful for unit tests, offline demos, and environments where you want deterministic (if fake) results. The _stub: True flag in the response makes it easy to assert in tests that you're in the mode you expect. Don't delete the stub; just make it secondary.
