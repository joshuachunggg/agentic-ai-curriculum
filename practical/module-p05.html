Section 01

What we're building

Scout can already search the web and save notes — but every piece of information it works with comes from the web. It has no way to read a file you point it to: a spec doc, a codebase, a report. If you tell Scout "analyze this design document" or "review my agent.py," it can't do it — there's no tool for file access.

This module adds workspace file access via the MCP filesystem server. You'll install one MCP server, create mcp_filesystem.py to wrap it, and add two new tools: read_workspace_file and list_workspace. The ReAct loop doesn't change. The tool dispatch doesn't change. Only the tool list grows.

The MCP filesystem server exposes read_file, write_file, list_directory, and search_files — standard file operations via the same JSON-RPC protocol used by every MCP server. We'll use read_file and list_directory, giving Scout enough to read any file in the workspace and discover what's available.

Section 02

The concept — MCP

The Model Context Protocol is Anthropic's open standard for how agents communicate with tools. Before MCP, every agent had its own bespoke integration — custom API wrappers, custom schemas, custom auth flows, custom error handling. Connecting a new tool meant writing new glue code every time. MCP standardizes the contract: a tool server exposes its capabilities via a defined protocol, and any MCP-compatible agent can discover and use those capabilities without writing custom integration code. It's the USB-C of agent tools — one standard, many devices.

Technically, an MCP server is a process that implements the MCP protocol. It exposes a tools/list endpoint (here are the tools I have) and a tools/call endpoint (call this tool with these parameters). The agent discovers what's available, then invokes tools by name with typed parameters. The server handles execution and returns structured results. Communication happens over stdio for local servers — the server is a subprocess, your agent pipes JSON-RPC messages into its stdin and reads results from its stdout. For remote servers the transport is HTTP+SSE, but the protocol is identical.

Why MCP matters for the ecosystem is best understood through the alternative. Without it, a filesystem integration written for Scout would need to be rewritten from scratch to work with a different agent framework, a different language, or a different model provider. With MCP, a tool built once as an MCP server works with any MCP-compatible consumer — Claude Code, your Python agent, any future framework. The tool investment compounds instead of stacking up as one-off integrations.

Since SDK version 0.40+, the Anthropic Python SDK has built-in support for connecting to MCP servers via MCPServerStdio and related classes. For this module, however, we use a direct subprocess approach to the MCP server — it's more explicit, easier to debug, and works without SDK version dependencies. The pattern is: start the server process, send a JSON-RPC initialize handshake, then send tools/call requests, parse the response. Once you understand the wire protocol, the higher-level SDK abstractions are easy to adopt later.

Key Insight

MCP is not just for Anthropic models. It's an open standard — any agent framework can implement it. Wrapping your tools as MCP servers means they're immediately reusable across models, frameworks, and contexts. For tools you build and use repeatedly (web search, database access, calendar, email), MCP is the right abstraction. The upfront cost of the protocol is paid back the first time you reuse the server in a second context without writing new integration code.

MCP in Claude Code

When you add an MCP server to Claude Code's configuration, Claude Code's built-in agent gains that tool for all sessions — automatically, for any task where it's relevant. The same filesystem MCP server you configure for Scout today can be added to ~/.claude/claude_desktop_config.json — Claude Code gains workspace file awareness for all your sessions. One MCP server, many consumers, zero additional integration code.

Step 02

Create mcp_filesystem.py

This file wraps the filesystem MCP server in a clean Python interface:

Claude Code Prompt
Create mcp_filesystem.py to wrap the @modelcontextprotocol/server-filesystem MCP server:

- WORKSPACE = Path(os.getenv("SCOUT_WORKSPACE", ".")).resolve() — the root the server is allowed to access
- call_filesystem(method: str, arguments: dict) — async function that starts the server as a subprocess (npx -y @modelcontextprotocol/server-filesystem <WORKSPACE>), sends initialize + tools/call JSON-RPC messages via stdin/stdout, returns the parsed result. Use asyncio.create_subprocess_exec, asyncio.wait_for with a 10s timeout.
- read_workspace_file(path: str) — sync wrapper: validates path doesn't escape WORKSPACE, calls asyncio.run(call_filesystem("read_file", {"path": ...})), returns {"path": path, "content": text[:5000], "chars": len(text)} or a structured error dict.
- list_workspace(directory: str = ".") — sync wrapper: validates path, calls asyncio.run(call_filesystem("list_directory", {"path": ...})), returns {"directory": directory, "listing": text}.

Only create mcp_filesystem.py.

Claude Code will generate a file close to this:

mcp_filesystem.py
# mcp_filesystem.py
import os
import json
import asyncio
from pathlib import Path

WORKSPACE = Path(os.getenv("SCOUT_WORKSPACE", ".")).resolve()

async def call_filesystem(method: str, arguments: dict) -> dict:
    init_msg = json.dumps({
        "jsonrpc": "2.0", "id": 0,
        "method": "initialize",
        "params": {
            "protocolVersion": "2024-11-05",
            "capabilities": {},
            "clientInfo": {"name": "scout", "version": "1.0"}
        }
    }) + "\n"

    call_msg = json.dumps({
        "jsonrpc": "2.0", "id": 1,
        "method": "tools/call",
        "params": {"name": method, "arguments": arguments}
    }) + "\n"

    try:
        proc = await asyncio.create_subprocess_exec(
            "npx", "-y", "@modelcontextprotocol/server-filesystem", str(WORKSPACE),
            stdin=asyncio.subprocess.PIPE,
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.DEVNULL
        )

        stdout, _ = await asyncio.wait_for(
            proc.communicate(input=(init_msg + call_msg).encode()),
            timeout=10.0
        )

        for line in reversed(stdout.decode().split("\n")):
            line = line.strip()
            if not line:
                continue
            try:
                data = json.loads(line)
                if data.get("id") == 1:
                    content = data.get("result", {}).get("content", [])
                    if content and content[0].get("type") == "text":
                        return {"text": content[0]["text"]}
            except (json.JSONDecodeError, KeyError):
                continue

        return {"error": "parse_error", "message": "Could not parse MCP server response"}

    except asyncio.TimeoutError:
        return {"error": "timeout", "message": "Filesystem MCP server timed out"}
    except FileNotFoundError:
        return {
            "error": "not_installed",
            "message": "npx not found — install Node.js: https://nodejs.org"
        }

def read_workspace_file(path: str) -> dict:
    safe = (WORKSPACE / path).resolve()
    if not str(safe).startswith(str(WORKSPACE)):
        return {"error": "path_traversal", "message": "Path is outside workspace"}
    try:
        result = asyncio.run(call_filesystem("read_file", {"path": str(safe)}))
        if "error" in result:
            return result
        text = result.get("text", "")
        return {"path": path, "content": text[:5000], "chars": len(text)}
    except RuntimeError as e:
        return {"error": "runtime_error", "message": str(e),
                "suggestion": "From async code, use: await asyncio.to_thread(read_workspace_file, path)"}

def list_workspace(directory: str = ".") -> dict:
    safe = (WORKSPACE / directory).resolve()
    if not str(safe).startswith(str(WORKSPACE)):
        return {"error": "path_traversal", "message": "Path is outside workspace"}
    try:
        result = asyncio.run(call_filesystem("list_directory", {"path": str(safe)}))
        if "error" in result:
            return result
        return {"directory": directory, "listing": result.get("text", "")}
    except RuntimeError as e:
        return {"error": "runtime_error", "message": str(e)}

Section 04

Under the hood

MCP protocol basics — JSON-RPC 2.0 over stdio: Every MCP interaction follows the same two-phase pattern. First: an initialize request where the client announces the protocol version and its capabilities; the server responds with its own capabilities. Second: a sequence of tools/call requests, each with a tool name and typed arguments, each returning a structured result. The server runs as a subprocess and communicates exclusively via stdin/stdout — there's no port to open, no service to run, no daemon. The server starts when you need it and the process exits when the pipe closes. This is why local MCP servers work in sandboxed environments and require no network configuration.

Async in a sync codebase: asyncio.run() in a synchronous function works correctly when there is no active event loop in the current thread — which is the case when read_workspace_file is called from Scout's synchronous ReAct loop. The problem arises when read_workspace_file is called from within an already-running async context — which can happen if you extend subagents.py to call read_workspace_file directly. In that case asyncio.run() raises RuntimeError: This event loop is already running. The fix is to call it via await asyncio.to_thread(read_workspace_file, path) from async code — the error message in the returned dict includes this suggestion so the failure is self-documenting.

Path safety and workspace sandboxing: The path_traversal check in read_workspace_file is not optional. Without it, a prompt like "read the file ../../etc/passwd" resolves outside the workspace and reads a sensitive system file. Resolving to an absolute path and checking that it starts with WORKSPACE is the standard guard. The MCP filesystem server also enforces its own root restriction, so this is defense in depth — two independent checks, neither trusting the other.

Why two separate tools instead of one: read_workspace_file and list_workspace are separate by design. A single "access_filesystem" tool that bundles listing and reading would force the model to guess which operation it needs or include mode flags in the API. Separate tools with clear names let the model reason correctly: "I should list the directory first so I know what files exist, then read the relevant one." Tight tool boundaries produce more predictable agent behavior.

Section 06

What Scout can do now

Scout can now work with files in your project, not just the web. Ask it to analyze a spec, review a code file, or summarize a document — it will list what's available, read the relevant content, and synthesize from it the same way it synthesizes from web sources. The MCP filesystem server handles the file I/O; the ReAct loop, the memory system, and the subagent pipeline all work exactly as before.
