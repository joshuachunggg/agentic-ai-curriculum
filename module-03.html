Context Engineering:
The Skill That Replaced
Prompt Engineering

Prompt engineering is about what you say. Context engineering is about what the model sees. By 2025–2026, the AI practitioner community had reached consensus: context quality is the primary determinant of agent performance. This module teaches you to treat context as a finite, high-value resource to be designed — not assumed.

Duration 1.5 weeks
Level Core
Prerequisites Modules 01–02
Topic 01

What Context Engineering Means — and What It Isn't

The community consensus in 2026 is clear: prompt engineering, while still relevant, is no longer the bottleneck. Agents fail because their context is noisy, overloaded, or irrelevant — not because the prompt was poorly worded. A brilliantly phrased instruction surrounded by 40,000 tokens of irrelevant conversation history will produce worse results than a plain instruction in a clean, well-structured context.

Prompt engineering asks: how should I phrase this instruction? Context engineering asks: what information should the model be seeing at all, and in what form? These are different questions. The first is about language. The second is about architecture.

Beyond Prompts: Everything the Model Sees at Inference Time

A model's context window is the totality of what it processes when generating a response. That includes your system prompt, yes — but also conversation history, retrieved documents, tool call results, injected agent state, few-shot examples, structured output schemas, and any other text that arrives before the model's generation starts. Everything the model sees is context. Everything the model does not see might as well not exist.

Context engineering is the practice of deciding what goes into that window: what to include, what to compress, what to retrieve on demand, and what to discard entirely. It requires you to think about information value per token — and to make deliberate tradeoffs. The model doesn't have a memory outside the context window. If something isn't in there, the model can't use it. If too much is in there, important information gets crowded out.

Insight

Think of the context window as a whiteboard in a conference room. Every token you write on that whiteboard takes up space. When the board is full, you have to erase something before you can write anything new. The art is deciding what's worth keeping on the board and what can be summarized in a sticky note.

This shift in framing has real consequences. It means that the team responsible for agent quality is no longer just writing prompts — they are architecting information flows. They're deciding what gets stored, when it gets retrieved, how it gets formatted, and when it gets evicted. That's a fundamentally different skill than prompt writing, and it's where most of the performance gains are found in 2026.

Topic 02

How Long Contexts Fail: Dilution, Attention Drift, Reasoning Fatigue

When context window sizes expanded from 4K to 128K to 1M tokens, many practitioners assumed the context management problem was solved. It wasn't. A larger bucket doesn't fix a leaky bucket. Long contexts introduce failure modes that have nothing to do with running out of space — they have everything to do with how models attend to information.

Models don't read their context the way humans read a document. They assign attention weights to tokens, and those weights are not uniform. Research has repeatedly demonstrated that models pay more attention to tokens at the beginning and end of a context, and systematically less attention to tokens in the middle. This is called the lost-in-the-middle effect. If you bury a critical instruction or a key fact in the middle of a 60,000-token context, the model may effectively ignore it — not because it can't read it, but because its attention mechanism deprioritizes it relative to tokens at the edges.

  • Lost-in-the-Middle
    Models attend more to the beginning and end of context than the middle. Critical information placed in the center of a long context gets systematically underweighted. In retrieval tasks, models perform significantly better when relevant content appears first or last in the retrieved set versus sandwiched in the middle.
  • Attention Dilution
    As context grows, signal-to-noise ratio drops. Every token competes for the model's attention. A relevant sentence surrounded by 50,000 tokens of irrelevant content gets a fraction of the attention it would receive in a clean, short context. More context doesn't help — it actively hurts when the signal is outweighed by noise.
  • Reasoning Fatigue
    Long chains of prior reasoning in context can anchor the model to earlier, possibly wrong, conclusions. If the model reasoned itself into a dead end in turn 12 of a 40-turn conversation and that reasoning is still visible in turn 40, it has a tendency to reference and extend that prior reasoning even when it's no longer correct. The solution isn't to reason less — it's to evict stale reasoning and replace it with updated conclusions.

Why Bigger Context Windows Don't Solve Bad Context Design

A 1M-token context window is genuinely useful for document-level tasks: reasoning over an entire codebase, reading a book, analyzing a long legal contract. But for multi-turn agent tasks, the failure modes above scale with context length, not against it. An agent that dumps every tool result, every prior reasoning chain, and every conversation turn into a 500K-token context will perform worse than an agent that actively curates its context to the most relevant 15K tokens.

Common Mistake

The naive assumption: "I'll just use the largest context window available and never worry about context management." This leads to agents that degrade over time, produce inconsistent outputs as conversations lengthen, and are expensive to run. Context management isn't an optimization — it's a correctness requirement for long-horizon agents.

Example — Aria at Turn 40+

Aria, the customer success agent we've been tracking, has a problem at turn 40 of a long support conversation. Her context contains the full raw transcript: greetings, pleasantries, dead-end troubleshooting paths, tool results for queries that turned out to be irrelevant, and outdated assumptions about the customer's account state. By turn 40, the useful content — the actual account details, the current error state, the agreed-upon troubleshooting path — is buried in the middle of 35,000 tokens of noise. Aria starts giving inconsistent answers because the signal she needs is diluted. The fix is not a bigger context window. The fix is context engineering.

Topic 03

Structuring Agent Context: System Prompts, Conversation History, Injected State

A well-engineered agent context has structure. It isn't a flat dump of information — it's a set of distinct zones, each with a different purpose, each managed differently. Understanding these zones is the foundation of context architecture.

The Role of the System Prompt

The system prompt is your highest-leverage piece of real estate. It's read at every inference call, it's at the top of the context (maximum primacy), and the model treats it as persistent background knowledge. This is where you encode the agent's persona, goals, constraints, operational rules, and any invariants that should never be violated.

A good system prompt is dense with intent and sparse with verbosity. It answers four questions: Who is this agent? What is it trying to accomplish? What constraints apply in all situations? What format should outputs take? Everything beyond these four is likely noise. The system prompt is not the place for dynamic information — it's the place for stable information.

# Aria — Customer Success Agent
## Identity
You are Aria, a customer success agent for Acme SaaS.
Your primary goal is customer resolution, not deflection.

## Constraints
- Never promise features not on the roadmap
- Never share another customer's data
- Escalate to a human agent when: billing disputes > $500,
  legal threats, or 3+ failed resolution attempts

## Output format
Always respond in plain prose. No bullet lists unless
listing steps. Confirm understanding before troubleshooting.

## Current context (injected dynamically below)
[AGENT_STATE_BLOCK]

Notice the [AGENT_STATE_BLOCK] placeholder. This is where structured, dynamic information gets injected at each inference call. The system prompt itself stays stable — but it designates a slot for the context layer that does change.

How to Encode Persona, Goals, and Constraints

Persona should be stated once, concisely, and never repeated. "You are Aria, a customer success agent focused on resolution" is enough. Repeating it doesn't help — it wastes tokens. Goals should specify outcomes, not behaviors. "Your goal is to resolve the customer's issue" is better than "You should try to help customers and be nice to them and listen carefully." Constraints should be stated as hard rules with specific triggers, not as vague guidance.

Conversation History and Injected State

Conversation history is the most dynamic and most dangerous part of the context. Raw conversation history grows without bound, contains redundancy, and includes information that loses relevance over time. It should never be naively appended forever. We'll cover how to manage it in Topic 4.

Injected state is the bridge between your agent's external memory systems and the context window. This is where you place the output of a retrieval query, the current task progress, facts established earlier in the conversation, and any structured data the agent needs for the current step. Injected state is ephemeral — it changes every call — but it should be formatted consistently so the model knows exactly where to find it.

Insight

The distinction between "always in context" (system prompt) and "injected per-call" (state block) is one of the highest-impact architectural decisions you can make. Information that belongs in the system prompt should be stable, universal, and identity-defining. Information that belongs in the state block is situational and changes with each step of the task.

# [AGENT_STATE_BLOCK] — injected each call
## Customer Profile
- Account: Acme Corp (Enterprise tier)
- Open tickets: 2 (IDs: T-4421, T-4398)
- Last login: 2026-05-21
- Subscription status: Active

## Current Issue
Customer reports: "Dashboard not loading since yesterday"
Confirmed: Browser logs show 403 on /api/v2/dashboard

## Established Facts
- Issue began after 2026-05-20 deploy (v4.2.1)
- Customer is on Chrome 124, Windows 11
- Basic auth confirmed working

## Conversation Summary (turns 1–12)
Customer contacted re: dashboard outage. Confirmed account
active. Reproduced 403. Ruled out: cache, extensions,
network. Likely server-side permission regression in v4.2.1.

## Current Turn: 13

This structure puts the most important information at the top (customer identity and current issue), followed by established facts, then a summary of prior reasoning. The raw turns 1–12 are gone — replaced by a 5-sentence synthesis. The model sees everything it needs and nothing it doesn't.

Topic 04

Dynamic Context Management: What to Include, Compress, or Evict

Static context design gets you started. Dynamic context management is what makes agents work over long horizons. Every step of an agentic loop produces new information: tool results, model outputs, updated task state. You can't keep all of it. You have to make active decisions about what survives each step and what gets transformed or discarded.

Rolling Summarization

The most common pattern is rolling summarization: when the raw conversation history exceeds a threshold (say, 8,000 tokens), a summarization step is triggered. The oldest N turns are compressed into a dense summary block. The raw turns are evicted. The summary replaces them at the same location in the context. The model continues from the compressed representation, not the raw transcript.

Good summarization is lossy in the right ways. It discards pleasantries, redundant confirmations, and failed approaches. It preserves conclusions, established facts, committed actions, and current task state. A summary that tries to preserve everything isn't compression — it's just rewriting.

# Rolling summarization trigger logic

def should_summarize(context_tokens: int, threshold: int = 8000) -> bool:
    return context_tokens > threshold

def summarize_turns(turns: list[dict], llm) -> str:
    """
    Compress old turns into a dense summary.
    Preserve: conclusions, facts, decisions, current state.
    Discard: greetings, failed paths, redundant steps.
    """
    prompt = f"""
You are summarizing a support conversation for agent memory.
Extract only: established facts, agreed actions, current issue state.
Maximum 200 words.

Conversation to summarize:
{format_turns(turns)}
"""
    return llm.complete(prompt)

# In the agentic loop:
if should_summarize(token_count(context)):
    old_turns = history[:SUMMARIZE_WINDOW]
    summary = summarize_turns(old_turns, llm)
    history = [{"role": "summary", "content": summary}] + history[SUMMARIZE_WINDOW:]

Explicit Memory Slots

Rather than letting your context grow as an undifferentiated stream, carve it into named sections. Each section has a purpose, a maximum size, and an update policy. The model learns (through system prompt instruction) that specific things live in specific places. This reduces the search space for each piece of information and makes the context more navigable.

Slot 01
Agent State
Current mode, active task, subtasks in progress. Updated every step. Maximum ~500 tokens. Never grows unbounded.
Slot 02
Established Facts
Facts confirmed during the task that the agent must not re-derive. Append-only during task; reset between tasks. ~1,000 tokens max.
Slot 03
Conversation Summary
Rolling compressed representation of prior turns. Replaces raw history beyond a threshold. Updated by summarization step.
Slot 04
Retrieved Context
Output of retrieval queries — documents, knowledge base chunks, tool results. Freshly injected each call. Evicted when no longer relevant.

Context Budget Tracking

Treat tokens like a budget. Your total context window might be 128K tokens. Your system prompt costs 800. Your agent state block costs 600. Your conversation summary costs 1,200. Your retrieved chunks cost 4,000. That leaves roughly 120K for the current turn, tool results, and generation. When a tool returns a 40,000-token document, you can't just dump it in — you've blown your budget for retrieved context.

Budget-aware agents make this explicit. Before injecting any new content, they check the current token count against the budget. If the retrieved content exceeds the slot's budget, it gets truncated, summarized, or chunked. The generation itself is also budgeted — if you need the model to produce a 2,000-token structured output, you can't fill the context to 127,999 tokens and expect that to work.

Priority Ordering and Primacy/Recency Effects

Because models attend more to the beginning and end of context, put the most important information in those positions. System prompt goes first (primacy). The most recent, most relevant information goes last (recency). Supporting context, historical summaries, and reference material go in the middle — but keep them short, because middle content is systematically underweighted.

Insight

A practical ordering rule: put constraints and identity at the top (system prompt), the immediate task and most relevant retrieved facts just before the current turn, and never put mission-critical instructions only in the middle of a long context. If something must be obeyed, it belongs in the system prompt — not in a long document buried 20,000 tokens in.

Example — Aria After Context Redesign

After turn 12, Aria's conversation is summarized into a 300-token block. Her context at turn 40 looks like this: system prompt (800 tokens) → agent state block (600 tokens) → conversation summary through turn 38 (400 tokens) → turns 39–40 raw (600 tokens) → retrieved knowledge base chunk for the specific error code (800 tokens). Total: under 3,200 tokens, perfectly structured, all signal. She resolves the case consistently and cheaply. The difference from the 35,000-token version isn't capability — it's architecture.

Topic 05

RAG and Retrieval-Augmented Agents — When It's Right

Retrieval-Augmented Generation is the pattern of fetching relevant information from an external store at inference time and injecting it into the context. It's not a new idea — but as agents became more prevalent, RAG became the default answer to the question "how does the agent know things it wasn't trained on?"

The intuition is straightforward. You can't fit a 500-page product documentation into a context window. You can't include every past customer case in Aria's context. But you can retrieve the three most relevant passages and inject those. The model gets the information it needs, when it needs it, without blowing its context budget on information it doesn't need right now.

RAG vs. Fine-Tuning: The Right Decision

The recurring confusion is between RAG and fine-tuning as solutions to the same problem. They're not solving the same problem. Use RAG when your knowledge is dynamic and changes frequently: product updates, customer records, current events, internal documentation that gets revised. RAG retrieves the current version at runtime, so your agent is always working with fresh information.

Use fine-tuning when you need to change the model's behavior, style, or reasoning patterns — not its knowledge. Fine-tuning is for teaching the model how to respond, not what to know. A model fine-tuned on your support ticket data will learn the tone and format of good support responses. It will not reliably "remember" specific ticket details — that's what RAG is for.

Situation Use RAG Use Fine-tuning
Knowledge changes frequently Yes No — retraining is expensive
Need specific facts at runtime Yes No — models hallucinate memorized facts
Need consistent output format/style No Yes
Need domain-specific reasoning patterns No Yes
Knowledge base is >1M tokens Yes Impractical to train on

Chunking Strategies

RAG doesn't retrieve documents — it retrieves chunks. How you cut documents into chunks determines what the model sees. Fixed-size chunking is the simplest: split every document into 512-token blocks with some overlap. It's fast and predictable, but it can cut sentences mid-thought, severing context that the model needs.

Semantic chunking splits on meaningful boundaries: paragraphs, sections, sentences. The chunks vary in size but preserve coherent units of meaning. This generally outperforms fixed-size chunking on question-answering tasks because the retrieved chunks are self-contained. Hierarchical chunking takes this further: you index both summary-level chunks (section headings, paragraph summaries) and detailed chunks (the full text). Retrieval first finds the right section, then pulls the detailed passage. This is especially effective for long, structured documents like technical specifications.

Hybrid Retrieval: Dense + Sparse

Dense retrieval uses vector embeddings and semantic search. You embed the query and the chunks into the same vector space, then find the closest neighbors. It handles synonyms, paraphrases, and conceptual similarity well. It struggles with exact keyword matches — if a user asks about "Error Code 4421," dense retrieval may not return the chunk that literally contains "4421" if that string isn't well-represented in the embedding space.

Sparse retrieval (BM25 and its variants) is keyword-based. It's excellent at exact matches and technical terms. It fails on semantic similarity — "fix the login problem" won't match a document about "authentication resolution."

Hybrid retrieval combines both. Run both dense and sparse retrieval in parallel, then re-rank the combined results using a cross-encoder or a weighted fusion. The combined retriever consistently outperforms either alone, particularly for technical domains where users mix semantic queries with exact identifiers.

Example — COMPASS Synthesizer and RAG

COMPASS is the 3-agent competitive intelligence system from Module 2. Its Synthesizer agent takes research results from the Researcher and Analyst subagents and writes a synthesis report. The problem: those subagents collectively produce 80,000+ tokens of research notes — far more than the Synthesizer's budget for retrieved context. The Synthesizer can't hold all of it. Instead, it uses RAG. For each section of the report (market positioning, feature comparison, threat assessment), it queries the research notes vector store with a section-specific query and retrieves only the most relevant 4–6 chunks. The Synthesizer writes one section at a time, each with a fresh retrieval call. Total context per section: under 8,000 tokens. The final report is coherent and grounded — not because the Synthesizer read everything, but because it retrieved the right things at the right time.

Retrieval Quality Is the Bottleneck

This is the insight practitioners learn the hard way: retrieval quality is the primary determinant of RAG system quality. A frontier-level generation model paired with mediocre retrieval produces bad outputs. A medium-strength model paired with excellent retrieval produces good outputs. The generator can only work with what retrieval gives it. If retrieval returns the wrong chunks, no amount of generation quality compensates.

What degrades retrieval quality? Poor chunking that splits coherent content. Embeddings trained on different domains from your content. Insufficient metadata for filtering. No re-ranking step. Missing content in the index — the most common failure, where the answer simply isn't indexed. Retrieval evaluation should be its own workstream, with its own metrics (recall@k, MRR, NDCG) and its own test suite, separate from end-to-end generation quality.

Common Mistake

Treating RAG as a black box. Teams often embed their documents, spin up a vector store, and ship — then debug failures at the generation layer when the real problem is at the retrieval layer. If the model is producing wrong answers, the first thing to check is whether retrieval returned the right chunks. Print the retrieved context. Evaluate retrieval independently. Don't assume retrieval is working.

Topic 06

Few-Shot Examples and Structured Outputs in Agent Context

Few-shot examples — concrete input/output demonstrations placed in the model's context — are one of the oldest tricks in prompting. In the context engineering frame, they're better understood as behavioral anchors. They show the model not just what to do but what correct-looking output looks like in this specific context. That's different from instruction.

Static vs. Dynamic Few-Shot

Static few-shot examples live in the system prompt. You write them once, they're always present, and they consume tokens at every call. They're appropriate when your task is uniform: every call has the same structure, the same output format, the same type of input. Three or four carefully chosen examples in the system prompt can dramatically anchor the model's behavior.

Dynamic few-shot retrieves examples at runtime based on the current input. You maintain a library of high-quality input/output pairs, embed them, and at inference time retrieve the examples most similar to the current query. The model sees examples that are semantically close to what it's being asked to do right now. This outperforms static few-shot on diverse tasks because the examples are always relevant — but it requires an example library, an embedding index, and a retrieval step.

# Static few-shot in system prompt (appropriate for uniform tasks)
SYSTEM:
You are Aria, customer success agent.
Respond to issues using this format:

---EXAMPLE 1---
Customer: "I can't log in"
Response: "Let me help with that. Can you tell me
what happens when you try to log in — error message,
or just nothing?"

---EXAMPLE 2---
Customer: "My export is stuck at 0%"
Response: "That's a known issue with large exports.
Let me check if there's an active job in your queue.
One moment."
---END EXAMPLES---


# Dynamic few-shot (appropriate for diverse tasks)
def retrieve_examples(query: str, k: int = 3) -> list[dict]:
    """Retrieve k most relevant examples for this query."""
    query_embedding = embed(query)
    return example_store.search(query_embedding, k=k)

def build_context(query: str) -> str:
    examples = retrieve_examples(query)
    example_text = format_examples(examples)
    return system_prompt + "\n\n" + example_text + "\n\n" + query

The Few-Shot Tradeoff

More examples produce better behavioral anchoring. The model has more signal about what correct output looks like, which reduces variance and reduces format errors. But more examples cost tokens — tokens that could otherwise be used for reasoning, for retrieved context, or for the current task itself. Each example you add to the system prompt is a fixed cost on every single call.

The practical rule: start with three examples. Evaluate whether errors are format errors (the model produces the wrong structure) or reasoning errors (the model produces the wrong answer in the right structure). Format errors benefit from more examples. Reasoning errors do not — they require better context, better tool design, or better retrieval, not more behavioral anchoring.

Structured Outputs and JSON Mode

Structured generation — constraining the model to produce valid JSON, XML, or any other schema-conformant output — is one of the highest-ROI context engineering techniques for agents. When an agent needs to call a tool, update its state, or produce a machine-readable output, free-form text is fragile. Parsing errors cascade. A misplaced bracket in a JSON tool call means the tool doesn't get called, the agentic loop breaks, and you have an error to handle.

JSON mode (or structured generation using a schema) constrains the model's output space at the decoding layer. The model cannot produce invalid JSON if constrained to produce valid JSON. This dramatically reduces format errors without requiring examples to demonstrate format. The model doesn't need five examples of "always produce valid JSON" if the decoding is constrained to guarantee it.

# Structured output with schema constraint
from anthropic import Anthropic

client = Anthropic()

response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    system="""You are Aria. When escalating a ticket,
produce a structured escalation record.""",
    messages=[{"role": "user", "content": user_message}],
    tools=[{
        "name": "create_escalation",
        "description": "Create a structured escalation record",
        "input_schema": {
            "type": "object",
            "properties": {
                "severity": {
                    "type": "string",
                    "enum": ["low", "medium", "high", "critical"]
                },
                "reason": {"type": "string"},
                "customer_id": {"type": "string"},
                "assigned_team": {"type": "string"}
            },
            "required": ["severity", "reason", "customer_id"]
        }
    }]
)

# Tool input is guaranteed valid against the schema
escalation = response.content[0].input

Structured outputs also reduce the cognitive load on the model. When the output format is locked by a schema, the model doesn't have to reason about how to format its response — it only has to reason about content. This frees up reasoning capacity for the actual task. The few-shot tradeoff applies here too: when you use structured generation, you need fewer examples to demonstrate format, because the format is enforced. You can redirect those tokens to reasoning or retrieval.

Insight

Use structured outputs for everything that will be parsed by code. Use free-form text only for outputs that will be read by humans. If an agent's output goes back into the system — as a tool input, a state update, a database write — it should be structured. Structured outputs are not just an aesthetic choice; they're a reliability requirement for agentic systems.

The established facts block gives the model the conclusions of 34 turns of work without forcing it to re-read or re-derive them. The system prompt gives the model a clear identity, hard constraints, and output format guidance.

Module 03 Summary

  • Context engineering is the practice of deciding what the model sees at inference time — not just what you say to it. It's a fundamentally different skill from prompt engineering, and in 2026 it's the primary determinant of agent performance.
  • Long contexts fail in specific, predictable ways: lost-in-the-middle attention drift, signal dilution as noise accumulates, and reasoning fatigue from stale prior conclusions. Larger context windows don't solve these problems — they scale them.
  • Structure your agent context into distinct zones: system prompt (stable, identity-defining), injected state block (dynamic, per-call), conversation summary (compressed history), and retrieved context (on-demand, evicted when stale).
  • Manage context dynamically using rolling summarization, explicit memory slots with size budgets, token budget tracking, and priority ordering that puts critical information at primacy and recency positions.
  • RAG is the right pattern for dynamic, changing knowledge at runtime. Fine-tuning is the right pattern for stable behavior, style, and reasoning patterns. Use retrieval quality as the primary lever — a great generator with bad retrieval still fails.
  • Few-shot examples anchor model behavior and reduce format errors; dynamic few-shot (retrieval-based) outperforms static examples on diverse tasks. Structured outputs constrain the decoding layer, eliminating format errors entirely for machine-read outputs without spending tokens on demonstrations.
  • When debugging an agent, check the context first. Print what the model actually sees. Most failures are context failures — wrong information, missing information, or too much information drowning the signal.
