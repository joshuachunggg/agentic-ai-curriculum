Topic 01

Why Multi-Agent? Three Legitimate Reasons (and One That Isn't)

Before we talk about how to build multi-agent systems, we need to be honest about when you should build one at all. Multi-agent architecture adds real costs: coordination overhead, debugging complexity, more failure modes, and higher token spend. The question isn't "can we use multiple agents?" It's "does the task structure actually justify it?"

There are exactly three reasons to go multi-agent that hold up under scrutiny.

Reason 1: Parallelism

Some tasks decompose into subtasks that don't depend on each other's results. When they do, you can run those subtasks concurrently instead of sequentially. A single-agent system is serial by nature — it must complete each ReAct loop step before starting the next. A multi-agent system can dispatch multiple subagents simultaneously, and total latency becomes the time of the slowest subagent, not the sum of all of them.

COMPASS Example

The COMPASS competitive intelligence system receives a research question like "How are B2B SaaS companies responding to AI-native competitors entering their market?" The Planner decomposes this into five sub-questions: pricing strategy shifts, feature roadmap acceleration, churn patterns, messaging changes, and M&A activity. Each sub-question goes to a separate Researcher subagent. All five Researchers run simultaneously. The Synthesizer assembles their outputs. Total wall-clock time: ~40 seconds instead of ~200 seconds if run serially.

Reason 2: Specialization

Different subagents can have different system prompts, different tool access, and even different underlying models. A Researcher subagent needs web search tools and instructions optimized for factual extraction. A Synthesizer needs different instructions — about structure, argument clarity, and synthesis — and no web search at all. Trying to serve both roles with a single system prompt produces an agent that does neither well.

Specialization also lets you right-size models. A subagent doing simple data formatting doesn't need the same model as the one making complex analytical judgments. Running cheaper models for routine subagent work and expensive models only where reasoning depth matters is a real cost lever.

Reason 3: Error Isolation

In a single-agent system, a tool failure or a bad model output can derail the entire task. In a multi-agent system with an orchestrator, a subagent failure is localized. The orchestrator can detect the failure, log it, and decide to retry, reroute to a different subagent, or degrade gracefully — returning a partial result rather than a total failure. The system has seams where faults can be caught.

This is especially important in production. When you have ten Researcher subagents and one returns a garbage result, the Synthesizer can flag the anomaly and the orchestrator can retry just that one. The other nine results are preserved.

The Illegitimate Reason

"Because it sounds more sophisticated." We see this constantly: teams adding agents to a system because multi-agent feels more impressive, not because the task structure demands it. Adding an orchestrator layer to a system that was working fine as a single agent doesn't make it better. It makes it slower, harder to debug, and more expensive. Aria — the customer success agent we've been building since Module 1 — would be made strictly worse by multi-agent complexity. She handles one customer conversation at a time, her tasks aren't decomposable in parallel, and the coordination overhead would dwarf any benefit. Aria stays single-agent.

Topic 02

Orchestration Topologies: Hierarchical, Peer-to-Peer, Market-Based

There are three ways to arrange agents relative to each other. The topology you choose shapes the debugging story, the failure modes, and the governance model for the entire system.

Most Common
Hierarchical
One orchestrator at the top. Subagents below. The orchestrator decomposes tasks, dispatches work, monitors completion, and synthesizes results. Subagents don't communicate with each other — they report only to the orchestrator.
Production-ready. Debug easily. Clear accountability.
Emerging
Peer-to-Peer
Agents communicate directly with each other without a central coordinator. Useful for iterative refinement cycles: a Drafter sends output to a Critic who sends feedback back. Good for tasks where the answer evolves through dialogue.
Harder to debug. No single point of accountability.
Theoretical
Market-Based
Agents bid on tasks from a shared queue. The task goes to the agent that offers the best combination of capability and cost. Dynamic resource allocation. Handles variable task volumes without static role assignment.
More theoretical in 2026. Watch this space.

COMPASS is Hierarchical

The COMPASS system has a clear hierarchy: one Planner, three-to-five Researchers, one Synthesizer. The Planner doesn't know or care which Researcher handles which sub-question. The Researchers don't communicate with each other. The Synthesizer doesn't talk back to the Planner. Information flows down from Planner to Researchers, and up from Researchers to Synthesizer. This structure is what makes COMPASS debuggable: when a result is wrong, you check the Synthesizer first, then the relevant Researcher, then the Planner's decomposition.

Role Specialization Within Topologies

Regardless of topology, well-designed multi-agent systems define role boundaries explicitly. Four roles appear repeatedly in production systems:

Role
Researcher
Fetches and summarizes information from external sources. Optimized for factual extraction, source citation, and concise summarization. Tool access: web search, document retrieval, databases.
Role
Critic
Reviews outputs from other agents for accuracy, coherence, and completeness. Does not produce primary content — it evaluates it. Common in peer-to-peer topologies and quality gate patterns.
Role
Executor
Takes a fully specified plan and carries it out — writing code, making API calls, manipulating files. Needs no reasoning about what to do, only how to do it. Optimized for reliability and tool use accuracy.
Role
Evaluator
Compares output against a success criterion and produces a structured verdict. Used in evaluation loops where the orchestrator needs a signal about whether to accept, retry, or escalate a result.

These are archetypes, not mandates. Your system may combine roles or invent new ones. The discipline is in making sure every agent knows its role and has only the tools appropriate to it.

Topic 03

Model Context Protocol (MCP): Standardized Agent-to-Tool Communication

Before MCP, every agent framework had its own way of connecting agents to tools. LangChain had its tool abstraction. AutoGen had another. Custom deployments had their own ad hoc integrations. Every tool integration was framework-specific, meaning a Slack integration built for one framework wouldn't work with another. When a team switched frameworks, they rewrote their tool integrations from scratch.

MCP is Anthropic's answer to this fragmentation. It's an open standard — a JSON-RPC protocol — that defines how an agent (the MCP client) discovers and calls tools exposed by an MCP server. Any agent framework that implements the MCP client spec can use any MCP-compatible tool server, regardless of how either was built.

Insight

Think of MCP as USB for agent tools. Before USB, every peripheral had its own connector. USB standardized the interface so any peripheral could plug into any computer. MCP standardizes the interface so any agent can call any tool. The 97 million monthly downloads by March 2026 signal that the ecosystem has converged on this as the standard — not just for Anthropic's own products, but across the agent-building community.

Protocol Architecture

MCP uses a client/server model. The MCP server owns the tool — it knows how to call a GitHub API, query a PostgreSQL database, or post to Slack. The MCP client is the agent runtime — it calls the MCP server when it needs a tool executed. The agent never directly calls the underlying API; it always goes through the MCP server.

An MCP server exposes three things:

  • Manifest (Tool Discovery)
    A list of available tools with their names, descriptions, and input schemas. The agent reads the manifest to know what tools exist and how to call them. This is how an agent can dynamically discover capabilities at runtime rather than having them hardcoded.
  • Tool Handler (Execution)
    The implementation that actually runs when a tool is called. The agent sends a JSON-RPC request with the tool name and arguments. The server executes the tool, then returns a structured result. Errors surface as structured error objects, not raw exceptions.
  • Resource Handler (Data Exposure)
    A mechanism for the server to expose data that isn't tied to a specific tool call — configuration, reference documents, live data streams. Resources are read by the agent as part of context construction, not as tool calls.

Transport Modes

MCP supports three transport mechanisms, depending on where your MCP server lives relative to your agent:

Transport Use Case Latency
stdio Local MCP server running on the same machine as the agent. Fastest. Used in development and for local tool execution (filesystem access, local code execution). Sub-millisecond
HTTP + SSE Remote MCP server accessed over HTTP. Server-sent events for streaming responses. Standard for cloud-deployed tool servers. Works through firewalls and load balancers. Network-dependent
WebSocket Bidirectional streaming between agent and server. Used when the tool needs to push updates back to the agent in real time — progress updates, streaming results, event subscriptions. Network-dependent

The MCP Ecosystem in 2026

The ecosystem has expanded far beyond Anthropic's own servers. As of early 2026, there are MCP servers for GitHub, Slack, PostgreSQL, Notion, Stripe, Jira, Salesforce, Google Drive, and hundreds of community-built integrations. The practical implication: if your agent needs to integrate with a mainstream SaaS tool, there's probably already an MCP server for it. You define the tool selection logic; someone else built the integration.

COMPASS and MCP

Each COMPASS Researcher subagent connects to MCP servers for web search (Brave or Perplexity), a news aggregator, and a structured data source (Crunchbase or similar). The Planner connects to none — it only reasons. The Synthesizer connects to none — it only synthesizes from what the Researchers return. Separation of tool access is a forcing function for specialization. If a Researcher can't call the web search MCP server, it will fail fast rather than hallucinating information.

What an MCP Tool Call Looks Like

// Agent sends to MCP server (JSON-RPC 2.0) { "jsonrpc": "2.0", "method": "tools/call", "id": "req-001", "params": { "name": "web_search", "arguments": { "query": "B2B SaaS AI-native competitor pricing strategy 2025", "max_results": 5 } } } // MCP server response { "jsonrpc": "2.0", "id": "req-001", "result": { "content": [ { "type": "text", "text": "[Structured search results as text...]" } ], "isError": false } }
Topic 04

Agent-to-Agent (A2A): The Interoperability Standard for Agent Networks

MCP standardizes how agents talk to tools. A2A standardizes how agents talk to each other. These are different problems with different solutions, and both are necessary for a functioning agentic internet.

A2A is Google's open standard, published in 2025 and gaining rapid adoption. The core insight is that agents, from a network perspective, look like services: they have capabilities, they accept inputs, they produce outputs, they can be called remotely. A2A gives those services a common interface so that agents built by different teams, on different frameworks, can interoperate without custom integration work.

MCP Agent → Tool
Vertical integration
  • JSON-RPC 2.0 over stdio, HTTP+SSE, or WebSocket
  • MCP server exposes tools and resources
  • Agent discovers tools at runtime via manifest
  • Designed for tool execution and data retrieval
  • Anthropic-originated, broadly adopted
A2A Agent → Agent
Horizontal integration
  • HTTP-based with standard REST semantics
  • Each agent exposes an Agent Card at /.well-known/agent.json
  • Tasks are the unit of work; Messages carry communication
  • Designed for agent delegation and coordination
  • Google-originated, cross-platform adoption

These protocols are complementary, not competing. A COMPASS Researcher subagent might use MCP to call a web search tool, and use A2A to receive task assignments from the Planner and return results to the Synthesizer. MCP is the plumbing inside a single agent's tool use. A2A is the highway between agents.

The Agent Card

Every A2A-compliant agent publishes an Agent Card — a JSON document at the well-known URL /.well-known/agent.json. The Agent Card is the agent's public identity: what it can do, what inputs it accepts, what outputs it produces, and what authentication it requires. Any agent that wants to delegate work to this agent reads the card first to confirm capability match before sending a task.

// Agent Card for a COMPASS Researcher subagent { "name": "COMPASS-Researcher", "version": "1.2.0", "description": "Researches a scoped sub-question using web search and news aggregation. Returns a structured summary with source citations.", "capabilities": ["web-research", "news-search", "summarization"], "inputSchema": { "type": "object", "properties": { "sub_question": { "type": "string" }, "max_sources": { "type": "integer", "default": 5 } }, "required": ["sub_question"] }, "outputSchema": { "type": "object", "properties": { "summary": { "type": "string" }, "sources": { "type": "array" }, "confidence": { "type": "string", "enum": ["high", "medium", "low"] } } }, "auth": { "type": "bearer" } }

A2A Primitives

The A2A protocol defines three core primitives that every agent interaction uses:

Primitive What It Is Lifecycle
Task The unit of delegated work. Contains the input, priority, deadline, and a unique ID for tracking. submitted → working → completed / failed / requires-input
Message Communication between agents within a task. Can carry instructions, clarifications, partial results, or status updates. Many messages may occur within a single task. Stateless. Each message stands alone.
Artifact The deliverable output of a completed task. Structured according to the agent's output schema. Persisted and referenced by ID so downstream agents don't re-fetch. Created on completion. Immutable once created.

The requires-input task state is worth noting specifically. It's how an A2A agent implements HITL (human-in-the-loop) pauses without breaking the protocol. When a subagent reaches a decision point it can't resolve autonomously, it transitions the task to requires-input and sends a Message explaining what it needs. The orchestrator (or a human) responds, and the task resumes. This is structured ambiguity handling at the protocol level.

Topic 05

Shared State, Conflict Resolution, and Communication Overload

Multiple agents acting on the same environment create coordination problems that don't exist in single-agent systems. Two agents that can both write to the same database will eventually write conflicting values. Two agents that can both send emails will eventually send duplicates. Coordination isn't free — it must be designed.

Two Models for Agent State

The blackboard model (also called shared environment) gives all agents read and write access to a common data store. It's simple to implement: any agent can write its findings, and any other agent can read them. The problem is race conditions. If two Researcher subagents both find and write a conclusion about the same topic at the same time, the last write wins — and the first agent's work is silently discarded. In a system with tight timing, the outcome becomes nondeterministic.

Message passing is the alternative. Agents communicate only through explicit messages routed through the orchestrator or a message broker. No agent can read another agent's state directly — it can only receive what's been explicitly sent to it. This eliminates race conditions and makes the information flow auditable, at the cost of more overhead and more deliberate system design.

Insight

COMPASS uses message passing. The Planner sends task messages to each Researcher. Each Researcher sends result messages to the Synthesizer. No agent reads another's state. The orchestrator is the only entity that sees all messages. This means any failure is traceable: you can replay the message log and see exactly where the system diverged from expected behavior.

Conflict Resolution Strategies

When multiple agents produce conflicting outputs — two Researchers return contradictory findings, for example — the system needs a strategy for resolution. Three approaches are common in production:

  • Last-Write-Wins
    The most recent output overwrites earlier ones. Simple, deterministic, but information-destroying. Acceptable when outputs are independent and recency implies relevance. Not acceptable when outputs represent competing perspectives that should both be surfaced.
  • Critic Arbitration
    A dedicated Critic subagent receives all conflicting outputs and produces a structured verdict: which is more credible, why, and what the resolution is. More expensive — you're running an additional agent — but produces reasoned conflict resolution rather than arbitrary overwriting.
  • Orchestrator Override
    The orchestrator itself resolves conflicts using simple rules (prefer higher-confidence outputs, prefer more recent sources) or flags the conflict for human review. Works well when the orchestrator has enough context to judge, and when HITL escalation is already part of the system design.

Communication Overload

More agents does not mean better output. There's a real phenomenon — borrowed from distributed systems theory — where adding more agents past an optimal number increases coordination cost faster than it increases output quality. We see this in COMPASS: three well-scoped Researchers produce a better brief than five would, because the Synthesizer has to reconcile more outputs, some of which are redundant. Adding a fourth Researcher without adding complexity to the original question means that Researcher is covering ground already covered by another — and the Synthesizer has to spend more context figuring out which Researcher to trust when they partially overlap.

Common Mistake

Teams often increase the number of subagents in response to quality complaints, as if more agents will average out to a better answer. They won't. If the Researchers are returning low-quality outputs, the problem is almost always in the Planner's decomposition (sub-questions are too broad or too overlapping) or in the Researcher's system prompt and tool access — not in the number of Researchers. Fix the root cause, not the headcount.

Topic 06

Coordination Patterns That Break at Scale

Multi-agent systems that work in demos frequently fail in production. The failure modes are predictable — they're the same ones that appear in distributed computing, because agent fleets are distributed systems. Knowing them in advance is the difference between a system that degrades gracefully and one that fails silently.

  • Tail Latency
    In a parallel system, total latency equals the latency of the slowest subagent, not the average. If you have five parallel Researchers and one gets stuck on a slow web source for 45 seconds, the entire pipeline waits 45 seconds — even though the other four finished in 8. As you add more parallel agents, you increase the probability that at least one will be slow. Mitigation: set timeout budgets per subagent, and design the Synthesizer to work with whatever results have arrived when the budget expires.
  • Cascading Failures
    A failure in one subagent propagates upward and takes out the whole pipeline. The Planner fails to parse a malformed response from a Researcher, throws an exception, and the Synthesizer never runs. Design for partial failure explicitly: the Synthesizer should be able to produce a degraded brief from whatever results it receives. "Three out of five Researchers returned results; here is the brief with a note on missing coverage" is a valid, useful output. A crash is not.
  • Agent Swarm Anti-Pattern
    Spawning many undifferentiated agents in the hope that their aggregate output will be good. It won't. Quantity does not substitute for quality. Twenty undifferentiated Researchers without scoped sub-questions will return twenty overlapping, poorly focused summaries that the Synthesizer cannot coherently assemble. Three COMPASS Researchers with precisely scoped sub-questions and clear output schemas consistently outperform twenty ungoverned agents. Specificity beats volume.
  • Token Storms
    Each agent in the system has its own context window. When agents pass full outputs to the next agent in the pipeline, token costs multiply. A Researcher that returns a 4,000-token summary means the Synthesizer's context starts with 4,000 tokens per Researcher — 20,000 tokens before it writes a single word of synthesis. Mitigate by having each Researcher return a structured, compact summary (not its full reasoning trace), and by having intermediate agents compress before passing. The rule: summarize before you send.
Design Principle

Think of each agent handoff as a compression boundary. What does the next agent actually need? Not everything the current agent knows — just the distilled conclusion, with enough context to act on it. Design your output schemas to enforce this discipline. If a Researcher's output schema has a summary field with a 500-token max, it can't pass token storms downstream even if it tries.

Topic 07

Agent Factories: The Emerging Pattern for Knowledge Work

The multi-agent patterns we've covered so far assume a fixed system topology: you design the agents, define the roles, and deploy. The system runs the same way every time. This works well when your task type is predictable. It breaks down when you need to handle diverse task types that require different agent configurations.

Agent factories are the answer. A meta-orchestrator sits at the top of the hierarchy and, rather than dispatching to a fixed set of subagents, spawns the right agents dynamically based on the incoming task. The factory pattern turns agent composition into a runtime decision, not a design-time decision.

The meta-orchestrator reads the incoming task, classifies it, and instantiates the appropriate agent pipeline. Both pipelines use MCP-connected tools. Both use A2A for inter-agent communication. But the roles, sequencing, and handoff schemas are different because the task structure is different.

Real 2026 Examples

Coding agents are the most mature factory pattern in production. The typical pipeline: a Planner breaks down the bug report or feature request into subtasks, a Coder implements each subtask, a Tester runs the test suite against each implementation, a Reviewer checks for style and correctness, and a Deployer runs the deployment if all checks pass. The entire pipeline may run with zero human intervention for routine bugs. For novel architecture decisions, the Planner escalates to HITL before proceeding.

DevOps agent factories follow a similar pattern: Diagnostician identifies the incident root cause, Patch Agent writes the fix, Test Agent validates it in staging, Deploy Agent pushes to production. Mean time to resolution for known incident classes drops significantly when the factory can handle the full pipeline autonomously.

Organizational Analogy

An agent factory is structurally identical to a well-run project team with defined roles, structured handoffs, and a project manager who assigns the right team to the right project. The management insight that makes project teams work — clear role definitions, explicit deliverable schemas at each handoff, escalation protocols for blockers — is the same insight that makes agent factories work. If you've built effective human teams, you already understand the design principles. The implementation just happens to be in code.

When Not to Use a Factory

Factory patterns add significant engineering overhead: you need task classification, dynamic agent instantiation, inter-agent routing, and logging infrastructure that works across dynamically spawned agents. Don't build a factory if your system handles one task type at predictable volume. Build a factory when you have multiple distinct task types, when new task types appear frequently, or when task volume is variable enough that static agent allocation would be wasteful.

Lab · Module 04

Build COMPASS: A 3-Agent Research Pipeline

Build a hierarchical multi-agent system with a Planner, parallel Researchers using MCP-connected tools, and a Synthesizer. Compare quality and latency against a single-agent baseline running the same question serially.

This lab builds the COMPASS system end-to-end. You'll implement the Planner, three Researcher subagents, and the Synthesizer as separate agent runtimes communicating via structured JSON messages. You'll also build the single-agent baseline for comparison.

Architecture Overview

The pipeline: Planner receives the research question → decomposes into 3–5 sub-questions and outputs a structured task assignment → Researchers run in parallel, each fetching and summarizing sources via MCP-connected web search → Synthesizer receives all Researcher outputs and assembles the final brief.

Step 01
Implement the Planner Agent
The Planner receives the high-level research question and produces a structured JSON task assignment. Constrain its output schema so it can't return ambiguous or overlapping sub-questions. The schema enforces decomposition discipline at the source.
# Planner system prompt (abbreviated) PLANNER_SYSTEM = """ You are a research decomposition specialist. Given a research question, decompose it into 3–5 non-overlapping sub-questions. Each sub-question must be independently researchable with web search. Do not overlap — each sub-question covers distinct territory. Output ONLY valid JSON matching this schema: { "original_question": string, "sub_questions": [ { "id": "sq-1", "question": string, "focus_area": string, "search_hints": [string] // 2–3 suggested search queries } ], "synthesis_instructions": string // guidance for the Synthesizer } """ # Planner invocation def run_planner(research_question: str) -> dict: response = llm.invoke( system=PLANNER_SYSTEM, messages=[{"role": "user", "content": research_question}], response_format={"type": "json_object"} ) plan = json.loads(response.content) assert "sub_questions" in plan, "Planner output missing sub_questions" assert 3 <= len(plan["sub_questions"]) <= 5, "Expected 3–5 sub-questions" return plan
Step 02
Implement the Researcher Subagent with MCP Tool Access
Each Researcher receives one sub-question from the Planner's output and runs its own agentic loop — searching, reading results, and summarizing. Connect it to a web search MCP server. The Researcher's output schema enforces compact summaries (500 tokens max) with mandatory source citations and a confidence rating.
# Researcher system prompt RESEARCHER_SYSTEM = """ You are a research specialist. You receive a scoped sub-question and must find the best available information using web search. Search at least 3 sources. Evaluate source credibility. Return ONLY valid JSON: { "sub_question_id": string, "summary": string, // max 400 words — distilled findings only "key_findings": [string], // 3–5 bullet points "sources": [ {"title": string, "url": string, "relevance": "high"|"medium"|"low"} ], "confidence": "high"|"medium"|"low", "confidence_rationale": string } Do not include your search reasoning. Return only findings. """ # Researcher is an agentic loop — it calls tools until it has enough async def run_researcher(sub_question: dict, mcp_client) -> dict: messages = [{ "role": "user", "content": f"Research this sub-question:\n{sub_question['question']}\n\nSearch hints: {sub_question['search_hints']}" }] # Agentic loop — model calls web_search tool until satisfied while True: response = await llm.invoke_async( system=RESEARCHER_SYSTEM, messages=messages, tools=mcp_client.get_tools(), # tools from MCP manifest response_format={"type": "json_object"} ) if response.stop_reason == "tool_use": tool_result = await mcp_client.call_tool(response.tool_call) messages.append(response.to_message()) messages.append(tool_result.to_message()) else: return json.loads(response.content) # final JSON output
Step 03
Run Researchers in Parallel
Dispatch all Researcher subagents concurrently using async gather. Set a per-researcher timeout — 60 seconds is a reasonable starting point. Collect results and flag any that timed out or returned errors. The Synthesizer will receive a partial result set if any Researchers fail.
async def run_researchers_parallel(plan: dict, mcp_client) -> list[dict]: tasks = [ run_researcher(sq, mcp_client) for sq in plan["sub_questions"] ] # asyncio.gather preserves order; gather all even if some fail results = await asyncio.gather(*tasks, return_exceptions=True) researcher_outputs = [] for sq, result in zip(plan["sub_questions"], results): if isinstance(result, Exception): # Degraded result — note failure but continue researcher_outputs.append({ "sub_question_id": sq["id"], "error": str(result), "summary": None, "confidence": "failed" }) else: researcher_outputs.append(result) return researcher_outputs
Step 04
Implement the Synthesizer
The Synthesizer receives the Planner's synthesis instructions and all Researcher outputs. It has no tool access. Its job is to reconcile findings, note conflicts, and produce the final brief. It should explicitly acknowledge any failed Researcher slots so the reader knows what coverage is missing.
SYNTHESIZER_SYSTEM = """ You are a research synthesis specialist. You receive summaries from multiple research agents covering different aspects of a question. Your job: 1. Identify areas of consensus across sources 2. Surface and explain any contradictions 3. Note any coverage gaps (failed or low-confidence Researchers) 4. Write a coherent executive brief Output valid JSON: { "executive_summary": string, // 200–300 words "key_findings": [ // ordered by importance {"finding": string, "supported_by": [sub_question_id], "confidence": string} ], "contradictions": [ {"topic": string, "positions": [string], "resolution": string} ], "coverage_gaps": [string], "overall_confidence": "high"|"medium"|"low" } """ def run_synthesizer(plan: dict, researcher_outputs: list[dict]) -> dict: synthesis_input = json.dumps({ "original_question": plan["original_question"], "synthesis_instructions": plan["synthesis_instructions"], "researcher_outputs": researcher_outputs }, indent=2) response = llm.invoke( system=SYNTHESIZER_SYSTEM, messages=[{"role": "user", "content": synthesis_input}], response_format={"type": "json_object"} ) return json.loads(response.content)
Step 05
Build the Single-Agent Baseline
Implement a single agent that receives the same research question and runs all research serially — one search query at a time, in a single agentic loop. Use the same tools and the same underlying model. Record total latency and output quality for both systems on the same three test questions.
Step 06
Compare and Measure
Run both systems on three research questions of increasing complexity. Record wall-clock latency, total tokens used (across all agents in COMPASS vs. the single agent), and output quality scored on a rubric: coverage breadth, source diversity, finding accuracy, and citation quality. Document where COMPASS wins and where it doesn't — the single agent often wins on simple questions where decomposition adds no value.

Expected Findings

On complex, multi-faceted questions, COMPASS should win on coverage breadth and latency. The parallel execution eliminates serial bottlenecks. On simple, focused questions, the single agent typically wins: COMPASS adds coordination overhead (the Planner decomposition, the structured handoffs) without meaningful benefit. Document this. The ability to articulate when multi-agent helps and when it doesn't is the practical skill this lab builds.

Module 04 — Key Takeaways

  • Multi-agent is justified by three things: parallelism, specialization, and error isolation. "More sophisticated" is not a reason. Apply this test before adding any agent to a system.
  • Hierarchical topology is the production default — debuggable, auditable, clear accountability. Peer-to-peer is useful for iterative refinement but harder to debug. Market-based remains mostly theoretical in 2026.
  • MCP is the standard for agent-to-tool communication: JSON-RPC, three transport modes (stdio, HTTP+SSE, WebSocket), and a discovery manifest that lets agents find tools at runtime. 97M monthly downloads signals ecosystem convergence.
  • A2A is the standard for agent-to-agent communication: HTTP-based, Agent Cards for capability discovery, and three primitives (Task, Message, Artifact). MCP is vertical (agent-to-tool). A2A is horizontal (agent-to-agent). They are complementary.
  • Shared state is simple and prone to race conditions. Message passing is more overhead but auditable and safe. Choose message passing for production systems where debugging matters.
  • Four failure patterns to design against: tail latency (slowest subagent sets total time), cascading failures (design for partial results), agent swarm anti-pattern (specificity beats volume), and token storms (summarize before passing between agents).
  • Agent factories — meta-orchestrators that spawn agents dynamically — are the emerging pattern for knowledge work pipelines with variable task types. They add engineering overhead and are only worth building when task diversity and volume justify it.
