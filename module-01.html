What Makes Something
Agentic?

We start with the question that trips up most people: what actually distinguishes an AI agent from a workflow or a chatbot? This module builds the mental model that everything else in the curriculum depends on. You'll leave able to look at any AI system and classify it correctly — and understand exactly what you'd need to add to make it agentic.

Topic 01

The Spectrum from Static AI to Full Autonomy

Most people use the word "AI" to describe everything from a spell-checker to a system that can autonomously research, plan, and execute multi-step tasks. That's a problem. Lumping them together creates false expectations, bad architecture decisions, and a lot of wasted engineering effort. Let's draw the lines clearly.

Think of AI systems on a spectrum of autonomy — not a binary on/off, but a continuum from systems that do exactly one thing when told, to systems that pursue goals across time with minimal human direction. At each level, the system gains something qualitatively new. Understanding what that new thing is tells you both the power and the risk you're taking on.

Level 1
LLM API Call
Single prompt in, single completion out. No memory. No state. No action. Stateless text transformation.
Level 2
Chatbot
Multi-turn conversation. Maintains context across turns. Generates responses. Still only produces text — takes no actions.
Level 3
Automation
AI embedded in a fixed workflow. Triggers actions, but follows a predetermined script. Branches are pre-defined.
Level 4
Agent
Perceive, reason, act, observe — in a loop. Chooses which tools to use. Adapts based on results. Goal-directed.
Level 5
Agent Network
Multiple agents coordinating. Specialization, parallelism, delegation. An orchestrator decomposes tasks; subagents execute them.

The jump from Level 1 to Level 2 is about memory — the chatbot can refer back to what was said before. The jump from Level 2 to Level 3 is about action — the system can now do things, not just say things. But that action is scripted. You, the developer, wrote the branches in advance.

The critical jump is from Level 3 to Level 4. This is where the system stops following a script and starts making decisions. An agent at Level 4 looks at the current situation, reasons about what to do next, executes something, observes the result, and then reasons again. The path isn't predetermined. The model chooses it. That's what makes something agentic — and it's also what makes it harder to predict, test, and govern.

Key Insight

The distinguishing feature of an agent is not that it uses AI — everything on this spectrum does. It's that the AI decides what to do next based on what it observes, rather than following a path you've pre-specified. The model is the decision-maker, not the executor.

Level 5 — agent networks — builds on Level 4 by introducing coordination. Multiple agents, each with their own agentic loops, communicate and collaborate to accomplish tasks no single agent could handle efficiently. One agent plans, others research in parallel, another synthesizes. We cover this in depth in Module 4. For now, understand that agent networks are agents all the way down — the architecture adds coordination, not a new type of system.

Common Mistake

Teams often build a Level 3 automation with lots of branching logic and call it an agent. It isn't. If you wrote all the branches in code, the AI is not deciding — you are. The AI is just classifying inputs into your pre-written buckets. That's a useful system, but it's not agentic, and you should not expect it to handle novel situations gracefully.

Topic 02

The Four Pillars of Agency

Strip any agent down to its essentials and you find the same four capabilities: the ability to perceive its environment, the ability to reason about a goal, the ability to act through tools, and the ability to learn from the results of those actions. We call these the four pillars. Remove any one of them and what you have is no longer an agent — it's something less.

Pillar 01
Perceive
The agent can observe its environment. This includes the user's message, the results of previous tool calls, retrieved documents, database records, API responses — any information that gets placed into its context window.
Without this: The agent is blind. It can't respond to the actual situation.
Pillar 02
Reason
The agent can interpret what it perceives and decide what to do. It can decompose a goal into steps, evaluate options, recognize when it doesn't have enough information, and plan a path forward. The language model does the heavy lifting here.
Without this: The agent is reactive, not deliberate. It can't plan or handle novel situations.
Pillar 03
Act
The agent can do things in the world via tools — send an email, query a database, run code, call an API, write a file. Actions have real-world effects. This is what separates agents from chatbots, which can only produce text.
Without this: The agent is a very smart chatbot. It can only advise, not execute.
Pillar 04
Observe (Learn)
The agent receives feedback from the actions it took — a tool's return value, an error message, a confirmation — and uses that feedback to inform its next decision. This closes the loop. Without observation, there's no loop to speak of.
Without this: The agent acts blindly and can't correct course when something goes wrong.

These four pillars form what we call the agentic loop: Perceive → Reason → Act → Observe → (repeat). The loop continues until the agent decides its goal is met, hits a stop condition, or gets stuck and escalates. Every agent you'll ever encounter is an implementation of this loop, no matter how complex the framework wrapped around it.

Key Insight

The loop is the thing. Not the model, not the framework, not the tools. An agent is fundamentally defined by its loop — the repeated cycle of perceiving, reasoning, acting, and observing. When you're debugging a misbehaving agent, you're almost always debugging a broken loop: the agent observed something wrong, reasoned incorrectly, acted on bad information, or couldn't see the result of what it did.

Why "Learn" and Not Just "Observe"?

We use "Learn" alongside "Observe" deliberately. At the session level, the agent is learning from each action's outcome within a single run — it observes that a search returned no results, updates its internal reasoning, and tries a different query. This is in-context learning, and it's fundamental to what makes agents adaptive.

There's also a longer-horizon sense of learning: agents can be updated over time based on aggregated outcomes, user feedback, and evaluation data. That's a separate engineering problem (covered in later modules), but it shares the same underlying idea — the system improves based on the gap between what happened and what was intended.

The key point for now: an agent that can't learn from within-session observations will repeat its mistakes in the same run. That's a fundamental failure mode to design against.

Common Mistake

Giving an agent tools but no feedback mechanism. If your agent can call an API but the result never makes it back into the context window, the agent is acting blind. It has Pillar 3 (Act) but not Pillar 4 (Observe). The result is an agent that confidently does the wrong thing, repeatedly, with no ability to self-correct.

Topic 03

Linear Automations vs. Agentic Loops

The distinction between a linear automation and an agentic loop is the single most important line in this curriculum. Get it wrong and you'll spend months building sophisticated-looking systems that are actually just complex pipelines — unable to handle anything that deviates from the happy path you designed for.

Linear Automations: Predetermined Paths

A linear automation is a fixed sequence of steps. It may branch — "if customer sentiment is negative, route to tier 2 support; otherwise, send the FAQ" — but the branches are predetermined. A human wrote them. The AI might classify the situation, but it doesn't choose what happens next from open-ended possibility space. It selects from options you've pre-enumerated.

Linear automations are excellent for well-defined, repetitive processes with predictable variation. They're fast, cheap to run, easy to test, and easy to audit. Don't dismiss them — for many real business problems, they're exactly the right tool. The mistake is using them where you need genuine decision-making, then wondering why the system breaks on edge cases you didn't anticipate.

// Linear automation: all branches written by a human
function handleSupportTicket(ticket) {
  sentiment = classifysentiment(ticket.message)     // AI call: classification
  if (sentiment == "urgent"):
    escalate(ticket, tier=2)
  else if (sentiment == "billing"):
    route(ticket, queue="billing")
  else:
    send_reply(ticket, template="standard_faq")
}
// The AI classifies. The human decides what every classification means.

Agentic Loops: Dynamic Decision-Making

An agentic loop doesn't have predetermined branches. The agent reads the situation, decides what tool to call (if any), calls it, reads the result, and decides what to do next. The path through the problem space is determined at runtime by the model, not at design time by the engineer. This means the agent can handle situations the engineer never explicitly anticipated — which is its power, and its risk.

// Agentic loop: the model decides what to do next
while goal_not_met:
  observation = perceive(context)          // What do I know right now?
  action = reason(observation, goal)       // What should I do next?

  if action.type == "tool_call":
    result = execute_tool(action.tool, action.params)
    context.add(result)                    // Feed result back into context
  elif action.type == "respond":
    send_response(action.content)
    break
  elif action.type == "escalate":
    hand_off_to_human(action.reason)
    break

  // The model chose which branch. Not the engineer.

The loop continues until a stop condition is met — the goal is achieved, the agent decides to escalate, or a safety limit is reached. That stop condition is one of the most important things to design carefully. Agents without clear stop conditions can run indefinitely, burning tokens and sometimes causing damage in the process.

State Management in Agentic Systems

Linear automations typically pass state forward as a simple data object — each step reads and writes to a shared record. Agentic loops face a harder problem: the agent's state is its context window, which is finite. As the agent takes more steps and accumulates more observations, it has to make decisions about what to keep, what to summarize, and what to discard. This is the context engineering problem, and it's one of the primary reasons agents fail in practice. We cover it thoroughly in Module 3.

For now, understand the implication: the longer an agentic loop runs, the more important it becomes to manage what's in that loop's working memory. A well-designed agent doesn't just act intelligently — it curates its own context intelligently as it works.

Key Insight

Goal-directed behavior is the defining characteristic of an agentic loop. The agent isn't executing a plan you wrote. It's pursuing a goal you specified, and choosing its own path. This shifts the engineering challenge from "write all the branches" to "specify the goal clearly, give the agent the right tools, and build the right guardrails."

Topic 04

The Role of Tools, Memory, and Planning

Three capabilities elevate a language model from a text generator to a functioning agent: tools, memory, and planning. Understanding what each of these actually means at the architecture level — not just the marketing level — is essential for building systems that work.

Tools: Real-World Effects

A tool, in the technical sense, is any capability an agent can invoke that either has a real-world effect or returns information from outside the model. This covers a wide range: web search, code execution, database reads and writes, API calls to external services, file I/O, browser control, sending emails, issuing refunds. If it reaches outside the model's inference pass and touches the world, it's a tool.

This definition matters because it determines what an agent can actually do versus what it can only simulate. A model that's been told "you can issue refunds" but has no actual refund API to call is not an agent — it's a chatbot playing pretend. The tool is the mechanism that makes the action real.

At the architecture level, tool use works roughly like this: the model is given a list of available tools and their descriptions. When the model determines that invoking a tool is the right next step, it outputs a structured call — a tool name and its parameters. The system (not the model) executes the tool and returns the result. That result is fed back into the model's context, and the model continues. The model never directly executes anything. It only requests execution. This is a crucial safety boundary.

Key Insight

The model requests tool calls; the runtime executes them. This indirection is where you insert control — you can validate parameters, enforce rate limits, require approval, or block calls that exceed permission boundaries, all before any tool ever executes. Every guardrail you'll build in Module 5 lives in this gap between "model requests" and "system executes."

Tool design is its own discipline (covered in Module 2), but the foundational principle is: tools should be well-named, narrowly scoped, and honest about their error surfaces. Vague or overly powerful tools lead to overly powerful — and unpredictable — agents.

Memory: Four Types, Four Roles

When people talk about "agent memory," they're actually describing several different things that are easy to conflate. Each has a different architecture and a different set of tradeoffs.

In-context memory is everything in the active context window. It's fast to access and directly influences the model's reasoning, but it's finite and expensive. Everything the agent has done, seen, and concluded in the current session lives here — until you run out of space, at which point you have to make choices about what to keep.

External memory is any persistent store outside the model: a database, a vector store, a file system. The agent retrieves from it explicitly, usually through a search or lookup tool. This allows agents to work with far more information than fits in context, but retrieval introduces latency and the risk of retrieving the wrong thing. This is the foundation of retrieval-augmented generation (RAG) for agents.

Episodic memory stores records of past interactions and their outcomes. "Last time I tried this approach with this type of customer, it resulted in an escalation." This is currently underexplored in production agents but is an active area of development — agents that get better over sessions, not just within sessions.

Semantic memory stores factual, structured knowledge — product catalogs, policy documents, ontologies. This is typically accessed via retrieval and injected into context at the right moment. The agent doesn't "know" this information inherently; it knows where to look it up.

Planning: Deciding Before Acting

Planning is the process by which an agent decides what to do before doing it. At the simplest level, every step of a ReAct loop is a tiny act of planning — the model reasons about the current situation and decides on one next action. More sophisticated planning involves generating a multi-step plan upfront, evaluating options, anticipating failure modes, and then executing against the plan while remaining open to revising it when observations don't match predictions.

The architecture for planning varies from minimal (generate one step at a time) to elaborate (generate a full plan, critique it, revise it, then execute). More planning is not always better — it costs tokens, introduces latency, and can lead to over-commitment to a plan that turns out to be wrong. The right level of planning depends on the task. Simple, well-defined tasks need minimal planning. Long-horizon tasks with many steps and significant uncertainty benefit from upfront structure. We explore the specific planning patterns — chain-of-thought, tree-of-thought, skeleton-of-thoughts — in Module 2.

Common Mistake

Treating planning as a one-time activity at the start of a task. Agents that generate a plan upfront and then execute it mechanically without checking whether the plan still makes sense are fragile. Real agentic systems re-plan when observations deviate from expectations. A plan is a hypothesis about how to reach a goal — it should be revised when the evidence says it's wrong.

Topic 05

Generative AI vs. Agentic AI

Generative AI and agentic AI are not the same thing, and conflating them leads to a specific kind of confusion that's endemic in this field right now. Let's be precise.

Generative AI refers to AI systems that generate content — text, images, code, audio, video. The input is a prompt, the output is generated content. The interaction is fundamentally one-shot (or multi-turn within a conversation), stateless relative to the external world, and consequence-free in the sense that generating text doesn't inherently change anything outside the system. ChatGPT generating a draft email is generative AI. Midjourney creating an image is generative AI. GitHub Copilot suggesting the next line of code is generative AI.

Agentic AI refers to AI systems that pursue goals through action. The defining characteristics are the agentic loop, tool use with real-world effects, and the ability to take actions that have consequences beyond the conversation. An agent is not just generating content — it is doing things. It can read your email and draft a reply, or it can read your email, look up your calendar, check a policy database, draft a reply, send it, and update a CRM record. That's a fundamentally different category.

The Consequences Distinction

The most important difference between generative and agentic AI is the concept of real-world consequences. When a generative AI produces wrong output, a human reviews it and either uses it or discards it. The model's error doesn't propagate unless a human chooses to act on it. When an agentic AI takes a wrong action, the action has already happened. It may be reversible (update a record that can be updated again) or irreversible (send an email, execute a trade, delete a file). This is why agentic systems require a fundamentally different approach to safety and governance than generative systems.

Key Insight

With generative AI, errors are in the output — a human is the last line of defense before anything happens in the world. With agentic AI, errors are in the actions — the system is the last line of defense, because the human may not see what happened until after the fact. This asymmetry drives every safety and governance decision in Module 5.

The Scope of Effect

Generative AI systems are, by design, disconnected from the world except through the human reading their output. This is not a bug — it's a safety property. Agentic systems deliberately give up that safety property in exchange for the ability to act. The question for any given use case is: is the gain in capability worth the gain in risk? For many enterprise applications in 2026, the answer is yes — but only when the right controls are in place.

One way to think about this: generative AI amplifies a human's ability to produce. Agentic AI partially replaces the human's role in a process. That's a much bigger claim, and it demands much higher standards for reliability, safety, and auditability. The best agentic systems are built by teams that internalize this distinction from the start.

Common Mistake

Evaluating an agentic system using generative AI metrics. Measuring an agent by the quality of its text output misses what actually matters — whether it completed the goal, whether it took the right actions, whether it stayed within its sanctioned boundaries, and at what cost. An agent can produce beautifully written reasoning and still do the wrong thing. Task completion rate, action accuracy, and escalation appropriateness are the right metrics.

Topic 06

Real-World Examples: What Is and Isn't an Agent

Theory is useful. But the best way to internalize the distinctions we've built in this module is to look at real systems — or realistic analogs of them — and classify them honestly. This section does exactly that, across four domains: customer service, software development, research, and DevOps.

Meet Aria: A Customer Success Agent

Throughout this curriculum, we'll use a running example called Aria. Aria is a customer success agent deployed by a mid-size SaaS company to handle inbound support tickets. Her capabilities: read CRM data, query order history, look up product documentation, issue refunds up to $50, escalate to human agents with a context summary, and send templated and custom emails. She's not a hypothetical — she represents a class of agents that are being deployed right now in production.

Is Aria an agent? Yes. Here's how she maps to the four pillars. She perceives: she reads the incoming ticket, retrieves the customer's order history from the CRM, and looks up relevant documentation. She reasons: she assesses the issue, determines the appropriate resolution path, and decides whether she can handle it autonomously or needs to escalate. She acts: she issues refunds, sends emails, creates follow-up tasks, and escalates with structured summaries. She observes: if the email send fails, she sees the error and tries again or flags it. She loops: if the first resolution attempt doesn't resolve the customer's issue and they write back, she processes the new message, looks at the full conversation history, and tries again.

Example: Aria in Action

A customer writes: "My order hasn't arrived after 3 weeks and I want a refund." Aria's loop: (1) Perceive — read ticket, retrieve order record from CRM, see order was shipped 24 days ago and last tracking scan was 18 days ago. (2) Reason — this is a lost shipment, not a delay. Per policy, this qualifies for a refund or reship. Order total is $38, within her $50 autonomous refund authority. (3) Act — issue refund via payments API, send confirmation email with refund timeline. (4) Observe — payment API returns success code, email send returns 200. Goal met. Loop ends.

Notice what Aria didn't do: she didn't route to a human, she didn't ask clarifying questions she could answer herself by looking at the data, and she didn't generate a draft for a human to approve. She handled it — and only because her tools, her authority limits, and her goal were all clearly defined would this be safe to deploy.

What's Not an Agent: Common Misclassifications

An LLM-powered chatbot with no tools is not an agent. It can have a sophisticated conversation about how to fix your order problem. It cannot fix the order problem. It lacks Pillar 3 (Act) entirely. This is the most common source of confusion — companies deploy chatbots with impressive-sounding AI capabilities, but they're still just generating text responses for a human to act on.

A sentiment-based routing automation is not an agent. It uses AI for classification, but the routing logic is fully predetermined. The AI labels the input; the code decides what to do with the label. There's no agentic loop, no dynamic decision-making beyond the classification step. It's a Level 3 system on our spectrum — a useful one, but not an agent.

A coding assistant that suggests the next line is not an agent. It's generative AI doing next-token prediction within a conversation. Add a tool that lets it write files, run tests, read the test output, and decide what to change — now you have an agent (like GitHub Copilot Workspace or similar systems).

Coding Agents: The Software Development Domain

Coding agents are among the most mature examples of agentic systems in 2026. A coding agent receives a task — "fix the failing tests in module X" — and then works through it: reads relevant source files, runs the test suite, examines the failure output, edits the code, runs tests again, examines the new failure output, edits again. The loop continues until tests pass or the agent hits a stop condition (e.g., five iterations without progress, at which point it files a detailed issue and escalates).

The key distinction between a coding agent and a "AI-assisted IDE" is exactly the four pillars. The AI-assisted IDE waits for you to invoke it; a coding agent operates on your behalf. The IDE suggests, you decide; the agent decides, implements, tests, and delivers. That's not better in every context — for code you're actively writing, the IDE experience is often preferable. But for background tasks, refactors, and maintenance work, the agentic approach multiplies what a developer can accomplish.

Research Agents: The Information Domain

A research agent receives a question — "Summarize the competitive landscape for enterprise CRM software, focusing on pricing models and recent product changes" — and autonomously searches the web, reads articles, extracts relevant information, cross-references claims, and produces a structured synthesis. The agent decides which searches to run, which sources to trust, when it has enough information, and how to structure the output.

What makes this agentic rather than just "a really good search"? The model is making decisions about research strategy: what to search for next, whether the results so far are sufficient, when to go deeper on a specific thread and when to move on. The tool set might include web search, reading URLs, running calculations, and writing to a document. The agentic loop is doing continuous synthesis — each round of search informs the next decision.

DevOps Agents: The Infrastructure Domain

DevOps agents are where the stakes get highest and the case for careful guardrails becomes most urgent. A DevOps agent might receive a task: "investigate why the API service is returning elevated error rates and remediate if possible." It can query metrics dashboards, read logs, restart services, modify configuration, deploy a rollback, and alert the on-call engineer.

This is a full-featured agent: it perceives (reads metrics and logs), reasons (diagnoses the likely cause), acts (restarts a service, adjusts a config), and observes (checks whether the error rate dropped). The loop may run through multiple remediation attempts. But notice the risk surface: restarting a service in production, modifying configuration, or deploying a rollback are all consequential actions. A DevOps agent needs explicit limits, clear escalation paths for situations outside its authority, and human-in-the-loop approval for high-impact actions. Done right, this is extremely powerful. Done without controls, it's how you get a $12,000 compute bill from an agent trying to fix a CI loop all night.

Key Insight

The right question for any real-world agent deployment is not "can we build this?" but "what are the boundaries of its authority?" Every agent needs a clear answer to: what actions can it take without human approval, what actions require approval, and what situations require it to stop and escalate immediately. Aria can issue a $50 refund autonomously. She cannot issue a $500 refund — that requires a human. That limit is not a limitation; it's what makes her trustworthy enough to deploy at all.

Module 01 · Group Exercise

Classify the Systems

Below are 10 AI system descriptions. For each one, classify it on the autonomy spectrum (Level 1–5), identify which of the four pillars it has and which it's missing, and describe what you'd need to add to move it one level higher. Work individually first, then discuss as a group. The goal isn't to reach consensus on every answer — it's to practice the reasoning.

System 01
The Document Summarizer
A company has built an internal tool that takes any uploaded document and returns a bullet-point summary using an LLM. Employees paste in meeting transcripts, reports, or emails. The tool sends the text to the model with a fixed system prompt and returns the generated summary. There is no conversation history, no memory between sessions, and no connection to other systems.
Consider: Which pillars does it have? What does it lack? Is it useful? Is it an agent?
System 02
The FAQ Chatbot
A software company has deployed a chatbot on their support page. It can answer questions about their product based on a retrieval-augmented knowledge base of documentation. It maintains conversation history within a session, so it can handle follow-up questions. When it can't find an answer in its knowledge base, it tells the user to contact human support. It cannot take any actions: it cannot create tickets, check account status, or do anything but provide information.
Consider: This system has retrieval (a kind of tool). Does that make it an agent? What's the critical missing capability?
System 03
The Sentiment Router
An e-commerce company built an automated support pipeline. When a customer email arrives, an LLM classifies its sentiment and topic (positive, neutral, negative — and billing, shipping, product, other). Based on the classification, the system automatically routes the email to the appropriate queue and sends a templated acknowledgment. There are five queues, each with a predefined response template. No further AI processing happens after the initial classification.
Consider: This system takes real actions (routing, sending emails). Does that make it an agent? Who's really deciding what happens?
System 04
The Research Assistant
A market research firm built a system where a user types a research question. The system then autonomously runs multiple web searches (choosing the search queries itself), reads the top results from each search, decides whether it needs more information (and if so, runs additional searches), synthesizes what it found, and produces a structured report. The whole process takes 3–7 minutes and runs without any human interaction after the initial question is submitted.
Consider: Map this explicitly to the agentic loop. How many iterations might the loop run? What are the stop conditions?
System 05
The Code Reviewer
A software team has a bot that runs on every pull request. It reads the diff, generates a code review comment using an LLM, and posts the comment to GitHub. The comment may include suggestions for improvement, questions, or flags for potential bugs. The bot cannot approve or reject the PR, cannot modify the code, and cannot access any external systems beyond reading the PR diff and posting a comment.
Consider: This system posts to GitHub — that's a real-world effect. But is "posting a review comment" what we mean by agentic action? What's the meaningful distinction?
System 06
The Autonomous Bug Fixer
A development team uses an agent that can be assigned GitHub issues. The agent reads the issue, explores the relevant codebase (using file reading tools), writes a fix, creates a new branch, commits the changes, runs the test suite, reads the test output, iterates on the fix if tests fail (up to three times), and if tests pass, opens a pull request for human review. If it can't fix the issue within three iterations, it adds a comment to the issue explaining what it tried and what it found.
Consider: This is clearly an agent. Map out its full tool set, its stop conditions, and its escalation path. Where are the appropriate human checkpoints?
System 07
The Scheduled Report Generator
Every Monday at 9am, an automated system queries three databases (sales, support tickets, and web analytics), formats the data into a prompt, sends it to an LLM, and emails the generated weekly summary report to the leadership team. The queries are fixed. The prompt is fixed. The only thing the LLM does is generate prose from the structured data. The system never makes decisions based on what it finds.
Consider: This system is fully automated and touches multiple systems. Does automation equal agency? What would need to change to make it agentic?
System 08
The Customer Onboarding Agent
A B2B SaaS company has an agent that handles new customer onboarding. When a new account is created, the agent reviews the account details, sends a personalized welcome email (choosing from several templates based on the company size and industry it detects), schedules a kickoff call by checking both the customer's indicated availability and the team's calendar, creates an onboarding project in the project management tool, and assigns tasks based on the customer's product tier. If the customer hasn't completed setup steps after 48 hours, the agent sends a follow-up.
Consider: How many distinct tools does this agent use? Does it have a meaningful loop, or is it a sophisticated linear automation? What would indicate it has genuine agency?
System 09
The Competitive Intelligence Monitor
An agent runs nightly to monitor competitor activity. It searches the web for news about three named competitors, reads relevant articles, checks their public job postings (which indicate strategic investment areas), and compares current pricing pages to a stored baseline. If it detects significant changes — a major funding round, a new product launch, a significant pricing shift — it generates an alert with a structured summary and sends it to the strategy team's Slack channel. It also updates a persistent database with the new data for trend analysis.
Consider: This agent runs on a schedule without human initiation. Does that affect its level of autonomy? How does the persistent database change the picture compared to a purely in-context memory approach?
System 10
The Multi-Agent Procurement System
A large organization has a procurement system with three cooperating agents. A Procurement Planner agent receives purchase requests, decomposes them into sourcing tasks, and delegates to Supplier Research agents (which run in parallel, researching different potential vendors). The research agents return structured reports to the Planner, which synthesizes the findings, generates a recommendation, and sends it — along with all supporting evidence — to the Finance Compliance agent, which checks the recommendation against budget constraints and policy rules before either approving for human signature or flagging for human review.
Consider: Identify the orchestrator and the subagents. What are the boundaries of each agent's authority? Where in this pipeline should human review be mandatory, regardless of what the agents recommend?
Facilitation Guide
  • Start with individual work: give people 10–15 minutes to write down their classifications and reasoning before discussing. This prevents anchoring on the first person who speaks.
  • Systems 1, 2, and 7 are designed to provoke the "automation vs. agent" distinction. Expect disagreement on System 2 (the FAQ chatbot with retrieval) — use the disagreement to sharpen the definition of "agentic action."
  • System 5 (the code reviewer) is a useful edge case: it posts to GitHub (a real-world effect), but is that the kind of action that makes something agentic? Guide the discussion toward the idea that actions matter because of their consequences — and a code review comment is inherently advisory, not executable.
  • Systems 3 and 8 often generate the most debate about the automation/agent boundary. The key question: who is deciding what happens next — the model or the code? For System 8, probe whether the agent actually adapts its behavior based on what it finds, or just fills in a template.
  • System 6 is the clearest example of a genuine agent. Use it to anchor the group on what the four pillars look like in practice — have someone walk through each pillar explicitly.
  • System 10 is designed for a conversation about governance and human oversight. Resist letting the group optimize for efficiency; push them to think about where autonomy is appropriate and where it isn't, regardless of technical capability.
  • Close with this question: "For the systems you classified as not-yet-agents — is making them agentic actually the right move? What would you gain, and what new risks would you take on?" Not every system should be an agent.

By the End of This Module, You Should Be Able To...

  • Define an agent precisely — not as "AI that does things" but as a system that perceives its environment, reasons about a goal, acts via tools, and observes the results in a loop.
  • Place any AI system correctly on the autonomy spectrum from LLM API call to agent network, and explain what capability each level adds.
  • Identify the four pillars of agency (Perceive, Reason, Act, Observe) in any system and recognize which pillar is missing when a system fails to behave agentically.
  • Explain the critical distinction between a linear automation (where a human pre-specifies all branches) and an agentic loop (where the model decides what to do next based on what it observes).
  • Articulate why tools are the mechanism that gives agents real-world effect, how memory functions in four different modes (in-context, external, episodic, semantic), and why planning is a hypothesis to be revised rather than a script to be followed.
  • Explain the consequences distinction between generative AI and agentic AI — and why that distinction drives every safety and governance decision in production.
  • Classify real-world AI systems correctly, using customer service (Aria), coding agents, research agents, and DevOps agents as reference examples.
  • Articulate why not every system should be an agent — and what criteria to use when deciding whether adding agency is worth the added risk and complexity.
