How Agents Are Built:
Architecture Patterns

This module goes inside the machine. You'll learn the major architectural patterns used to build agents today — from the simplest ReAct loop to full orchestrator-subagent hierarchies — and understand when to reach for each one. Special attention is paid to the difference between single-agent and multi-agent designs, and why complexity should be justified by the task, not imported by default.

Topic 01

The ReAct Pattern: Reason + Act

Every agent architecture you'll encounter is a variation of one core idea: the model should be able to think, then do something, then look at what happened, then think again. This is the ReAct pattern — Reasoning and Acting interleaved in a loop — and it was formalized in a 2022 paper by Yao et al. that changed how people thought about grounding LLM outputs in real-world actions.

The insight behind ReAct is simple but powerful. A language model on its own is a one-shot function: input goes in, output comes out. There's no feedback, no ability to correct mistakes, no way to gather new information mid-task. ReAct breaks that constraint by giving the model a scratchpad — a place to reason — and a set of tools it can invoke. The output of each tool call becomes new input. The loop continues until the model decides it's done, or a stop condition fires.

In code terms, the loop looks like this: the model produces a "thought" and an "action" (a tool call with parameters). The runtime executes the tool and returns an "observation." That observation is appended to the conversation context. The model sees it and produces the next thought-action pair. Repeat until the model outputs a final answer instead of an action.

Aria in the ReAct Loop

A customer emails: "My order hasn't arrived — I was told it shipped two weeks ago." Aria's ReAct loop might look like this: Thought: I need to look up this customer's order history. Action: lookup_order(customer_id="CX-4421"). Observation: Order #8823 shipped 14 days ago, carrier USPS, last scan 10 days ago in Memphis. Thought: The shipment is stalled. I should check if it's within my refund authority. Action: get_order_value(order_id="8823"). Observation: $34.99. Thought: Under my $50 limit. I can issue a refund without escalating. Action: issue_refund(order_id="8823", amount=34.99). Observation: Refund issued. Confirmation #RF-9912. Thought: I should notify the customer. Action: send_email(...). Done.

What makes this pattern powerful is not any single step — it's the coupling between reasoning and evidence. Aria doesn't just issue a refund based on the customer's description. She looks up the order. She checks the value. She acts on facts, not assumptions. Every action is grounded in an observation, and every observation updates the reasoning. This is why agents built with ReAct are substantially more reliable than agents that try to plan everything upfront in a single pass.

The limitations of ReAct are worth naming honestly. The loop is sequential — each step waits for the previous one to complete. That adds latency. The model can also get stuck in repetitive cycles if it isn't told how to handle failed tool calls. And the quality of the reasoning depends entirely on the quality of the model and the quality of the tools. Bad tools produce bad observations, and bad observations lead the model astray. We'll cover tool design in the next section for exactly this reason.

When ReAct is enough

For a large fraction of real-world agent use cases, a single ReAct loop with a well-chosen tool set is all you need. If the task is bounded — a single user intent, a knowable set of actions, a clear completion state — don't reach for multi-agent complexity. Aria handles most customer service scenarios with a single loop and five to eight tools. The art is in choosing the right tools and writing the right stop conditions, not in layering more architecture on top.

Key Insight

ReAct is not a framework or a library — it's a design principle. Any system where a model can (1) reason about what to do, (2) invoke a tool, and (3) observe the result before deciding what to do next is implementing ReAct, regardless of what it's called. Most production agent frameworks are wrappers around this loop.

Topic 02

Tool Design: What Makes a Good Tool for an Agent

Tools are where agents make contact with the real world. A web search, a database query, a code execution sandbox, an API call to issue a refund — these are all tools. In Module 1, we established that tools are capabilities invoked by the agent and executed by the runtime. Now we need to go deeper: what separates a tool that makes an agent more reliable from one that makes it less reliable?

The short answer is: good tools are narrow, legible, and honest about failure. Bad tools are broad, ambiguous, or silent when something goes wrong.

Granularity: fewer, sharper tools

The temptation when designing an agent's tool set is to build everything into as few tools as possible. One "do_crm_stuff" tool that handles lookups, updates, and escalations sounds efficient. In practice it's a reliability disaster. The model can't easily distinguish which sub-capability to invoke. Error messages become ambiguous. The tool's parameter surface becomes complex enough that the model frequently misuses it.

The opposite mistake is over-splitting: a separate tool for every conceivable micro-action. Then the model spends reasoning cycles just navigating the tool list, and you've created an API design problem masquerading as an agent problem.

The useful frame is: one tool, one side-effect domain. A tool should do one type of thing in the world. lookup_order reads. issue_refund writes money. send_email creates external communication. These are categorically different side effects, and they belong in separate tools — not because of software engineering purism, but because the model needs to know the stakes of what it's calling before it calls it. A tool that reads is low risk. A tool that writes money is not. Keeping them separate lets you apply different confirmation logic, rate limits, and guardrails to each.

Aria's Tool Surface

Aria's tool list is deliberately small: lookup_customer, lookup_order, get_order_value, issue_refund (capped at $50), escalate_to_human, send_email. Six tools. Each does exactly one thing. The refund tool enforces its own cap — the model doesn't need to check, and a bug in the model's reasoning can't bypass the limit. This is defense in depth through tool design.

Naming: the model reads your tool names

Tool names and descriptions are not just documentation for human engineers. The model reads them. A poorly named tool — process_request, handle_thing, do_action — gives the model no signal about what the tool does or when to use it. This forces the model to infer from context, which introduces errors. Name your tools as if you were writing them for a competent but information-limited colleague who has no other context: issue_partial_refund is better than refund. search_knowledge_base is better than search.

Descriptions matter just as much. For each tool, describe what it does, what parameters it takes and why, what it returns, and under what conditions the model should or should not call it. This is not boilerplate — it is control logic. The description is part of the system prompt, and it shapes the model's behavior just as directly as any instruction you'd write there.

Error surfaces: what the model does when tools fail

Every tool call can fail. The network times out. The database returns an unexpected schema. The API rate limits you. The order ID doesn't exist. Your tool design needs to anticipate these cases and return structured, actionable error messages — not stack traces, not empty responses, not generic "something went wrong" strings.

A tool that returns {"error": "order_not_found", "order_id": "8823", "suggestion": "verify customer ID and retry"} gives the model something to work with. A tool that raises an uncaught exception crashes the loop. A tool that returns None silently may cause the model to hallucinate a successful result. The error surface is as important as the happy path.

Common Mistake

Wrapping third-party APIs as tools without error handling is one of the most common sources of agent unreliability. If the external API returns a 503, and your tool just passes that error string to the model, the model may interpret it as data, misunderstand it, or retry in a way that causes unintended side effects. Always translate external errors into agent-legible structured responses before they reach the model.

Think of tool design as the single highest-leverage point in building a reliable agent. You can't prompt-engineer your way out of a bad tool. The model is only as capable as the tools it has access to, and only as reliable as the contracts those tools expose.

Principle
One Side Effect Per Tool
Read tools and write tools should never be the same function. Separate stakes mean separate controls.
Principle
Descriptive Names
The model reads your tool names. Name them like documentation for an expert with no context.
Principle
Structured Errors
Every tool should return a legible error object. Silent failures and raw exceptions are both wrong.
Principle
Enforce Limits in Tools
Business rules like refund caps belong in the tool, not the prompt. Don't trust the model to remember limits.
Principle

A tool the model can safely call twice is far less dangerous than one with irreversible first-call effects.

Successful responses should include enough context for the model to know what to do next, not just confirm the action.
Topic 03

Memory Architecture: Where Agents Store What They Know

Agents don't have persistent memory by default. The model processes a context window — the finite block of text it sees at inference time — and produces output. When the interaction ends, nothing is retained unless you explicitly persist it somewhere. This is the fundamental memory problem in agent design, and how you solve it shapes everything from cost to capability.

There are four distinct memory types used in production agents. Understanding when to use each is as important as understanding how they work.

Type 01
In-Context Memory
Everything currently in the context window: the system prompt, conversation history, tool call results, injected documents. Fast and immediate — the model can reference it without any retrieval step. Limited by the context window size and cost per token.
Type 02
External Memory
A database, vector store, or file system outside the model. Practically unlimited capacity. Requires explicit read/write tool calls. The agent retrieves what it needs, when it needs it — this is the basis of Retrieval-Augmented Generation (RAG).
Type 03
Episodic Memory
A log of past interactions or tasks that the agent can query. "What did I do last time a customer had a stalled shipment?" Enables cross-session learning and consistency. Implemented as structured logs in an external store with retrieval capabilities.
Type 04
Semantic Memory
Embedded knowledge — product documentation, policy rules, FAQ content — stored as vector embeddings and retrieved by semantic similarity. The agent can answer "what's our return policy?" without hallucinating, because the answer lives in the store.

Short-term context vs. long-term storage

The context window is your agent's working memory. It's fast, it's always available, and the model can reference any part of it without a retrieval step. But it's expensive and finite. At 200k tokens — which sounds generous — you'll hit limits faster than you expect once you include a system prompt, tool definitions, conversation history, and multiple tool call results per loop iteration.

The general principle: keep only what's decision-relevant right now in context. Summarize or externalize everything else. For Aria, the active conversation thread stays in context. Her knowledge base — return policies, shipping partner SLAs, escalation procedures — lives in a vector store and is retrieved per-turn only when relevant. She doesn't need to read the entire policy document every time a customer asks about an order.

This is context engineering in practice: making deliberate choices about what information earns a spot in the context window for any given inference call. Context engineering is a skill that separates working prototypes from production-grade agents. Poor context engineering is the single most common cause of agents that perform well in demos and fail under real conditions.

Retrieval-augmented generation (RAG) for agents

RAG as a pattern is widely understood in the context of question-answering systems. In agent contexts, it takes on a slightly different character. The agent isn't just retrieving context for a single response — it's deciding, mid-loop, whether to retrieve and what to retrieve. That decision is itself a reasoning step. The agent might call a search_knowledge_base tool not because the user asked a factual question, but because the agent recognizes mid-task that it lacks the information to proceed reliably.

Retrieval quality matters enormously. A RAG system that retrieves the wrong chunks, or returns chunks that are semantically close but contextually wrong, will mislead the agent. Chunk size, embedding model choice, and retrieval scoring all become engineering decisions with direct consequences for agent reliability. This is not a detail you can treat as a commodity configuration — it requires evaluation against your specific data and task distribution.

Key Insight

There is no universal rule for how much to put in context vs. how much to retrieve. The right answer depends on your task's information density, your context budget, and how much retrieval latency you can tolerate. The wrong answer is to ignore the question and dump everything into context — that's expensive, slow, and often makes the model perform worse, not better, because useful signal gets drowned in noise.

Topic 04

Planning Patterns: How Agents Reason Before They Act

Not every task is simple enough for a linear ReAct loop. Some tasks require decomposing a goal into subgoals, evaluating multiple possible approaches, or generating a plan that spans dozens of steps before committing to any of them. This is the domain of planning patterns — explicit strategies for structuring how a model reasons through a complex problem before it acts.

Three patterns dominate current practice. Each makes a different tradeoff between latency, reasoning quality, and computational cost.

Pattern 01
Chain-of-Thought
When: most tasks
The model reasons step-by-step in a linear sequence before producing an answer or action. The original "let's think step by step" prompting technique. Low overhead — just adds tokens before the action. Works well for problems with a clear sequential structure. The ReAct loop is essentially chain-of-thought with tool calls interleaved.
Pattern 02
Tree-of-Thought
When: high-stakes, branching decisions
The model generates multiple candidate reasoning paths simultaneously, evaluates each, and selects the best one to continue. Think of it as beam search applied to reasoning — you explore branches before committing. High reasoning quality, high cost. Appropriate for tasks where choosing the wrong path has irreversible consequences (legal reasoning, code architecture decisions, complex debugging).
Pattern 03
Skeleton-of-Thoughts
When: complex tasks requiring upfront structure
The model first generates a high-level plan ("skeleton") with placeholder steps, then fills in each step — potentially in parallel. Optimized for latency on decomposable tasks. You get the plan's structure quickly and can parallelize the detail work. Good for document generation, multi-section research reports, or any task where the shape of the output is predictable even if the content isn't.

The latency-quality tradeoff

Chain-of-thought is fast and cheap. Tree-of-thought is expensive and slow but can find solutions that chain-of-thought misses. Skeleton-of-thoughts amortizes latency through parallelism but requires tasks that decompose cleanly.

In production, most agents use chain-of-thought by default and escalate to tree-of-thought only for explicitly high-stakes or high-ambiguity subtasks — and only if the latency budget allows. The error is reaching for tree-of-thought because it sounds more rigorous. More computation doesn't always mean better outcomes, and the additional tokens are real cost.

For COMPASS, the competitive intelligence network we'll introduce in the next section, skeleton-of-thoughts is the natural fit. The planner generates an outline of what needs to be researched, then researcher agents fill in each section in parallel, and a synthesizer assembles the result. The structure is predictable; only the content varies by run.

Key Insight

Planning patterns are implemented through prompting and context structure — they're not separate APIs or framework features. A tree-of-thought implementation is just a series of model calls with carefully designed prompts that ask the model to generate, evaluate, and select between alternatives. Understanding this means you can implement any planning pattern without waiting for a framework to support it.

Topic 05

Orchestrator vs. Subagent: Multi-Agent Patterns

A single agent with a well-designed tool set can accomplish a remarkable range of tasks. But some tasks genuinely benefit from parallelism, specialization, or separation of concerns that a single agent can't easily provide. This is when multi-agent architectures become worth their added complexity.

The core pattern is simple: an orchestrator decomposes a goal into scoped tasks, delegates each task to a subagent, and synthesizes the results. The orchestrator is itself an agent — it uses the same perceive-reason-act-observe loop — but its "tools" are other agents. The subagents have no awareness of each other; they receive a task, execute it, and return a result.

Introducing COMPASS

COMPASS is a three-agent competitive intelligence network. The business problem it solves: a product team needs a weekly briefing on competitor activity — pricing changes, new feature launches, press releases, partnership announcements. Doing this manually takes hours. Doing it with a single agent produces adequate but slow results. COMPASS is designed to be fast and thorough.

The Planner receives the goal ("compile this week's competitive intelligence for competitors A and B") and decomposes it into parallel research tasks. Both Researcher subagents run simultaneously — one per competitor. Each has access to web search tools, a news API, and a structured data store for pricing history. When both researchers complete, the Synthesizer receives their combined output and writes the final briefing.

Why does this beat a single agent? Three reasons. First, true parallelism: both competitors are researched at the same time, cutting wall-clock time roughly in half. Second, specialization: each Researcher subagent has a focused, minimal context — it doesn't need to know about the other competitor, the synthesizer's needs, or anything outside its task. This reduces the chance of context contamination and hallucination. Third, isolation: if Researcher A fails, Researcher B can still complete, and the synthesizer can flag the gap rather than failing entirely.

When to decompose, when not to

Multi-agent architecture is not free. Every agent boundary is a communication interface, and interfaces have costs: latency (waiting for subagent results), potential for information loss (summarized results may omit details the synthesizer needs), and debugging complexity (where did the error originate?). You should reach for multi-agent design when at least one of these conditions is true:

Parallelism provides a meaningful speedup. If COMPASS's researchers ran sequentially, there's no benefit to having two of them. Parallelism only pays when tasks can genuinely run at the same time and the task is latency-sensitive.

The context window is a genuine constraint. Research tasks that span 50 web pages, thousands of tokens of source material, and multiple API responses will overflow a single agent's context window. Breaking the task into chunks handled by separate agents with separate contexts is a real architectural necessity, not premature optimization.

Specialization reduces errors. A subagent with a narrow task and a lean context will outperform a single overloaded agent that's trying to do everything at once. Specialization is a reliability pattern, not just an organizational preference.

Common Mistake

Building multi-agent systems before validating that a single agent can't do the job. Every additional agent is an additional point of failure, an additional latency cost, and an additional thing to debug. Start with one agent. Add complexity only when you have evidence — not intuition — that it's needed.

Delegation and result synthesis

The orchestrator's job isn't just decomposing tasks — it's writing good task specifications. A subagent that receives a vague task will produce a vague result. The Planner in COMPASS doesn't tell Researcher A "look into Competitor A." It tells Researcher A: "Find any pricing changes, new product announcements, partnership press releases, and significant customer reviews published by or about Competitor A in the past 7 days. Return structured JSON with fields: [pricing_changes, product_news, partnerships, notable_reviews]. If no data is found for a field, return an empty array with a note explaining the absence."

Specificity in task delegation is the orchestrator's primary responsibility. The Synthesizer's job is equally demanding: it must recognize when subagent outputs are contradictory, when a gap exists because no data was found vs. because a subagent failed, and how to present uncertainty honestly in the final output. Synthesis is not concatenation — it's judgment applied to multiple imperfect inputs.

Topic 06

When NOT to Use Agents

Agents are powerful. They're also slow, expensive, and harder to debug than a simple pipeline. Every architectural decision has a cost, and the cost of unnecessary agentic complexity is real: higher latency, higher token spend, more failure modes, and harder-to-maintain code.

Here's a useful heuristic: if you can express the task as a directed acyclic graph where every node is a deterministic function, don't use an agent. Use a pipeline. A pipeline is faster, cheaper, and completely auditable. Its failure modes are enumerable. You can test each node in isolation. An agentic loop can't give you any of those properties without significant additional investment.

The case for pipelines

Consider a common enterprise workflow: extract data from an invoice PDF, validate the fields against a schema, look up the vendor in a database, write the result to an accounting system. This is four deterministic steps with no branching logic, no information gaps, and no ambiguous decision points. Turning this into an agent doesn't make it smarter — it makes it slower, more expensive, and harder to test. The right tool is a pipeline: OCR → validator → database lookup → write.

Agents earn their cost when the task has genuine uncertainty or requires real-time information gathering. The invoice pipeline has no uncertainty. The structure of the input may vary, but that's an extraction problem, not an agency problem. An LLM call in the extraction step is fine; an agentic loop is overkill.

Approach Latency Cost Reliability Best For
Static Pipeline Low Low High Fixed, deterministic workflows
Single LLM Call Low Low Medium Classification, extraction, single-step generation
ReAct Agent Medium Medium Medium Dynamic tasks requiring tool use and iteration
Multi-Agent Network High* High Variable Parallel research, expert specialization, scale

* Can be lower than single-agent if tasks run truly in parallel

The cost of latency

Every loop iteration adds latency. In a customer-facing product, 3–5 seconds per turn is survivable. 15–20 seconds is not. If your task requires 8–10 tool calls to complete, you need to budget that latency explicitly. Either the task is appropriate for async processing (queue it, notify the user when done), or you need to redesign it to require fewer loop iterations, or you shouldn't use an agent at all.

Cost scales with tool calls. Every iteration is one or more LLM inference calls plus the tool execution. At production scale, poorly bounded agent loops can generate thousands of unnecessary LLM calls per day. Set explicit iteration limits. Monitor actual vs. expected loop depth. Treat a loop that takes more than N iterations as a bug signal, not just slow performance.

Key Insight

The autonomy spectrum from Module 1 isn't just a taxonomy — it's a decision tree. Start at the simplest point that could possibly work. Move right only when you have clear evidence that the simpler approach has a ceiling you've hit. Most real-world AI applications that are described as "agents" are, on inspection, pipelines with one LLM call. That's not a failure — that's appropriate engineering.

Topic 07

The 12-Factor Agent Principles

The 12-Factor App methodology, published by Heroku engineers in 2011, codified a set of practices that made web applications easier to build, scale, and operate. As agent systems have matured, an analogous set of principles has emerged — a practical checklist for building LLM-based agents that are reliable, observable, and maintainable in production. These aren't theoretical ideals; they're lessons extracted from real systems failing in predictable ways.

If you build agents long enough, you will rediscover most of these the hard way. Consider this an advance preview of the lessons.

01
Natural Language to Tool Calls
Agents translate user intent into structured actions. The gap between ambiguous natural language input and a precise tool call is where errors happen. Invest in prompt engineering that reliably maps intent to the correct tool and parameters. Test this mapping explicitly.
02
Own Your Prompts
Don't let frameworks abstract away your system prompts. If you can't read and edit the exact text the model receives, you can't control its behavior. Frameworks that hide prompts make debugging nearly impossible. Own every token in your context.
03
Own Your Context Window
Know exactly what the model sees at inference time. Understand what's in the system prompt, the conversation history, the tool definitions, and any injected documents. Surprise context is the most common source of surprising behavior. Log and inspect the full context during development.
04
Tools Are the Interface to the World
Everything outside the model is a tool. Databases, APIs, file systems, other agents — if the model needs to interact with it, it needs a tool. Don't try to bake external state into prompts directly. Design the tool interface deliberately, not as an afterthought.
05
Small, Focused Agents
One agent, one job. An agent with 20 tools and a 5,000-token system prompt covering 8 different domains is an agent waiting to fail. Focused agents with narrow scopes are easier to prompt, easier to test, and easier to fix when they break. Specialize before you generalize.
06
Handle Errors Gracefully
Model the failure modes before you deploy. What happens when a tool times out? When the model produces a malformed tool call? When a subagent returns a partial result? Build recovery logic for each case. An agent that crashes on first error is not a production-grade agent.
07
Support Human-in-the-Loop
Design for escalation from the start. Every agent should have a clear escalation path to a human for cases where it lacks authority, confidence, or information to proceed. HITL is not a fallback for broken agents — it's a first-class design decision. Build it in, not on top.
08
Return Results, Don't Just Act
Agent outputs should be observable. Every significant action an agent takes should produce a structured result that can be logged, inspected, and verified — not just a side effect in the world. Observability is how you debug production agents. Make outputs first-class artifacts.
09
Stateless Agents When Possible
Implicit state accumulation — where an agent's behavior changes based on undocumented prior actions — is a major source of subtle bugs. Prefer agents that receive all necessary context in each call and don't rely on persistent internal state. When state is necessary, make it explicit and external.
10
Explicit Stop Conditions
Every agent loop needs a defined exit. What counts as task completion? What triggers an escalation? What is the maximum number of iterations? What happens when the loop has been running for N seconds? Define these before you deploy, not after your first runaway loop burns through your API budget.
11
Log Everything
Agent traces — the complete record of every thought, tool call, and observation in a session — are first-class artifacts. Log them. Store them. Make them searchable. When an agent fails, the trace is your only window into what happened. Logging is not optional infrastructure; it is debugging infrastructure.
12
Evaluate Constantly
Evals are not optional. They are how you know your agent works, how you detect regressions when you update prompts or models, and how you justify confidence to stakeholders. Build an eval suite before you ship. Run it on every significant change. Treat eval coverage like test coverage — a measure of how much you actually know about your system's behavior.

These twelve principles aren't sequential — you don't implement them in order. They're a checklist to hold up against any agent system you build. If you're violating several of them, you're accumulating technical debt that will surface as production incidents. The earlier you identify and address each one, the less painful the reckoning.

Key Insight

Principles 2 and 3 — own your prompts, own your context — are the ones most frequently violated by teams using agent frameworks. The convenience of high-level abstractions is real, but the loss of visibility is costly in proportion to how much your agent is doing. Use frameworks that let you inspect and override the underlying context. Treat any framework that hides this from you as a red flag.

Module 02 Lab

Build a Minimal ReAct Agent from Scratch

No frameworks. No magic. Just an LLM, a tool loop, and a stop condition. The goal is to understand the mechanics before you abstract them away. By the end of this lab, you'll have a working ReAct agent in fewer than 100 lines of Python, and you'll understand exactly what a framework like LangChain or Claude's agent SDK is doing under the hood.

We're building a minimal version of Aria's customer service loop. The agent has three tools: lookup_order, issue_refund, and send_email. We'll implement them as stubs — they return plausible fake data — so you can run the full loop locally without any external API dependencies beyond an LLM.

Step 01
Define your tools as Python functions
Each tool is a regular Python function that takes typed parameters and returns a dictionary. The structure of the return value is what the model will see as its "observation." Write clean, structured returns — not strings, not raw exceptions.
# tools.py — stub implementations for the lab

def lookup_order(order_id: str) -> dict:
    """Look up an order by ID. Returns order details or an error."""
    # Stub: return fake data
    orders = {
        "ORD-001": {
            "order_id": "ORD-001",
            "customer": "Alex Rivera",
            "item": "Wireless Headphones",
            "value": 89.99,
            "status": "shipped",
            "last_scan": "Memphis, TN — 10 days ago",
            "carrier": "USPS"
        },
        "ORD-002": {
            "order_id": "ORD-002",
            "customer": "Sam Chen",
            "item": "Phone Case",
            "value": 19.99,
            "status": "delivered",
            "delivered_at": "2 days ago"
        }
    }
    if order_id in orders:
        return {"success": True, "order": orders[order_id]}
    return {
        "success": False,
        "error": "order_not_found",
        "order_id": order_id,
        "suggestion": "Verify the order ID and retry."
    }


def issue_refund(order_id: str, amount: float) -> dict:
    """Issue a refund. Capped at $50. Returns confirmation or error."""
    REFUND_CAP = 50.00
    if amount > REFUND_CAP:
        return {
            "success": False,
            "error": "exceeds_authority",
            "requested": amount,
            "cap": REFUND_CAP,
            "suggestion": "Escalate to human agent for refunds over $50."
        }
    return {
        "success": True,
        "refund_id": f"RF-{order_id}-{int(amount * 100)}",
        "amount": amount,
        "order_id": order_id,
        "status": "processed"
    }


def send_email(to: str, subject: str, body: str) -> dict:
    """Send an email to the customer."""
    print(f"\n--- EMAIL SENT ---")
    print(f"To: {to}")
    print(f"Subject: {subject}")
    print(f"Body: {body}")
    print(f"------------------\n")
    return {"success": True, "message_id": f"MSG-{hash(subject) % 10000}"}
Step 02
Define your tool schemas for the model
The model needs to know what tools are available, what parameters they take, and what they do. This is the tool definition that goes into the context. In a real system this would be formatted per your LLM provider's spec (e.g., Anthropic's tools format). Here we use a simple dict structure to keep it provider-agnostic.

Step 03
Build the tool dispatcher
The dispatcher is the runtime's job: it receives the model's tool call (name + parameters), routes it to the right function, and returns the result. This is the "executed by the runtime" part from Module 1's definition of tools. It's a plain Python dict lookup — nothing magic here.
# dispatcher.py — route tool calls to their implementations

import json
from tools import lookup_order, issue_refund, send_email

TOOL_REGISTRY = {
    "lookup_order": lookup_order,
    "issue_refund": issue_refund,
    "send_email": send_email,
}

def dispatch_tool(tool_name: str, parameters: dict) -> str:
    """
    Execute a tool call and return the result as a JSON string.
    The JSON string becomes the 'observation' in the next loop iteration.
    """
    if tool_name not in TOOL_REGISTRY:
        result = {
            "success": False,
            "error": "unknown_tool",
            "tool_name": tool_name,
            "available_tools": list(TOOL_REGISTRY.keys())
        }
    else:
        try:
            result = TOOL_REGISTRY[tool_name](**parameters)
        except TypeError as e:
            result = {
                "success": False,
                "error": "invalid_parameters",
                "detail": str(e)
            }
    return json.dumps(result, indent=2)
Step 04
Build the ReAct loop
This is the core of the lab. The loop calls the model, checks whether the model wants to use a tool or is done, dispatches the tool if needed, appends the observation to the conversation, and repeats. The stop conditions are: the model produces a final answer (no tool call), or we hit the iteration limit.
# agent.py — the ReAct loop

import json
import anthropic
from tool_schemas import TOOL_SCHEMAS
from dispatcher import dispatch_tool

client = anthropic.Anthropic()  # uses ANTHROPIC_API_KEY env var

SYSTEM_PROMPT = """You are Aria, a customer success agent.

You help customers with order issues. You have access to tools to look up orders,
issue refunds (up to $50 only — never exceed this limit), and send emails.

When handling a request:
1. Always look up the order before taking any action.
2. Verify the order value before issuing a refund.
3. Send a confirmation email after any action you take.
4. If a refund would exceed $50, tell the customer you're escalating to a human.

Be direct, clear, and helpful. Don't over-explain."""

MAX_ITERATIONS = 10  # stop condition: never run more than 10 loop turns


def run_agent(user_message: str) -> str:
    """
    Run the ReAct agent loop for a single user request.
    Returns the agent's final response.
    """
    messages = [{"role": "user", "content": user_message}]

    for iteration in range(MAX_ITERATIONS):
        print(f"\n[Loop iteration {iteration + 1}]")

        # Call the model
        response = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=1024,
            system=SYSTEM_PROMPT,
            tools=TOOL_SCHEMAS,  # tool definitions go here
            messages=messages
        )

        print(f"Stop reason: {response.stop_reason}")

        # Check stop condition: model is done (no more tool calls)
        if response.stop_reason == "end_turn":
            # Extract the final text response
            final_text = next(
                (block.text for block in response.content if hasattr(block, "text")),
                "I've completed the requested actions."
            )
            print(f"\n[Agent finished after {iteration + 1} iterations]")
            return final_text

        # Process tool use
        if response.stop_reason == "tool_use":
            # Add the model's response (including tool calls) to history
            messages.append({"role": "assistant", "content": response.content})

            # Execute each tool call and collect results
            tool_results = []
            for block in response.content:
                if block.type == "tool_use":
                    print(f"  Tool call: {block.name}({json.dumps(block.input)})")
                    observation = dispatch_tool(block.name, block.input)
                    print(f"  Observation: {observation[:200]}...")  # truncate for readability

                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": observation
                    })

            # Append observations as the next user turn
            messages.append({"role": "user", "content": tool_results})
            # Loop continues — model sees the observations and decides next step

        else:
            # Unexpected stop reason — treat as completion
            print(f"[Unexpected stop reason: {response.stop_reason}]")
            break

    return "I wasn't able to complete this request within the allowed number of steps."


# --- Run it ---
if __name__ == "__main__":
    test_request = (
        "Hi, I'm Alex Rivera. My order ORD-001 hasn't arrived — "
        "it was supposed to come two weeks ago. My email is alex@example.com. "
        "Can you help?"
    )

    print("=== ARIA CUSTOMER SERVICE AGENT ===")
    print(f"Customer: {test_request}\n")

    response = run_agent(test_request)
    print(f"\n=== FINAL RESPONSE ===\n{response}")

Once the basic loop is working, there are three extensions worth trying before moving to Module 3:

Extension A
Add an escalation tool
Implement an escalate_to_human tool that logs the escalation, pauses the loop, and returns a structured escalation record. Observe how the agent decides to use it vs. the refund tool. Notice what happens to the stop condition when escalation is the final action — does the loop terminate correctly?
Extension B
Log the full trace
Add logging to serialize the complete messages list at the end of each run to a JSON file. Open a few trace files and inspect them. This is exactly what production agent observability looks like. The trace is the artifact. Notice how much context accumulates over even a simple 4-step interaction.
Extension C
Induce a failure and build recovery
Modify lookup_order to return an error 50% of the time. Watch the agent struggle. Then update the tool's error response to include a clearer suggestion, and update the system prompt to instruct the agent to retry once on lookup failure. Compare the agent's behavior before and after. This is what "handle errors gracefully" means in practice.
